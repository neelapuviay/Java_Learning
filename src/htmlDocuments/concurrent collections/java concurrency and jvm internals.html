Java Concurrency & JVM Internals

Master Reference: Memory Architecture, Locks, Volatile, CAS, and Core Collections

1. The Big Picture: Software Memory vs. Physical Hardware

One common point of confusion in interviews is mixing up JVM software structures with real physical hardware.

A. JVM Software World (All in RAM)

  • Thread Stack: Each thread gets its own private execution stack. It holds local primitive variables (e.g., int temp = 10;) and object references (memory pointers). No other thread can read your stack.
  • Heap: A shared memory warehouse. All objects (e.g., new BankAccount()) and their instance fields live here. Any thread with a reference to an object can read or write its fields.
  • Metaspace: Holds class blueprints, method bytecode instructions, and constant pools.
Important: The JVM Thread Stack and the JVM Heap do not live on separate microchips! Both live inside your computer's physical RAM memory stick.

B. Physical Hardware World (The Real Chips)

Why Did Chip Makers Add L1, L2, and L3 Caches?

Reading directly from physical RAM takes ~100 to 200 clock cycles (~100 ns). If the CPU had to wait for RAM on every single instruction, it would spend 95% of its time doing nothing.

To keep things fast, the CPU automatically copies active parts of RAM into on-chip L1 and L2 caches (~1 ns). When a thread reads an object from the Heap, the hardware silently pulls that piece of RAM into Core 1's private L1 cache.

2. Why Single-Threaded StringBuffer is Slower than StringBuilder

A frequent interview question: "If only one single thread runs my program, why is StringBuffer still measurably slower than StringBuilder in a loop of 10 million appends?"

The Technical Reasons

  1. Atomic CPU Instructions: Every time a thread enters and exits a synchronized method, the JVM executes machine-level instructions (like CMPXCHG on x86) to update the object's header. Even without any competition from other threads, these atomic instructions force CPU pipelines to stall.
  2. Memory Barriers: Leaving a synchronized block issues a memory fence instruction. This tells the CPU: "Stop reordering instructions and ensure writes are visible." This stops the CPU from executing independent instructions in parallel.
  3. JIT Inlining & Vectorization Blocked: The C2 JIT compiler loves StringBuilder because it can inline the code directly into your loop and use SIMD vectorization (copying 16-32 characters in a single CPU cycle). StringBuffer contains complex exception edges and lock safepoints that block these optimizations.
  4. Biased Locking is Deprecated/Removed: Older JVMs tried to favor single threads by "biasing" locks. Because biased locking was complex and caused long safepoint pauses during revocation, it was disabled and removed in modern JDKs. Uncontended locks now default to lightweight locks using atomic CPU operations every single time.

3. How Object Locks Work (Sync vs. Non-Sync Methods)

In Java, locks belong to the entire object instance (stored in the Mark Word of the object's 12-byte header), not to individual methods. 

class BankAccount {
    int balance = 1000;

    public synchronized void withdraw(int amt) {
        balance -= amt;
    }

    public int checkBalance() {
        return balance; // Non-synchronized!
    }
}

The House Analogy

Think of the BankAccount object as a house:

  • The withdraw() method is a locked private room. To enter, you must hold the single house keycard.
  • The checkBalance() method is an open outdoor porch. There is no lock on the porch. Anyone can walk in without asking for the keycard.

Interview Scenarios

  • Scenario 1: Thread A is inside withdraw(). Can Thread B call checkBalance()?
    YES! Because checkBalance() is non-synchronized, it never asks for the lock. It walks right in and reads balance immediately.
  • Is this consistent?
    NO! This is a bug (Stale Read / Dirty Read). Thread B might see the balance before the withdrawal, or see a half-written value.
  • The Golden Rule of Synchronization: If you protect a variable with a lock during writes, every reader must also acquire the exact same lock to guarantee consistency.

4. The Truth About volatile (Visibility vs. Atomicity)

Many developers wrongly assume volatile replaces locks. Let's see what it does and where it fails.

What volatile Actually Does (Visibility)

Normally, if Core 1 changes a variable, the update stays in its private L1 cache. Core 2 might keep reading the old value from its own L1 cache.

When a field is marked volatile, the hardware uses the MESI Cache Coherence Protocol over the CPU bus:

  1. Core 1 writes the new value to its L1 cache.
  2. The hardware immediately broadcasts an "Invalidate" message over the internal CPU bus.
  3. Core 2's cache controller marks its local copy as invalid.
  4. When Core 2 reads that variable, it fetches the fresh value directly from Core 1's cache via L3/bus in ~10–15 ns. (It does not need to wait 100 ns for RAM!)

Why volatile Fails for count++ or balance -= 200

An operation like balance = balance - 200 is not one step. To the CPU, it is three separate operations: 

Step 1: READ value from cache/memory into CPU Register RAX.
Step 2: CALCULATE (RAX - 200) inside Register.
Step 3: WRITE updated RAX value back to cache/memory.

The Lost Update Problem (Step-by-Step Failure Timeline)

Assume volatile int balance = 1000;. Two threads try to withdraw 200 at the same moment:

  • Time 0 ns: Thread 1 reads balance (1000) into its register.
  • Time 0 ns: Thread 2 reads balance (1000) into its register.
  • Time 1 ns: Thread 1 computes 1000 - 200 = 800.
  • Time 1 ns: Thread 2 computes 1000 - 200 = 800.
  • Time 2 ns: Thread 1 commits and writes 800 to memory.
  • Time 3 ns: Thread 2 commits and writes 800 to memory!

Result: Two separate withdrawals of 200 occurred, but the balance is 800 instead of 600! One withdrawal was permanently lost.

Why Can't the CPU "Auto-Fix" This Using Caches?

Because the calculation was already completed inside Thread 2's private CPU Register before the invalidation arrived! The CPU cannot guess your mathematical intent or roll back instructions automatically. The developer must make the multi-step operation atomic in code.

5. CAS (Compare-And-Swap) & AtomicInteger

How do we make operations atomic without paying the high cost of coarse synchronized locks? Hardware-level CAS.

How CAS Works

The CPU has a built-in silicon instruction called LOCK CMPXCHG (Compare and Exchange). It performs an atomic conditional update in a single cycle:

"Check address X. If the value in memory is currently 1000, swap it with 800. If someone changed it and it's not 1000, reject the swap and tell me."

The CAS Retry Loop (Under the Hood of AtomicInteger)

// How Java AtomicInteger avoids locks:
public void withdraw(int deduct) {
    int current;
    int updated;
    do {
        current = balance.get();         // 1. Read fresh value
        updated = current - deduct;     // 2. Calculate in register
    } while (!balance.compareAndSet(current, updated)); // 3. Atomic hardware swap
}

If Thread 2's CAS fails because Thread 1 changed the balance first, Thread 2 does not crash or block. It simply loops around, reads the fresh value (800), recalculates (600), and tries the CAS again.

Common Interview Trick Question:

"Should I declare private volatile AtomicInteger balance;?"

Answer: NO. Declaring volatile AtomicInteger only makes the object reference pointer volatile. Inside the official Java source code, the integer itself is already declared volatile: 
public class AtomicInteger extends Number {
    private volatile int value; // Already volatile inside!
}
Always declare it as: private final AtomicInteger balance = new AtomicInteger(1000);

6. Under the Hood: ConcurrentHashMap vs Hashtable

Why did Java introduce ConcurrentHashMap when Hashtable was already thread-safe?

The Problem with Legacy Hashtable

In Hashtable, every single method (get, put, remove, size) is marked synchronized. The entire table has one single lock. If Thread 1 is reading key "A", Thread 2 cannot even read key "Z". It is coarse and slow.

How ConcurrentHashMap Achieves Lock-Free Reads & High-Speed Writes

Bucket Array:
[ Bucket 0 ] ──► Node(Key="A", Val=10) ──► Node(Key="E", Val=30)
[ Bucket 1 ] ──► null (Empty)
[ Bucket 2 ] ──► Node(Key="B", Val=20)
[ Bucket 3 ] ──► Node(Key="C", Val=40)
  1. Lock-Free Reads (get()): The node values and next pointers are marked volatile. When calling get(), the thread reads directly from CPU caches/memory without acquiring any lock. Readers never block writers, and writers never block readers!
  2. Lock-Free Write to Empty Bucket: When putting an item into an empty bucket (like Bucket 1), it uses a single atomic CAS instruction to place the head node. No lock is acquired.
  3. Fine-Grained Locking for Collisions: If a bucket already has data and there is a hash collision, it uses synchronized(headNode) to lock only that single bucket head. All other buckets (Buckets 1, 2, 3) remain 100% open for parallel reads and writes.
