01 — READ THIS FIRST

Every collection is just a memory management trick

Before we open ArrayList or HashMap, let's look at what "memory" means inside a running Java program. Once you see this clearly, every collection becomes easy — because a collection is nothing but a smart way of storing and finding data in memory.

Two areas of memory: Stack and Heap

When your Java program runs, the JVM (Java Virtual Machine) gives it two main areas of memory to work with.

Stack — small, fast, temporary

Each thread gets its own stack. Every time you call a method, a new "frame" is placed on top of the stack. That frame holds the method's local variables and primitives (int, boolean, char...). When the method finishes, its frame is thrown away instantly. The stack is very fast, but very small.

Heap — big, shared, long-lived

Every object you create with new — including every ArrayList, HashMap, and every element inside them — lives on the heap. The heap is shared by all threads in the program. It is much bigger than the stack, but also slower to work with, because objects can be scattered anywhere in it.

🗒️
Simple picture: sticky notes vs a warehouse
Think of the stack as sticky notes on your own desk — quick to write, quick to throw away, and only you can see them. The heap is a big shared warehouse where the actual boxes (objects) are stored. Your sticky note doesn't hold the box itself — it just holds the address of the shelf where the box sits in the warehouse. That address is what Java calls a reference. 
int age = 25;                    // "25" is stored directly on the stack (a primitive)
List<String> names = new ArrayList<>();  // "names" on the stack holds an ADDRESS
                                     // the real ArrayList object lives on the heap

This is exactly why collections only store objects, never raw primitives. A collection like List<Integer> cannot hold a plain int — Java has to wrap it inside an Integer object first (this automatic wrapping is called autoboxing). That's an extra object on the heap, with extra memory overhead, for every single number you put into a collection. Knowing this now will make the "memory overhead per element" numbers later in this guide make a lot more sense.

What happens to old data: Garbage Collection

In many languages, you must manually free memory when you're done with an object, or your program slowly runs out of memory (a "memory leak"). Java does this for you automatically with a background process called the Garbage Collector (GC).

The rule is simple: if nothing on the stack (and nothing reachable from it) still points to an object on the heap, that object is garbage. The GC finds these unreachable objects and reclaims their memory.

Why this matters for collections
This is the real reason LinkedList feels "heavier" than ArrayList: every node it creates is a separate heap object that the GC must later track and clean up. This is also why CopyOnWriteArrayList can cause GC pressure on every write — it throws away and recreates a whole array each time. When this guide later says a design choice "creates GC pressure," it simply means: this approach makes a lot of short-lived heap objects, and the garbage collector has to work harder to clean them all up, which can pause your program for a moment.

Putting it together: what a collection actually does

With stack, heap, references, and garbage collection in mind, here is the one-sentence idea behind this entire guide:

The core idea
A Java collection is just an object on the heap that organizes a group of references (addresses) to other objects, using some clever layout — a straight row (array), a chain of pointers (linked list), or a mathematical shortcut (hashing) — so that adding, finding, and removing items is as fast as possible for the way you plan to use them.
💡 Quick Knowledge Check
Why does creating List<Integer> list = new ArrayList<>() generate significantly more GC pressure than int[] arr = new int[1000]?
Answer: An int[] stores raw 32-bit values packed tightly together on the heap as a single contiguous object. In contrast, List<Integer> stores references to 1,000 separate Integer objects on the heap (autoboxing). Each Integer object incurs 16-24 bytes of object header overhead, creating 1,001 heap objects that the Garbage Collector must later scan and clean up!

What a "collection" even is

Before HashMap or ConcurrentHashMap mean anything, you need three ideas: what memory looks like, what Big-O is actually measuring, and why Java splits "collections" from "maps."

Memory, in one picture

Your computer's memory (RAM) is one enormous numbered street of boxes. Every box holds one small piece of data, and every box has an address — a house number. A variable in your program is just a label taped to one of these boxes.

🏘️
Analogy: memory is a street of numbered mailboxes
If a data structure keeps its items in consecutive mailboxes (house #100, #101, #102…), the postman can predict exactly where the next one is without asking. If it scatters items across random houses across town and each house has a note saying "next item lives at house #4471," the postman must walk to each house, read the note, and only then learn where to go next. The first approach is an array. The second is a linked list. This one distinction explains almost every performance difference in this whole guide.

Big-O, in plain terms

Big-O answers one question: as the collection grows, how does the work grow? It deliberately ignores constants and hardware speed — it's about shape, not seconds.

O(1) — constant

Same effort no matter how big the collection gets. Reading array index arr[500] costs the same whether the array has 501 or 5,000,001 elements.

O(log n) — logarithmic

Effort grows, but very slowly — each step eliminates half the remaining work. A balanced tree with a billion items needs about 30 steps to find anything.

O(n) — linear

Effort grows exactly as fast as the data. Double the elements, double the work. Scanning a list looking for a value is O(n).

Why Collection and Map are cousins, not siblings

Java's collections split into two families that look similar but solve different problems:

🎒
A Collection is a bag. A Map is a phonebook.
A Collection (List, Set, Queue) just holds items — you throw one thing in with add(item). A Map stores pairs — a name and a phone number — so adding requires two things: put(key, value). Because "add one thing" and "add two linked things" are fundamentally different actions, Java never forces Map to pretend it's a Collection. Instead, a Map exposes views — keySet() (just the names), values() (just the numbers), entrySet() (the pairs) — each of which is a real Collection you can loop over.

JDK Class vs Interface Distinction
«interface» Cyan / Sky Blue · Interface

Abstract Contract: Defines public API method contracts (e.g., add(), get(), size()) without physical heap memory layout. Cannot be instantiated with new. Used as reference types for polymorphic code.

«class» Green / Emerald · Concrete Class

Heap Implementation: Concrete data structure with actual memory allocation on the heap (continuous array, linked nodes, hash buckets). Instantiated with new (e.g., new ArrayList<>()).

legacy Coral Red · Legacy (Synchronized)

Pre-Java 2 Legacy: Thread-safe via coarse method-level locks (Vector, Stack, Hashtable). Retained for 100% backwards compatibility; superseded by modern collections and concurrent structures.

Sequenced Violet · Java 21+ Sequenced

Ordered Sequence Contract: Java 21 unified interface (SequencedCollection, SequencedSet, SequencedMap) providing standard addFirst(), addLast(), and reversed() view access.
