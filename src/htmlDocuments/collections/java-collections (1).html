01 — READ THIS FIRST

Every collection is just a memory management trick

Before we open ArrayList or HashMap, let's look at what "memory" means inside a running Java program. Once you see this clearly, every collection becomes easy — because a collection is nothing but a smart way of storing and finding data in memory.

Two areas of memory: Stack and Heap

When your Java program runs, the JVM (Java Virtual Machine) gives it two main areas of memory to work with.

Stack — small, fast, temporary

Each thread gets its own stack. Every time you call a method, a new "frame" is placed on top of the stack. That frame holds the method's local variables and primitives (int, boolean, char...). When the method finishes, its frame is thrown away instantly. The stack is very fast, but very small.

Heap — big, shared, long-lived

Every object you create with new — including every ArrayList, HashMap, and every element inside them — lives on the heap. The heap is shared by all threads in the program. It is much bigger than the stack, but also slower to work with, because objects can be scattered anywhere in it.

🗒️
Simple picture: sticky notes vs a warehouse
Think of the stack as sticky notes on your own desk — quick to write, quick to throw away, and only you can see them. The heap is a big shared warehouse where the actual boxes (objects) are stored. Your sticky note doesn't hold the box itself — it just holds the address of the shelf where the box sits in the warehouse. That address is what Java calls a reference. 
int age = 25;                    // "25" is stored directly on the stack (a primitive)
List<String> names = new ArrayList<>();  // "names" on the stack holds an ADDRESS
                                     // the real ArrayList object lives on the heap

This is exactly why collections only store objects, never raw primitives. A collection like List<Integer> cannot hold a plain int — Java has to wrap it inside an Integer object first (this automatic wrapping is called autoboxing). That's an extra object on the heap, with extra memory overhead, for every single number you put into a collection. Knowing this now will make the "memory overhead per element" numbers later in this guide make a lot more sense.

What happens to old data: Garbage Collection

In many languages, you must manually free memory when you're done with an object, or your program slowly runs out of memory (a "memory leak"). Java does this for you automatically with a background process called the Garbage Collector (GC).

The rule is simple: if nothing on the stack (and nothing reachable from it) still points to an object on the heap, that object is garbage. The GC finds these unreachable objects and reclaims their memory.

Why this matters for collections
This is the real reason LinkedList feels "heavier" than ArrayList: every node it creates is a separate heap object that the GC must later track and clean up. This is also why CopyOnWriteArrayList can cause GC pressure on every write — it throws away and recreates a whole array each time. When this guide later says a design choice "creates GC pressure," it simply means: this approach makes a lot of short-lived heap objects, and the garbage collector has to work harder to clean them all up, which can pause your program for a moment.

Putting it together: what a collection actually does

With stack, heap, references, and garbage collection in mind, here is the one-sentence idea behind this entire guide:

The core idea
A Java collection is just an object on the heap that organizes a group of references (addresses) to other objects, using some clever layout — a straight row (array), a chain of pointers (linked list), or a mathematical shortcut (hashing) — so that adding, finding, and removing items is as fast as possible for the way you plan to use them.
02 — START HERE

What a "collection" even is

Before HashMap or ConcurrentHashMap mean anything, you need three ideas: what memory looks like, what Big-O is actually measuring, and why Java splits "collections" from "maps."

Memory, in one picture

Your computer's memory (RAM) is one enormous numbered street of boxes. Every box holds one small piece of data, and every box has an address — a house number. A variable in your program is just a label taped to one of these boxes.

🏘️
Analogy: memory is a street of numbered mailboxes
If a data structure keeps its items in consecutive mailboxes (house #100, #101, #102…), the postman can predict exactly where the next one is without asking. If it scatters items across random houses across town and each house has a note saying "next item lives at house #4471," the postman must walk to each house, read the note, and only then learn where to go next. The first approach is an array. The second is a linked list. This one distinction explains almost every performance difference in this whole guide.

Big-O, in plain terms

Big-O answers one question: as the collection grows, how does the work grow? It deliberately ignores constants and hardware speed — it's about shape, not seconds.

O(1) — constant

Same effort no matter how big the collection gets. Reading array index arr[500] costs the same whether the array has 501 or 5,000,001 elements.

O(log n) — logarithmic

Effort grows, but very slowly — each step eliminates half the remaining work. A balanced tree with a billion items needs about 30 steps to find anything.

O(n) — linear

Effort grows exactly as fast as the data. Double the elements, double the work. Scanning a list looking for a value is O(n).

03 — SEQUENTIAL DATA

ArrayList vs. LinkedList

Same interface (List<E>), completely different physical strategy. This is the mailbox-street analogy made concrete — click through the buttons below and watch what each structure actually has to do.

ArrayList: one long, contiguous shelf

An ArrayList is a wrapper around a plain Java array (Object[] elementData). Every element lives in a numbered slot right next to its neighbors. Reading slot 500 is a single calculation — base address + (500 × slot size) — no walking required. That's why get(i) is O(1).

But arrays have a fixed size at creation. When the shelf fills up, ArrayList can't magically extend it in place — memory right after the array might belong to something else. So it:

  1. Allocates a brand-new array 1.5× the size (newCapacity = oldCapacity + (oldCapacity >> 1))
  2. Copies every existing element into it via System.arraycopy() — a highly optimized native memory copy
  3. Discards the old array

This resize is expensive, but it happens rarely and the cost is amortized — spread thin — across many cheap appends, so appending is still called O(1) "on average."

Watch: appending to the end is cheap. Inserting at the front forces every element to shift right by one slot — an O(n) memory shuffle.

LinkedList: a scattered chain of notes

A LinkedList holds no array at all. Each element is wrapped in its own little object (a "node") allocated somewhere in the heap — possibly nowhere near the previous node. Each node stores three things: the actual value, a pointer to the next node, and a pointer to the previous node (it's doubly linked).

Three nodes of the same list, scattered across three unrelated heap addresses. Getting from "Anna" to "Chen" means following two pointers — there is no shortcut.

This scattering is exactly why get(500) on a LinkedList is O(n): there's no formula for "where is element 500," so Java must start at one end and follow next 500 times. But once you're already standing at a node (say, via an iterator), inserting or removing right there is O(1) — you just rewire two pointers, no shifting required.

Why this matters more than it sounds
Modern CPUs read memory in 64-byte chunks called cache lines and speculatively prefetch the next chunk when they see a pattern of sequential access. ArrayList's contiguous layout plays perfectly into this — iterating it is extremely fast in practice, not just in theory. LinkedList's scattered nodes defeat this prefetching almost entirely, causing a real CPU stall (a "cache miss") at nearly every step. This is why, despite matching Big-O in places, ArrayList outperforms LinkedList for iteration by a wide margin in practice — and why LinkedList is rarely the right default choice today (use ArrayDeque instead for queue/stack behavior).

Vector and Stack: the old-timers you'll still see in interviews

Vector is basically an ArrayList that was written back in Java 1.0, before the modern Collections Framework even existed. It stores data exactly the same way — a growing array — but every single method (add, get, size...) is marked synchronized. That means only one thread can touch it at a time, even if you're running single-threaded code and don't need that protection at all.

Stack is even older — it's a subclass of Vector, adding push(), pop(), and peek() on top. So a Stack carries all of Vector's baggage: locking on every call, plus it inherits list methods like add(index, x) that can secretly break the "stack" discipline by letting you insert in the middle.

Why they're considered legacy today
Locking on every single call is expensive, and almost nobody actually needs a growable array that is thread-safe by default — most code is either single-threaded (use ArrayList) or needs a properly designed concurrent structure (use ConcurrentHashMap-style tools or CopyOnWriteArrayList). For stack behavior specifically, the JDK documentation itself recommends ArrayDeque over Stack — same push/pop/peek idea, no unnecessary locking, no leftover List methods that don't belong on a stack.

04 — THE MOST-ASKED INTERVIEW TOPIC

HashMap: how a key finds its shelf

HashMap's entire job is answering one question fast: "given this key, which of my internal buckets should I look in?" Everything below is in service of that one question.

Step 1 — turn the key into a number

Every Java object has a hashCode() method that reduces it to a single 32-bit integer. Think of it as a meaningless-looking fingerprint — two equal objects must produce the same fingerprint, but the fingerprint itself carries no readable meaning.

📇
Analogy: hashCode is a librarian's shelving code, not the book's title
A librarian doesn't file 10,000 books alphabetically by full title (slow to search). She converts each title into a short shelving code and stores books by that code. HashMap does the same: it never compares your key against every stored key. It uses the key's fingerprint to jump straight to the one shelf (bucket) it must be on.

Step 2 — spread the fingerprint's bits

A raw hashCode() can be a bad fit for a small bucket array — many hash codes differ only in their high bits, which get thrown away by the next step. So HashMap runs a cheap "spreading" step first:

static final int hash(Object key) {
    int h = key.hashCode();
    // shift the top 16 bits down, XOR them into the bottom 16
    return h ^ (h >>> 16);
}

This mixes high-order bits into the low-order bits, so differences that only show up "way up high" in the number still influence which bucket gets picked.

Step 3 — mask it down to a bucket index

HashMap's internal array (Node<K,V>[] table) always has a size that's a power of two (16, 32, 64…). This is deliberate: for a power-of-two size n, hash % n gives exactly the same answer as hash & (n - 1) — a bitwise AND — but AND is a single, near-free CPU instruction, while % (division) is dozens of times slower.

Table capacity fixed at 16 for this demo, so the mask is & 15 (binary 1111) — it simply keeps the lowest 4 bits of the spread hash.

Collisions: two keys, one bucket

Different keys can land on the same bucket index — that's a collision, and it's expected, not a bug. HashMap handles it with separate chaining: the bucket holds a linked list of every entry that landed there, and a lookup walks that short list comparing keys with equals().

16 buckets. Insert a few keys and watch collisions form chains.

When a chain gets long: treeification

A linked-list bucket is fine at 1–3 entries — a short walk. But imagine an attacker deliberately crafts thousands of keys that all hash to the same bucket (a "hash-flooding" attack): that bucket's list balloons, and every lookup degrades toward O(n). Since Java 8, HashMap defends against this:

The 8/6 rule
If a single bucket's chain reaches 8 entries and the table has at least 64 buckets total, that one bucket converts from a linked list into a small Red-Black tree (self-balancing binary search tree). Worst-case lookup in that bucket drops from O(n) to O(log n). If the bucket later shrinks to 6 or fewer entries, it converts back to a plain list. The 8-vs-6 gap (not both set to 7) is deliberate — it stops a bucket from flapping back and forth between tree and list every time one key is added or removed near the threshold.

Below 64 total buckets, HashMap prefers to just grow the whole table instead of building a tree — a bigger table usually spreads the same 8 entries across separate buckets anyway, so building a tree would be wasted work.

If two keys land in the same tree bucket and don't implement Comparable (or compare equal), Java can't decide tree order from the key's value alone — so it breaks the tie using System.identityHashCode(), essentially "which object was created first in memory," just to guarantee the tree stays consistently ordered.

Resizing: doubling without starting over

HashMap resizes (doubles its table) once occupancy passes capacity × load factor — by default 0.75, so a 16-bucket table resizes after its 13th entry. A smaller load factor wastes memory on empty buckets; a larger one causes more collisions. 0.75 is Java's measured sweet spot.

Here's the elegant part: because capacity always doubles (16→32→64…), the bitmask only ever grows by one bit at a time. That means every existing entry has only two possible destinations in the new table: its same index, or its same index + old capacity — depending on whether that one new bit happens to be 0 or 1 in its hash. HashMap never has to recompute a full hash during resize; it just checks one bit and splits each chain into a "stays low" list and a "moves high" list.

Interview trap
Always construct a HashMap (or ConcurrentHashMap) with an expected size up front — new HashMap<>(expectedSize) — when you know roughly how many entries are coming. Skipping this means the table silently resizes (and fully re-buckets) log₂(finalSize/16) times during a big bulk load, each one a stop-and-copy pause.
05 — YOU ALREADY KNOW THESE, YOU JUST DON'T KNOW IT YET

HashSet, LinkedHashSet, TreeSet, LinkedHashMap, TreeMap

Good news first: none of these five classes are a new data structure. Every single one is either a HashMap wearing a costume, or the same Red-Black tree you just met a moment ago. Once you see the trick, you can never un-see it.

HashSet: a HashMap wearing a costume

Open the real Java source code for HashSet and this is almost the entire class:

public class HashSet<E> {
    // a HashSet does not have its own buckets — it hides a HashMap inside itself
    private HashMap<E, Object> map;

    // one single dummy object, shared by every element, in every HashSet, in the whole program
    private static final Object PRESENT = new Object();

    public boolean add(E e) {
        return map.put(e, PRESENT) == null;   // your element becomes the KEY
    }
    public boolean contains(Object o) {
        return map.containsKey(o);
    }
}

Read that slowly, in plain words: add(x) really just means map.put(x, PRESENT), and contains(x) really just means map.containsKey(x). There is no separate hashing logic, no separate bucket array, no separate collision handling written anywhere for HashSet — because it doesn't need any. It borrows all of it from HashMap.

🎭
Simple picture: a coat rack with one spare coat
Imagine a coat rack (the HashMap) with a labeled hook for every item. A HashSet doesn't build its own coat rack — it uses the same one, and it hangs the exact same spare coat (the shared PRESENT object) on every hook, no matter what the hook's label is. The label is the only thing anyone actually cares about — that's your element.

This one fact means every rule you already learned in the HashMap section above is automatically true for HashSet too: hashCode() turns your object into a number, that number gets its bits spread and masked down to a bucket index, two elements landing in the same bucket form a chain, and a chain that grows past 8 entries (in a table of 64+ buckets) quietly turns into the same Red-Black tree. You did not learn a second data structure just now — you learned that HashSet is HashMap, minus the values.

On memory, specifically
A HashSet object on the heap doesn't hold a bucket array of its own — it holds one reference to a hidden HashMap object, which is the thing that actually holds the bucket array. So creating a HashSet costs one small extra object compared to creating a HashMap directly. The PRESENT placeholder costs almost nothing, because Java creates it exactly once, ever, and every HashSet in your entire program reuses that same single object — it is never duplicated per element.

LinkedHashSet and LinkedHashMap: one hidden chain, threaded through the buckets

A plain HashMap makes you no promises at all about the order you'll see when you loop over it — the order just falls out of which bucket each key happened to land in, and that looks completely random to a human. LinkedHashMap fixes exactly that one problem, with one small addition.

Every entry in a LinkedHashMap carries two extra fields that a normal HashMap entry does not have: before and after — references pointing to the entry that was inserted right before it, and the entry inserted right after it. Line all of those up, and you get a second, invisible linked list running through the entries, completely separate from the bucket array underneath. When you iterate, Java ignores the buckets entirely and just walks this hidden chain from the oldest entry to the newest — which is exactly why the order you see matches the order you inserted things in.

🧵
Simple picture: numbered raffle tickets on a shelf of unlabeled boxes
The boxes (buckets) are still scattered around in whatever order hashing puts them in — nothing changes there. But now imagine a piece of thread tied from the first box you filled, to the second, to the third, and so on. To read things back "in the order I added them," you don't look at the shelf at all — you just follow the thread.
This costs real memory — which is the whole point of this guide
Two extra references per entry sounds small, but it is not free: on most 64-bit JVMs that's around 16 extra bytes per entry, and two more fields the garbage collector must trace every time it scans that object. This is a direct, measurable trade: you are spending heap memory to buy yourself a predictable iteration order. LinkedHashSet is to LinkedHashMap exactly what HashSet is to HashMap — a thin wrapper hiding a private LinkedHashMap<E,Object> field inside, reusing the exact same PRESENT trick.

Building an LRU Cache: The Magic of accessOrder = true

📚
Simple picture: A 3-book shelf (The LRU eviction rule)
Imagine a small bookshelf that only holds 3 books. You want to keep your favorite, most popular books on this shelf. When the shelf is full and you buy a new book, which one do you throw away?

The smartest choice is usually: throw away the book you haven't touched for the longest time.

In computer science, this strategy is called an LRU Cache (Least Recently Used cache).

Part 1: How accessOrder = true Works

A standard map in Java just remembers data (key and value pairs). A LinkedHashMap is special because it also ties all the items together with an invisible chain in a specific line.

  • Normal behavior (accessOrder = false): The line is organized strictly by when items were first put into the map (insertion order).
  • Special behavior (accessOrder = true): The line updates every time you touch an item (both reads and writes).

In Java, you turn this into a functioning LRU cache by overriding removeEldestEntry():

// Textbook JDK LRU Cache (Max capacity: 3)
Map<String, String> lruCache = new LinkedHashMap<>(16, 0.75f, true /* accessOrder = true */) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, String> eldest) {
        return size() > 3; // Evict the head entry once size exceeds 3
    }
};
Part 2: The Hidden Catch (Why it fails under heavy traffic)

Most of the time in programming, reading data is completely safe to do with multiple people at once. Ten people can look at the same webpage or read the same book at the exact same second without bumping into each other.

Writing (changing) data is different. If two people try to rewrite the same page at the same time, it causes chaos. So programmers put a lock on the book: only one person can write at a time while everyone else waits.

Here is the critical problem with accessOrder = true:

  • Because of that flag, a read is secretly a write.
  • When you call get(), Java isn't just looking at the value. It is actively unhooking pointers (before and after) and rearranging the doubly linked chain behind the scenes.
  • If two computer threads try to rearrange the chain at the exact same millisecond, the chain breaks, cyclic references are formed, and the program crashes or loops infinitely.
  • The consequence: You must force every reader to wait in a single line using a lock (such as Collections.synchronizedMap). If thousands of users are reading data at the same second, everything slows to a crawl because nobody can read at the same time.

In high-speed, multi-user systems, engineers avoid this flag and use specialized concurrent caches (like Caffeine or custom striped rings) that don't need to rebuild internal chains on every simple read. (See Section 14 · Modern Caching for how W-TinyLFU and asynchronous ring buffers solve this without read locks).

TreeSet and TreeMap: the same Red-Black tree, used from the very first entry

You already met the Red-Black tree a moment ago — it's the shape a HashMap bucket turns itself into once its chain grows past 8 entries. TreeMap and TreeSet don't wait for that to happen. They use a Red-Black tree as their entire storage, starting from the very first entry you insert.

Here's the plain-English version of "self-balancing," since that word gets thrown around a lot without being explained: a normal binary search tree can accidentally turn into a straight line. If you insert 1, 2, 3, 4, 5 in that exact order into a plain BST, each new number is bigger than the last, so each one becomes the right child of the one before it — you end up with something that behaves exactly like a LinkedList, and looking something up costs O(n), a full walk. A Red-Black tree refuses to let this happen. Every time a node is inserted, the tree checks a small set of coloring rules (every node is marked red or black, and a few simple rules about which colors can sit next to each other must always hold), and if inserting the new node broke a rule, it performs a rotation — a quick local swap of a few pointers — to restore balance immediately.

The one guarantee that matters
A Red-Black tree guarantees the longest path from root to leaf is never more than roughly twice the length of the shortest path. That single guarantee is what keeps put(), get(), and remove() at O(log n) even in the worst case — unlike HashMap's O(1), which is only true on average and can degrade if hashing goes badly.

TreeSet follows the same pattern as HashSet and LinkedHashSet: it's a thin wrapper hiding a private TreeMap<E,Object> field, reusing the same one-shared-dummy-value trick. What you get in exchange for O(log n) instead of O(1) average is real ordering power a HashMap can never offer: first() / last() (smallest / largest), ceiling(x) / floor(x) (smallest ≥x / largest ≤x), higher(x) / lower(x) (strictly greater / strictly less), and whole range views like headMap(), tailMap(), and subMap(). None of this is possible on a HashMap — a HashMap doesn't track order, so it has no concept of "what comes just after this key."

06 — ORDERED EXTRACTION

Queue, Deque, and the binary heap

A List cares about position. A Queue cares about order of extraction — who gets served next.

ArrayDeque: the modern default

ArrayDeque ("double-ended queue") is a circular array with a head and tail index. It supports adding/removing from either end in O(1) without ever allocating a node object — so it plays FIFO queue, LIFO stack, and deque all at once, and generally beats both LinkedList and the ancient Stack class for these roles.

🔄
Analogy: a circular parking lot
Picture a row of parking spaces bent into a circle. Cars enter at one marker (tail) and leave from another (head). When the lot fills, instead of building a longer street, the whole ring just doubles in size. When the head pointer would run off the end of the array, it silently wraps back to index 0 — that's the bitwise trick head = (head - 1) & (capacity - 1), the same power-of-two masking trick HashMap uses.

PriorityQueue: a binary heap, not a sorted list

A common misconception: PriorityQueue does not keep its elements fully sorted. It keeps one guarantee only — the smallest element is always at the front — using a shape called a binary min-heap, stored compactly inside a plain array.

The trick is a pure-arithmetic tree: for any array index i, its parent lives at (i-1)/2, and its children live at 2i+1 and 2i+2. No pointers at all — the shape is implied entirely by position.

insert bubbles the new value up while it's smaller than its parent (siftUp). poll() moves the last element to the root, then sinks it down past its smaller child (siftDown). Both run in O(log n).
07 — JAVA 21

Sequenced Collections: one missing interface, finally added

A real gap existed for years: every ordered collection had a "first" and "last" element, but there was no common way to say so.
The problem, before Java 21
Getting the last element required a different idiom per type: list.get(list.size()-1) for a List, deque.getLast() for a Deque, sortedSet.last() for a SortedSet — and for a LinkedHashSet, there was no shortcut at all; you had to iterate the entire set just to reach the end.

JEP 431 introduced SequencedCollection<E>, sitting between Collection<E> and both List<E> and Deque<E>. It standardizes six methods every ordered collection can now share:

interface SequencedCollection<E> extends Collection<E> {
    void addFirst(E e);
    void addLast(E e);
    E getFirst();
    E getLast();
    E removeFirst();
    E removeLast();
    SequencedCollection<E> reversed();  // O(1) view, no copying
}

reversed() is the elegant part: it doesn't build a new reversed copy. It returns a thin view object that reads the same backing data back-to-front — so it's O(1) in time and memory, no matter the collection's size.

SequencedSet<E>

Extends both Set and SequencedCollection. LinkedHashSet now supports addFirst/addLast in O(1). SortedSet also implements this interface, but throws UnsupportedOperationException on addFirst — its order is dictated by a Comparator, not insertion, so "add at the front" is a contradiction it correctly refuses.

SequencedMap<K,V>

Adds firstEntry(), lastEntry(), pollFirstEntry(), pollLastEntry(), plus sequenced views sequencedKeySet() and sequencedEntrySet(). Implemented by LinkedHashMap and TreeMap.

08 — BEFORE ANY "CONCURRENT" CLASS MAKES SENSE

What actually goes wrong when two threads share data

Everything from here on — ConcurrentHashMap, CopyOnWriteArrayList, blocking queues — exists to solve one problem. Let's see the problem first.

A thread is an independent sequence of instructions your program runs. Modern CPUs have multiple cores, so multiple threads can genuinely execute at the same instant — not just take turns quickly. That's the whole point of concurrency: real parallel speed. It's also where the trouble starts.

🏧
Analogy: two people, one bank balance, no communication
A shared bank balance reads $100. You and your partner both check the balance at the same instant, both see $100, and both decide to withdraw $80. Each of you independently computes "100 − 80 = 20" and writes 20 back. The bank ends up at $20 — even though $160 was withdrawn from an account that only had $100. Nobody did anything individually wrong; the problem is that read, decide, and write weren't a single uninterruptible step. This is exactly what an unsynchronized counter++ does across two threads.

This is called a race condition: the final result depends on the unpredictable timing of two threads, rather than on the logic of the program. Java gives you two fundamentally different tools to prevent it:

🔒 Locking — make threads take turns

A synchronized block or ReentrantLock lets only one thread execute the protected code at a time. Every other thread trying to enter is parked — put to sleep by the OS — until the lock is free. Simple to reason about, but threads waiting on a lock do zero useful work, and heavy contention means most threads spend their time asleep.

⚡ CAS — bet, then check

Compare-And-Swap is a single CPU instruction: "if this memory location still holds the value I expect, replace it with my new value — atomically, as one indivisible step. Tell me if it worked." No thread ever sleeps. If the swap fails because someone else got there first, the thread just re-reads the current value and tries again. This is called lock-free programming.

CAS is what lets a data structure be thread-safe without ever putting a thread to sleep for the common case — which is exactly the trick ConcurrentHashMap, LongAdder, and ConcurrentSkipListMap all lean on.

09 — THE STANDARD THREAD-SAFE MAP

ConcurrentHashMap: CAS where it can, a tiny lock where it must

The most important upgrade in ConcurrentHashMap's history: Java 7 locked in coarse 16-way stripes. Java 8 rebuilt it to lock almost nothing.

The old way (Java 7): segment striping

Java 7's ConcurrentHashMap pre-split the table into 16 independent Segments, each guarded by its own lock. Up to 16 threads could write simultaneously — one per segment — but any operation needing a global view (like computing overall size, or resizing) had to lock across all segments at once.

The current design (Java 8+): per-bucket, not per-segment

Java 8 threw out segments entirely. The table now looks just like HashMap's — a flat array of buckets — but every operation on a bucket is protected individually and as cheaply as possible:

helps finish the resize instead of waiting

The insight: locking one bucket's head node blocks nothing else in the table. Two threads writing to two different buckets run fully in parallel — even though both technically "hold a lock" at that moment.

Cooperative resizing: nobody blocks, everybody helps

A single-threaded HashMap resize just stops and copies everything. A concurrent map can't get away with "stop the world" — other threads must be able to keep working. ConcurrentHashMap solves this with two shared counters:

  • sizeCtl — when negative, encodes that a resize is in progress, packing a generation stamp and a count of active migrating threads into one int
  • transferIndex — the next unclaimed stretch of buckets still needing migration

Any thread that stumbles onto a ForwardingNode (a marker left on an already-migrated bucket) doesn't wait around — it calls helpTransfer() and claims its own stride of buckets to migrate via a CAS decrement on transferIndex. Whichever threads happen to be around during a resize simply pitch in; the resize finishes faster the busier the map is.

Why null is banned
map.get(key) returning null is ambiguous in a single thread: is the key mapped to null, or just absent? You'd normally resolve this with a follow-up containsKey(key) call. In a concurrent map, another thread can insert or remove that exact key between your two calls — so the two-step check is no longer atomic and can lie to you. Doug Lea's fix was simpler than any locking scheme: ConcurrentHashMap just refuses to store null at all, and throws NullPointerException immediately if you try.

Counting size without a global lock: LongAdder

If every thread updated one shared counter with CAS, all of them would repeatedly collide on the exact same memory address — the CPU cache line backing that counter gets invalidated on every single update (more on this in the mechanical sympathy section). LongAdder instead keeps a base counter plus an array of independent striped counters. Under contention, each thread hashes to its own stripe and updates that instead — collisions become rare — and sum() just adds every stripe together when a total is actually needed.

10 — READ-HEAVY, WRITE-RARE

CopyOnWriteArrayList: reads that never even see a lock

An entirely different bet: what if writes were expensive, so reads could be completely free?

CopyOnWriteArrayList stores its data in a volatile Object[] array. Reads just read that reference directly — no lock, no CAS retry loop, nothing. They're as fast as reading a plain array, and they can never throw ConcurrentModificationException, because they never even look at whether the array has changed.

The cost is paid entirely by writers. Every single mutation — even adding one element — does this under a ReentrantLock:

public boolean add(E e) {
    lock.lock();
    try {
        Object[] newElements = Arrays.copyOf(getArray(), len + 1);
        newElements[len] = e;
        setArray(newElements);  // swap the volatile reference — readers now see it
    } finally { lock.unlock(); }
}
📋
Analogy: a clipboard that gets fully re-photocopied on every edit
Anyone can glance at the clipboard on the wall at any moment without asking permission — they just see whatever page is currently pinned up. But to make an edit, you have to photocopy the entire page, mark it up, and pin the new copy over the old one. If the clipboard has 50,000 lines, every single edit means recopying all 50,000 lines. Fine if edits are rare. Ruinous if edits happen constantly.

An iterator created over a CopyOnWriteArrayList captures the array reference at that instant — a snapshot. It will never reflect later writes, and it doesn't support remove()/set()/add() through the iterator at all. This makes it a strong fit for things like listener/observer lists — read constantly, modified almost never — and a poor fit for anything write-heavy.

11 — PRODUCER / CONSUMER PIPELINES

Blocking queues: when threads should actually wait

Sometimes waiting is correct — a consumer thread with nothing to do genuinely should sleep rather than spin. These queues make that safe and efficient.

ArrayBlockingQueue

Fixed-size array, bounded capacity fixed at creation. One single ReentrantLock guards both put() and take(), with two condition variables (notEmpty, notFull) used to park and wake threads efficiently. Because producers and consumers share the one lock, they can contend with each other under bursty load — but memory use is minimal and fully predictable.

LinkedBlockingQueue

Unbounded by default, built from linked nodes. Uses two separate locks — putLock and takeLock — so producers and consumers stop contending with each other entirely. The trade-off: every insertion allocates a new node, adding garbage-collection pressure that the array-backed queue avoids.

SynchronousQueue: a queue with zero capacity

This one holds nothing at all. Every put() must rendezvous directly with a waiting take() — it's a pure hand-off between two threads, not storage. Internally it's a lock-free "dual" structure (a dual-stack for LIFO mode, a dual-queue for FIFO mode) where nodes represent either "I have data waiting" or "I want data." This is the queue behind Executors.newCachedThreadPool(), where a new task should hand directly to an idle worker thread.

LinkedTransferQueue: the "give me everything" queue

Combines ideas from all of the above into one unbounded, lock-free queue. Its signature addition is transfer(e): it blocks until some consumer actually takes the element, guaranteeing direct hand-off semantics even though the queue is otherwise unbounded and non-blocking for normal put()/take() use.

12 — CONCURRENT + SORTED, WITHOUT A TREE

ConcurrentSkipListMap: an express-lane linked list

Balanced trees (Red-Black, AVL) rebalance by rotating nodes across multiple levels — brutal to do safely without locking large parts of the tree. Skip lists sidestep the whole problem.

A skip list is just several linked lists stacked on top of each other. Level 0 holds every element in sorted order — nothing fancy. Each level above it holds a randomly-chosen, thinner subset of the level below, like an express train that only stops at some of the same stations as the local train.

Whether a new node gets promoted to a higher level is decided by a random coin flip at insertion time (typically 50/50 per level) — no rebalancing operation is ever needed, because the structure's shape is probabilistic by construction rather than something that must be actively maintained.

Deleting without locking: the tombstone protocol

Removing a node safely while other threads are mid-traversal, without a lock, takes three CAS-driven steps:

  1. Logical deletion — CAS the node's value to null. It's now "dead" but still physically linked in.
  2. Marker insertion — CAS in a special tombstone node right after it, so any thread walking past knows this node is being removed.
  3. Physical unlinking — the next thread that happens to walk past (any thread — not necessarily the deleter) finishes the job, rewiring the previous node's pointer to skip over both the dead node and its tombstone.

That last step is the elegant part: cleanup work is shared opportunistically across whichever threads happen to pass by, instead of being one thread's exclusive responsibility.

ConcurrentSkipListMap is the map to reach for when you need both sorted order and thread safety — ConcurrentHashMap gives you thread safety but no ordering at all.

13 — WHY HARDWARE SHAPES THE "RIGHT" ANSWER

Cache lines, false sharing, and compressed pointers

Two structures with identical Big-O can perform completely differently — because Big-O doesn't know your CPU has caches.

Cache lines

CPUs never fetch a single byte from memory. They fetch in fixed 64-byte blocks called cache lines, on the assumption that if you touched one byte, you'll probably touch its neighbors soon (this is why ArrayList's contiguous layout wins — one cache-line fetch grabs several elements at once).

False sharing: contention on memory nobody's actually fighting over

🍕
Analogy: two people sharing one pizza box, eating different slices
Two threads increment two completely unrelated counters — Variable A and Variable B — that just happen to have been placed next to each other in memory, inside the same 64-byte cache line (the "pizza box"). Under the CPU's cache-coherence protocol (MESI), when Core 1 writes to Variable A, the entire cache line is invalidated in Core 2's cache — even though Core 2 was only ever touching Variable B. Core 2 now has to reload the whole line from a slower shared cache, purely because of where A happened to sit in memory. Nobody is actually contending for the same data — just the same delivery box.

The JDK's fix is the @Contended annotation, which pads a field with extra bytes so it lands on its own private cache line, immune to a neighbor's writes. ConcurrentHashMap.CounterCell and Striped64 (which backs LongAdder) both use it — it's precisely why striped counters actually deliver the scalability they promise.

Compressed OOPs: the 32 GB cliff

On a 64-bit JVM, a plain object reference is normally 8 bytes. But HotSpot aligns every object to an 8-byte boundary, which means the lowest 3 bits of any object's address are always zero — genuinely wasted information. Below a 32 GB heap, the JVM exploits this: it stores references as 32-bit numbers and shifts them left by 3 bits whenever they're loaded into a register, recovering the full 8-byte address cheaply. This is Compressed OOPs, and it's on by default.

The cliff
The instant your heap crosses roughly 32 GB, this trick stops working and compressed OOPs turn off automatically. Every reference field across your entire heap silently doubles from 4 to 8 bytes. For pointer-dense structures — HashMap nodes, LinkedList nodes, TreeMap entries — this alone can inflate memory use by 30–50%, with zero new data stored. Sizing a heap to sit just under 32 GB is often a deliberate, informed choice rather than an accident.
14 — MODERN CACHING

Why LinkedHashMap and bare ConcurrentHashMap both fail as caches

A cache needs two things neither built-in structure gives you for free: bounded size, and eviction of the right item.
  • LinkedHashMap in access-order mode can track recency and evict the least-recently-used item — but it does so by locking on every single read to reposition the accessed entry, which is a serialization bottleneck under concurrent traffic.
  • A bare ConcurrentHashMap has no eviction policy at all. Bolt one on with a periodic background scan and you've turned eviction into an O(n) sweep that can stall the whole application.

Modern caches (Caffeine, built by Ben Manes) solve this with Window TinyLFU (W-TinyLFU), which separates "is this cache full" from "did anyone actually look at this item recently" into two independent, cheap mechanisms:

Lock-free read buffering

A cache read is a plain ConcurrentHashMap.get() — no lock. The read event is separately dropped into a small ring buffer. A background thread drains that buffer in batches later, so recency bookkeeping never sits on the hot read path.

Count-Min Sketch filter

A tiny probabilistic structure (a few megabytes for millions of entries) estimates how often each key has been seen recently. A new candidate only evicts an existing item if its estimated frequency is actually higher — protecting the cache from being flushed by one big one-off scan.

Segmented LRU

Space splits into a small "Window" (catches short-term bursty access) and a larger "Main" cache (Probational + Protected). An adaptive algorithm shifts the boundary between them based on live hit-rate feedback.

The net effect: near-lock-free reads, bounded memory, and materially higher hit rates than a plain LRU under real-world access patterns.

15 — CODE YOU WILL ACTUALLY BE ASKED TO WRITE

Hands-on method reference

Knowing how something works is half the interview. The other half is writing correct code on a whiteboard or shared editor, fast. Below are the methods you will really use, with short, real code for each.

List — ArrayList / LinkedList

List<String> names = new ArrayList<>();
names.add("Anna");                 // append at end — O(1) amortized
names.add(0, "Zoe");               // insert at front — O(n), shifts everyone right
names.get(1);                        // read by index — O(1) for ArrayList
names.set(1, "Ravi");               // overwrite by index
names.remove("Zoe");                // remove by VALUE (uses equals())
names.remove(0);                     // remove by INDEX (be careful with Integer vs int here!)
names.contains("Anna");             // O(n) linear scan — no shortcut for List
names.removeIf(n -> n.length() < 3); // remove every element matching a condition
Collections.sort(names);             // natural order (needs Comparable) — O(n log n)
names.sort(Comparator.reverseOrder()); // or a custom Comparator
Classic interview trap
names.remove(2) removes the element at index 2. But names.remove(Integer.valueOf(2)) removes the element equal to the value 2 — because now you've passed an Integer object, not an int, so Java picks the other overloaded method. This exact gotcha gets asked a lot.

Set — HashSet / LinkedHashSet / TreeSet

Set<String> seen = new HashSet<>();
seen.add("a");                 // O(1) average — returns false if already present
seen.contains("a");            // O(1) average — the whole reason to use a Set
seen.retainAll(otherSet);      // keep only common elements — set intersection
seen.removeAll(otherSet);      // set difference
TreeSet<Integer> sorted = new TreeSet<>(List.of(5,1,9,3));
sorted.first(); sorted.last();       // smallest / largest — O(log n)
sorted.ceiling(4); sorted.floor(4);  // smallest ≥4 / largest ≤4

Map — HashMap / TreeMap / LinkedHashMap

Map<String, Integer> wordCount = new HashMap<>();
wordCount.put("cat", 1);                                  // insert or overwrite
wordCount.get("cat");                                     // returns null if missing — check carefully!
wordCount.getOrDefault("dog", 0);                         // safer read, no null surprise
wordCount.putIfAbsent("cat", 99);                         // only inserts if key is missing — no overwrite

// The single most useful pattern in interview code — counting frequency:
wordCount.merge("cat", 1, Integer::sum);                   // if absent: put 1. if present: add 1.

// Grouping items under a key, building a list as you go:
Map<String, List<String>> groups = new HashMap<>();
groups.computeIfAbsent("vowel", k -> new ArrayList<>()).add("apple");

for (Map.Entry<String,Integer> e : wordCount.entrySet()) {   // standard safe iteration
    System.out.println(e.getKey() + "=" + e.getValue());
}
Why merge() and computeIfAbsent() matter so much in interviews
Before these existed, counting frequencies took 3 lines (check contains, then either put or increment). merge() and computeIfAbsent() collapse that into one line and remove an entire class of bugs. Interviewers specifically look for whether you know these — using them is a strong, fast signal that you write modern Java, not Java from 2010.

Deque — as a stack, and as a queue

16 — INTERVIEW-STYLE STREAM API PROBLEMS

Solving collection problems with the Stream API

Interviewers love asking "now do it with streams." Below are common problems, each read as: take a collection in, get a new collection or value out, in one readable pipeline.

1. Count word frequency (List → Map)

List<String> words = List.of("cat","dog","cat","bird","dog","cat");
Map<String, Long> freq = words.stream()
    .collect(Collectors.groupingBy(w -> w, Collectors.counting()));
// {bird=1, cat=3, dog=2}

2. Find the top-3 most frequent elements

List<String> top3 = freq.entrySet().stream()
    .sorted(Map.Entry.<String,Long>comparingByValue().reversed())
    .limit(3)
    .map(Map.Entry::getKey)
    .collect(Collectors.toList());

3. Group a list of objects by a property

// group employees by department name
Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));

// same, but just count them per department
Map<String, Long> countByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.counting()));

4. Partition into two groups (even / odd, pass / fail)

Map<Boolean, List<Integer>> parts = numbers.stream()
    .collect(Collectors.partitioningBy(n -> n % 2 == 0));
List<Integer> evens = parts.get(true);
List<Integer> odds  = parts.get(false);

5. Flatten a list of lists into one list

List<List<Integer>> nested = List.of(List.of(1,2), List.of(3,4), List.of(5));
List<Integer> flat = nested.stream()
    .flatMap(List::stream)
    .collect(Collectors.toList());
// [1, 2, 3, 4, 5]

6. Remove duplicates while keeping insertion order

List<String> unique = names.stream()
    .distinct()                       // internally uses a HashSet to track "seen" items
    .collect(Collectors.toCollection(LinkedHashSet::new));

7. Join collection elements into one readable string

String csv = names.stream()
    .collect(Collectors.joining(", ", "[", "]"));
// "[Anna, Ravi, Chen]"
The pattern to remember
Every stream problem is really three steps: filter (keep what you want), map (transform each item into something else), and collect (pour the results into a real collection — usually via Collectors). Once you can name which of the three a problem needs, writing the stream becomes mechanical.

18 — PUTTING IT TOGETHER

Four system-design scenarios, worked through out loud

This is the shape a lead-level interview question actually takes: a constraint-laden scenario, not a "define HashMap" prompt. Here's how the reasoning above resolves each one.

1 — In-memory cache, 500K entries, 95:5 read:write, p99 < 2ms

Collections.synchronizedMap(LinkedHashMap) fails immediately — every read takes the global monitor to reposition LRU pointers, so reads queue behind each other under load. A bare ConcurrentHashMap plus a background sweep thread fails differently: the periodic O(n) eviction scan risks GC-pause-like latency spikes. Answer: a W-TinyLFU cache (Caffeine) — lock-free reads against an internal ConcurrentHashMap, async batched recency tracking, memory capped by the Count-Min Sketch admission filter.

2 — 1M+ events/sec between 8 producer threads and 1 consumer, GC pauses >1ms unacceptable

LinkedBlockingQueue is disqualified by its own design: a new Node object per event at 1M events/sec means tens of megabytes of short-lived garbage every second — frequent young-gen GC. ArrayBlockingQueue avoids allocation but funnels all 8 producers and the consumer through one shared lock. Answer: a pre-allocated lock-free ring buffer (LMAX Disruptor pattern) — no runtime allocation at all, sequence counters padded to avoid false sharing, producers claim slots via CAS.

3 — 50,000 live counters, high write rate, periodic full-scan reporting

A ReentrantReadWriteLock around a plain HashMap forces writers to queue behind the reporting thread's full scan every 5 seconds. CopyOnWriteArrayList/Set forces a full 50,000-entry array clone on every single write. Answer: ConcurrentHashMap<String, LongAdder> — writers hit only their own key's striped counter, and the reporting thread's weakly-consistent iteration reads live volatile references without blocking anyone.

4 — Pre-loading 10 million entries into a map at startup

Constructing with the default capacity forces roughly log₂(10,000,000 × 4/3 ÷ 16) ≈ 20 successive doublings, each one a full table reallocation and node migration under load. Answer: pre-size the map — new ConcurrentHashMap<>((int)(10_000_000/0.75f)+1) — allocating the final backing array once, up front, eliminating every intermediate resize.
