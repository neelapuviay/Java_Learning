08 — BEFORE ANY "CONCURRENT" CLASS MAKES SENSE

What actually goes wrong when two threads share data

Everything from here on — ConcurrentHashMap, CopyOnWriteArrayList, blocking queues — exists to solve one problem. Let's see the problem first.

A thread is an independent sequence of instructions your program runs. Modern CPUs have multiple cores, so multiple threads can genuinely execute at the same instant — not just take turns quickly. That's the whole point of concurrency: real parallel speed. It's also where the trouble starts.

🏧
Analogy: two people, one bank balance, no communication
A shared bank balance reads $100. You and your partner both check the balance at the same instant, both see $100, and both decide to withdraw $80. Each of you independently computes "100 − 80 = 20" and writes 20 back. The bank ends up at $20 — even though $160 was withdrawn from an account that only had $100. Nobody did anything individually wrong; the problem is that read, decide, and write weren't a single uninterruptible step. This is exactly what an unsynchronized counter++ does across two threads.

This is called a race condition: the final result depends on the unpredictable timing of two threads, rather than on the logic of the program. Java gives you two fundamentally different tools to prevent it:

🔒 Locking — make threads take turns

A synchronized block or ReentrantLock lets only one thread execute the protected code at a time. Every other thread trying to enter is parked — put to sleep by the OS — until the lock is free. Simple to reason about, but threads waiting on a lock do zero useful work, and heavy contention means most threads spend their time asleep.

⚡ CAS — bet, then check

Compare-And-Swap is a single CPU instruction: "if this memory location still holds the value I expect, replace it with my new value — atomically, as one indivisible step. Tell me if it worked." No thread ever sleeps. If the swap fails because someone else got there first, the thread just re-reads the current value and tries again. This is called lock-free programming.

CAS is what lets a data structure be thread-safe without ever putting a thread to sleep for the common case — which is exactly the trick ConcurrentHashMap, LongAdder, and ConcurrentSkipListMap all lean on.

09 — THE STANDARD THREAD-SAFE MAP

ConcurrentHashMap: CAS where it can, a tiny lock where it must

The most important upgrade in ConcurrentHashMap's history: Java 7 locked in coarse 16-way stripes. Java 8 rebuilt it to lock almost nothing.

The old way (Java 7): segment striping

Java 7's ConcurrentHashMap pre-split the table into 16 independent Segments, each guarded by its own lock. Up to 16 threads could write simultaneously — one per segment — but any operation needing a global view (like computing overall size, or resizing) had to lock across all segments at once.

The current design (Java 8+): per-bucket, not per-segment

Java 8 threw out segments entirely. The table now looks just like HashMap's — a flat array of buckets — but every operation on a bucket is protected individually and as cheaply as possible:

helps finish the resize instead of waiting

The insight: locking one bucket's head node blocks nothing else in the table. Two threads writing to two different buckets run fully in parallel — even though both technically "hold a lock" at that moment.

Cooperative resizing: nobody blocks, everybody helps

A single-threaded HashMap resize just stops and copies everything. A concurrent map can't get away with "stop the world" — other threads must be able to keep working. ConcurrentHashMap solves this with two shared counters:

  • sizeCtl — when negative, encodes that a resize is in progress, packing a generation stamp and a count of active migrating threads into one int
  • transferIndex — the next unclaimed stretch of buckets still needing migration

Any thread that stumbles onto a ForwardingNode (a marker left on an already-migrated bucket) doesn't wait around — it calls helpTransfer() and claims its own stride of buckets to migrate via a CAS decrement on transferIndex. Whichever threads happen to be around during a resize simply pitch in; the resize finishes faster the busier the map is.

Why null is banned
map.get(key) returning null is ambiguous in a single thread: is the key mapped to null, or just absent? You'd normally resolve this with a follow-up containsKey(key) call. In a concurrent map, another thread can insert or remove that exact key between your two calls — so the two-step check is no longer atomic and can lie to you. Doug Lea's fix was simpler than any locking scheme: ConcurrentHashMap just refuses to store null at all, and throws NullPointerException immediately if you try.

Counting size without a global lock: LongAdder

If every thread updated one shared counter with CAS, all of them would repeatedly collide on the exact same memory address — the CPU cache line backing that counter gets invalidated on every single update (more on this in the mechanical sympathy section). LongAdder instead keeps a base counter plus an array of independent striped counters. Under contention, each thread hashes to its own stripe and updates that instead — collisions become rare — and sum() just adds every stripe together when a total is actually needed.

💡 Quick Knowledge Check
Why does ConcurrentHashMap.get(key) require ZERO locks or synchronization blocks, even while another thread is concurrently inserting or modifying entries?
Answer: In Java's ConcurrentHashMap, Node.val and Node.next are declared volatile. Volatile reads guarantee happens-before memory visibility directly from CPU cache coherency (MESI protocol) without stale register caching. If a read races with rehashing, it transparently follows immutable ForwardingNode references to the new table, so reads never block or contend for locks!
10 — READ-HEAVY, WRITE-RARE

CopyOnWriteArrayList: reads that never even see a lock

An entirely different bet: what if writes were expensive, so reads could be completely free?

CopyOnWriteArrayList stores its data in a volatile Object[] array. Reads just read that reference directly — no lock, no CAS retry loop, nothing. They're as fast as reading a plain array, and they can never throw ConcurrentModificationException, because they never even look at whether the array has changed.

The cost is paid entirely by writers. Every single mutation — even adding one element — does this under a ReentrantLock:

public boolean add(E e) {
    lock.lock();
    try {
        Object[] newElements = Arrays.copyOf(getArray(), len + 1);
        newElements[len] = e;
        setArray(newElements);  // swap the volatile reference — readers now see it
    } finally { lock.unlock(); }
}
📋
Analogy: a clipboard that gets fully re-photocopied on every edit
Anyone can glance at the clipboard on the wall at any moment without asking permission — they just see whatever page is currently pinned up. But to make an edit, you have to photocopy the entire page, mark it up, and pin the new copy over the old one. If the clipboard has 50,000 lines, every single edit means recopying all 50,000 lines. Fine if edits are rare. Ruinous if edits happen constantly.

An iterator created over a CopyOnWriteArrayList captures the array reference at that instant — a snapshot. It will never reflect later writes, and it doesn't support remove()/set()/add() through the iterator at all. This makes it a strong fit for things like listener/observer lists — read constantly, modified almost never — and a poor fit for anything write-heavy.

11 — PRODUCER / CONSUMER PIPELINES

Blocking queues: when threads should actually wait

Sometimes waiting is correct — a consumer thread with nothing to do genuinely should sleep rather than spin. These queues make that safe and efficient.

ArrayBlockingQueue

Fixed-size array, bounded capacity fixed at creation. One single ReentrantLock guards both put() and take(), with two condition variables (notEmpty, notFull) used to park and wake threads efficiently. Because producers and consumers share the one lock, they can contend with each other under bursty load — but memory use is minimal and fully predictable.

LinkedBlockingQueue

Unbounded by default, built from linked nodes. Uses two separate locks — putLock and takeLock — so producers and consumers stop contending with each other entirely. The trade-off: every insertion allocates a new node, adding garbage-collection pressure that the array-backed queue avoids.

SynchronousQueue: a queue with zero capacity

This one holds nothing at all. Every put() must rendezvous directly with a waiting take() — it's a pure hand-off between two threads, not storage. Internally it's a lock-free "dual" structure (a dual-stack for LIFO mode, a dual-queue for FIFO mode) where nodes represent either "I have data waiting" or "I want data." This is the queue behind Executors.newCachedThreadPool(), where a new task should hand directly to an idle worker thread.

LinkedTransferQueue: the "give me everything" queue

Combines ideas from all of the above into one unbounded, lock-free queue. Its signature addition is transfer(e): it blocks until some consumer actually takes the element, guaranteeing direct hand-off semantics even though the queue is otherwise unbounded and non-blocking for normal put()/take() use.

12 — CONCURRENT + SORTED, WITHOUT A TREE

ConcurrentSkipListMap: an express-lane linked list

Balanced trees (Red-Black, AVL) rebalance by rotating nodes across multiple levels — brutal to do safely without locking large parts of the tree. Skip lists sidestep the whole problem.

A skip list is just several linked lists stacked on top of each other. Level 0 holds every element in sorted order — nothing fancy. Each level above it holds a randomly-chosen, thinner subset of the level below, like an express train that only stops at some of the same stations as the local train.

Whether a new node gets promoted to a higher level is decided by a random coin flip at insertion time (typically 50/50 per level) — no rebalancing operation is ever needed, because the structure's shape is probabilistic by construction rather than something that must be actively maintained.

Deleting without locking: the tombstone protocol

Removing a node safely while other threads are mid-traversal, without a lock, takes three CAS-driven steps:

  1. Logical deletion — CAS the node's value to null. It's now "dead" but still physically linked in.
  2. Marker insertion — CAS in a special tombstone node right after it, so any thread walking past knows this node is being removed.
  3. Physical unlinking — the next thread that happens to walk past (any thread — not necessarily the deleter) finishes the job, rewiring the previous node's pointer to skip over both the dead node and its tombstone.

That last step is the elegant part: cleanup work is shared opportunistically across whichever threads happen to pass by, instead of being one thread's exclusive responsibility.

ConcurrentSkipListMap is the map to reach for when you need both sorted order and thread safety — ConcurrentHashMap gives you thread safety but no ordering at all.
