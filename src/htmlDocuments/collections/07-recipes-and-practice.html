15 — CODE YOU WILL ACTUALLY BE ASKED TO WRITE

Hands-on method reference

Below are the methods you will really use, with short, idiomatic code for each.

List — ArrayList / LinkedList

List<String> names = new ArrayList<>();
names.add("Anna");                 // append at end — O(1) amortized
names.add(0, "Zoe");               // insert at front — O(n), shifts everyone right
names.get(1);                        // read by index — O(1) for ArrayList
names.set(1, "Ravi");               // overwrite by index
names.remove("Zoe");                // remove by VALUE (uses equals())
names.remove(0);                     // remove by INDEX (be careful with Integer vs int here!)
names.contains("Anna");             // O(n) linear scan — no shortcut for List
names.removeIf(n -> n.length() < 3); // remove every element matching a condition
Collections.sort(names);             // natural order (needs Comparable) — O(n log n)
names.sort(Comparator.reverseOrder()); // or a custom Comparator
Classic interview trap
names.remove(2) removes the element at index 2. But names.remove(Integer.valueOf(2)) removes the element equal to the value 2 — because now you've passed an Integer object, not an int, so Java picks the other overloaded method. This exact gotcha gets asked constantly in interviews.

Set — HashSet / LinkedHashSet / TreeSet

Set<String> seen = new HashSet<>();
seen.add("a");                 // O(1) average — returns false if already present
seen.contains("a");            // O(1) average — the whole reason to use a Set
seen.retainAll(otherSet);      // keep only common elements — set intersection
seen.removeAll(otherSet);      // set difference
TreeSet<Integer> sorted = new TreeSet<>(List.of(5,1,9,3));
sorted.first(); sorted.last();       // smallest / largest — O(log n)
sorted.ceiling(4); sorted.floor(4);  // smallest ≥4 / largest ≤4

Map — HashMap / TreeMap / LinkedHashMap

Map<String, Integer> wordCount = new HashMap<>();
wordCount.put("cat", 1);                                  // insert or overwrite
wordCount.get("cat");                                     // returns null if missing — check carefully!
wordCount.getOrDefault("dog", 0);                         // safer read, no null surprise
wordCount.putIfAbsent("cat", 99);                         // only inserts if key is missing — no overwrite

// The single most useful pattern in interview code — counting frequency:
wordCount.merge("cat", 1, Integer::sum);                   // if absent: put 1. if present: add 1.

// Grouping items under a key, building a list as you go:
Map<String, List<String>> groups = new HashMap<>();
groups.computeIfAbsent("vowel", k -> new ArrayList<>()).add("apple");

for (Map.Entry<String,Integer> e : wordCount.entrySet()) {   // standard safe iteration
    System.out.println(e.getKey() + "=" + e.getValue());
}
Why merge() and computeIfAbsent() matter so much in interviews
Before these existed, counting frequencies took 3 lines (check contains, then either put or increment). merge() and computeIfAbsent() collapse that into one line and remove an entire class of bugs. Interviewers specifically look for whether you know these — using them is a strong signal that you write clean modern Java.

Deque — as a stack, and as a queue

Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); stack.push(2);      // push = addFirst
stack.pop();                       // pop = removeFirst → returns 2 (LIFO — last in, first out)

Deque<Integer> queue = new ArrayDeque<>();
queue.offer(1); queue.offer(2);    // offer = addLast
queue.poll();                      // poll = removeFirst → returns 1 (FIFO — first in, first out)

PriorityQueue

PriorityQueue<Integer> minHeap = new PriorityQueue<>();                 // smallest first, by default
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder()); // largest first
minHeap.offer(5); minHeap.offer(1); minHeap.offer(9);
minHeap.peek();   // look at the smallest without removing — O(1)
minHeap.poll();   // remove and return the smallest — O(log n)

ConcurrentHashMap

ConcurrentHashMap<String, LongAdder> metrics = new ConcurrentHashMap<>();
metrics.computeIfAbsent("clicks", k -> new LongAdder()).increment(); // thread-safe, no external lock
metrics.forEach((key, adder) -> System.out.println(key + "=" + adder.sum())); // weakly consistent, non-blocking
16 — INTERVIEW-STYLE STREAM API PROBLEMS

Solving collection problems with the Stream API

Interviewers love asking "now do it with streams." Below are common problems, each read as: take a collection in, get a new collection or value out, in one readable pipeline.

1. Count word frequency (List → Map)

List<String> words = List.of("cat","dog","cat","bird","dog","cat");
Map<String, Long> freq = words.stream()
    .collect(Collectors.groupingBy(w -> w, Collectors.counting()));
// {bird=1, cat=3, dog=2}

2. Find the top-3 most frequent elements

List<String> top3 = freq.entrySet().stream()
    .sorted(Map.Entry.<String,Long>comparingByValue().reversed())
    .limit(3)
    .map(Map.Entry::getKey)
    .collect(Collectors.toList());

3. Group a list of objects by a property

// group employees by department name
Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));

// same, but just count them per department
Map<String, Long> countByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.counting()));

4. Partition into two groups (even / odd, pass / fail)

Map<Boolean, List<Integer>> parts = numbers.stream()
    .collect(Collectors.partitioningBy(n -> n % 2 == 0));
List<Integer> evens = parts.get(true);
List<Integer> odds  = parts.get(false);

5. Flatten a list of lists into one list

List<List<Integer>> nested = List.of(List.of(1,2), List.of(3,4), List.of(5));
List<Integer> flat = nested.stream()
    .flatMap(List::stream)
    .collect(Collectors.toList());
// [1, 2, 3, 4, 5]

6. Remove duplicates while keeping insertion order

List<String> unique = names.stream()
    .distinct()                       // internally uses a HashSet to track "seen" items
    .collect(Collectors.toCollection(LinkedHashSet::new));

7. Join collection elements into one readable string

String csv = names.stream()
    .collect(Collectors.joining(", ", "[", "]"));
// "[Anna, Ravi, Chen]"
The pattern to remember
Every stream problem is really three steps: filter (keep what you want), map (transform each item into something else), and collect (pour the results into a real collection — usually via Collectors). Once you can name which of the three a problem needs, writing the stream becomes mechanical.

18 — PUTTING IT TOGETHER

Four system-design scenarios, worked through out loud

This is the shape a lead-level interview question actually takes: a constraint-laden scenario, not a "define HashMap" prompt. Here's how the reasoning above resolves each one.

1 — In-memory cache, 500K entries, 95:5 read:write, p99 < 2ms

Collections.synchronizedMap(LinkedHashMap) fails immediately — every read takes the global monitor to reposition LRU pointers, so reads queue behind each other under load. A bare ConcurrentHashMap plus a background sweep thread fails differently: the periodic O(n) eviction scan risks GC-pause-like latency spikes. Answer: a W-TinyLFU cache (Caffeine) — lock-free reads against an internal ConcurrentHashMap, async batched recency tracking, memory capped by the Count-Min Sketch admission filter.

2 — 1M+ events/sec between 8 producer threads and 1 consumer, GC pauses >1ms unacceptable

LinkedBlockingQueue is disqualified by its own design: a new Node object per event at 1M events/sec means tens of megabytes of short-lived garbage every second — frequent young-gen GC. ArrayBlockingQueue avoids allocation but funnels all 8 producers and the consumer through one shared lock. Answer: a pre-allocated lock-free ring buffer (LMAX Disruptor pattern) — no runtime allocation at all, sequence counters padded to avoid false sharing, producers claim slots via CAS.

3 — 50,000 live counters, high write rate, periodic full-scan reporting

A ReentrantReadWriteLock around a plain HashMap forces writers to queue behind the reporting thread's full scan every 5 seconds. CopyOnWriteArrayList/Set forces a full 50,000-entry array clone on every single write. Answer: ConcurrentHashMap<String, LongAdder> — writers hit only their own key's striped counter, and the reporting thread's weakly-consistent iteration reads live volatile references without blocking anyone.

4 — Pre-loading 10 million entries into a map at startup

Constructing with the default capacity forces roughly log₂(10,000,000 × 4/3 ÷ 16) ≈ 20 successive doublings, each one a full table reallocation and node migration under load. Answer: pre-size the map — new ConcurrentHashMap<>((int)(10_000_000/0.75f)+1) — allocating the final backing array once, up front, eliminating every intermediate resize.

💡 Quick Knowledge Check
Why does modifying a collection inside an enhanced for-loop (for (String s : list) { list.remove(s); }) throw ConcurrentModificationException even in a single-threaded program?
Answer: The enhanced for-loop compiles down to an Iterator. The iterator records list's expectedModCount = modCount when created. Calling list.remove() directly mutates the underlying list and increments modCount++, but leaves the iterator's expectedModCount unchanged. On the very next iterator.next() check, modCount != expectedModCount is detected, throwing fail-fast ConcurrentModificationException! To safely remove elements, use iterator.remove() or Java 8's two-pointer list.removeIf(...).
