04 — THE MOST-ASKED INTERVIEW TOPIC

HashMap: how a key finds its shelf

HashMap's entire job is answering one question fast: "given this key, which of my internal buckets should I look in?" Everything below is in service of that one question.

Step 1 — turn the key into a number

Every Java object has a hashCode() method that reduces it to a single 32-bit integer. Think of it as a meaningless-looking fingerprint — two equal objects must produce the same fingerprint, but the fingerprint itself carries no readable meaning.

📇
Analogy: hashCode is a librarian's shelving code, not the book's title
A librarian doesn't file 10,000 books alphabetically by full title (slow to search). She converts each title into a short shelving code and stores books by that code. HashMap does the same: it never compares your key against every stored key. It uses the key's fingerprint to jump straight to the one shelf (bucket) it must be on.

Step 2 — spread the fingerprint's bits

A raw hashCode() can be a bad fit for a small bucket array — many hash codes differ only in their high bits, which get thrown away by the next step. So HashMap runs a cheap "spreading" step first:

static final int hash(Object key) {
    int h = key.hashCode();
    // shift the top 16 bits down, XOR them into the bottom 16
    return h ^ (h >>> 16);
}

This mixes high-order bits into the low-order bits, so differences that only show up "way up high" in the number still influence which bucket gets picked.

Step 3 — mask it down to a bucket index

HashMap's internal array (Node<K,V>[] table) always has a size that's a power of two (16, 32, 64…). This is deliberate: for a power-of-two size n, hash % n gives exactly the same answer as hash & (n - 1) — a bitwise AND — but AND is a single, near-free CPU instruction, while % (division) is dozens of times slower.

Table capacity fixed at 16 for this demo, so the mask is & 15 (binary 1111) — it simply keeps the lowest 4 bits of the spread hash.

Collisions: two keys, one bucket

Different keys can land on the same bucket index — that's a collision, and it's expected, not a bug. HashMap handles it with separate chaining: the bucket holds a linked list of every entry that landed there, and a lookup walks that short list comparing keys with equals().

16 buckets. Insert a few keys and watch collisions form chains.

When a chain gets long: treeification

A linked-list bucket is fine at 1–3 entries — a short walk. But imagine an attacker deliberately crafts thousands of keys that all hash to the same bucket (a "hash-flooding" attack): that bucket's list balloons, and every lookup degrades toward O(n). Since Java 8, HashMap defends against this:

The 8/6 rule
If a single bucket's chain reaches 8 entries and the table has at least 64 buckets total, that one bucket converts from a linked list into a small Red-Black tree (self-balancing binary search tree). Worst-case lookup in that bucket drops from O(n) to O(log n). If the bucket later shrinks to 6 or fewer entries, it converts back to a plain list. The 8-vs-6 gap (not both set to 7) is deliberate — it stops a bucket from flapping back and forth between tree and list every time one key is added or removed near the threshold.

Below 64 total buckets, HashMap prefers to just grow the whole table instead of building a tree — a bigger table usually spreads the same 8 entries across separate buckets anyway, so building a tree would be wasted work.

If two keys land in the same tree bucket and don't implement Comparable (or compare equal), Java can't decide tree order from the key's value alone — so it breaks the tie using System.identityHashCode(), essentially "which object was created first in memory," just to guarantee the tree stays consistently ordered.

Resizing: doubling without starting over

HashMap resizes (doubles its table) once occupancy passes capacity × load factor — by default 0.75, so a 16-bucket table resizes after its 13th entry. A smaller load factor wastes memory on empty buckets; a larger one causes more collisions. 0.75 is Java's measured sweet spot.

Here's the elegant part: because capacity always doubles (16→32→64…), the bitmask only ever grows by one bit at a time. That means every existing entry has only two possible destinations in the new table: its same index, or its same index + old capacity — depending on whether that one new bit happens to be 0 or 1 in its hash. HashMap never has to recompute a full hash during resize; it just checks one bit and splits each chain into a "stays low" list and a "moves high" list.

Interview trap
Always construct a HashMap (or ConcurrentHashMap) with an expected size up front — new HashMap<>(expectedSize) — when you know roughly how many entries are coming. Skipping this means the table silently resizes (and fully re-buckets) log₂(finalSize/16) times during a big bulk load, each one a stop-and-copy pause.
💡 Quick Knowledge Check
When a HashMap bucket reaches 8 elements, why does Java convert the linked list into a Red-Black Tree (TreeNode), and what happens if the keys do not implement Comparable?
Answer: A linked list degenerates to O(N) lookup under hash collision attacks (e.g. malicious duplicate hash codes). A Red-Black tree guarantees O(log N) worst-case lookup. If keys don't implement Comparable<K>, Java breaks ties using tieBreakOrder() which compares the keys' class names and native System.identityHashCode() to maintain a deterministic search tree!
05 — YOU ALREADY KNOW THESE, YOU JUST DON'T KNOW IT YET

HashSet, LinkedHashSet, TreeSet, LinkedHashMap, TreeMap

Good news first: none of these five classes are a new data structure. Every single one is either a HashMap wearing a costume, or the same Red-Black tree you just met a moment ago. Once you see the trick, you can never un-see it.

HashSet: a HashMap wearing a costume

Open the real Java source code for HashSet and this is almost the entire class:

public class HashSet<E> {
    // a HashSet does not have its own buckets — it hides a HashMap inside itself
    private HashMap<E, Object> map;

    // one single dummy object, shared by every element, in every HashSet, in the whole program
    private static final Object PRESENT = new Object();

    public boolean add(E e) {
        return map.put(e, PRESENT) == null;   // your element becomes the KEY
    }
    public boolean contains(Object o) {
        return map.containsKey(o);
    }
}

Read that slowly, in plain words: add(x) really just means map.put(x, PRESENT), and contains(x) really just means map.containsKey(x). There is no separate hashing logic, no separate bucket array, no separate collision handling written anywhere for HashSet — because it doesn't need any. It borrows all of it from HashMap.

🎭
Simple picture: a coat rack with one spare coat
Imagine a coat rack (the HashMap) with a labeled hook for every item. A HashSet doesn't build its own coat rack — it uses the same one, and it hangs the exact same spare coat (the shared PRESENT object) on every hook, no matter what the hook's label is. The label is the only thing anyone actually cares about — that's your element.

This one fact means every rule you already learned in the HashMap section above is automatically true for HashSet too: hashCode() turns your object into a number, that number gets its bits spread and masked down to a bucket index, two elements landing in the same bucket form a chain, and a chain that grows past 8 entries (in a table of 64+ buckets) quietly turns into the same Red-Black tree. You did not learn a second data structure just now — you learned that HashSet is HashMap, minus the values.

On memory, specifically
A HashSet object on the heap doesn't hold a bucket array of its own — it holds one reference to a hidden HashMap object, which is the thing that actually holds the bucket array. So creating a HashSet costs one small extra object compared to creating a HashMap directly. The PRESENT placeholder costs almost nothing, because Java creates it exactly once, ever, and every HashSet in your entire program reuses that same single object — it is never duplicated per element.

LinkedHashSet and LinkedHashMap: one hidden chain, threaded through the buckets

A plain HashMap makes you no promises at all about the order you'll see when you loop over it — the order just falls out of which bucket each key happened to land in, and that looks completely random to a human. LinkedHashMap fixes exactly that one problem, with one small addition.

Every entry in a LinkedHashMap carries two extra fields that a normal HashMap entry does not have: before and after — references pointing to the entry that was inserted right before it, and the entry inserted right after it. Line all of those up, and you get a second, invisible linked list running through the entries, completely separate from the bucket array underneath. When you iterate, Java ignores the buckets entirely and just walks this hidden chain from the oldest entry to the newest — which is exactly why the order you see matches the order you inserted things in.

🧵
Simple picture: numbered raffle tickets on a shelf of unlabeled boxes
The boxes (buckets) are still scattered around in whatever order hashing puts them in — nothing changes there. But now imagine a piece of thread tied from the first box you filled, to the second, to the third, and so on. To read things back "in the order I added them," you don't look at the shelf at all — you just follow the thread.
This costs real memory — which is the whole point of this guide
Two extra references per entry sounds small, but it is not free: on most 64-bit JVMs that's around 16 extra bytes per entry, and two more fields the garbage collector must trace every time it scans that object. This is a direct, measurable trade: you are spending heap memory to buy yourself a predictable iteration order. LinkedHashSet is to LinkedHashMap exactly what HashSet is to HashMap — a thin wrapper hiding a private LinkedHashMap<E,Object> field inside, reusing the exact same PRESENT trick.

Building an LRU Cache: The Magic of accessOrder = true

📚
Simple picture: A 3-book shelf (The LRU eviction rule)
Imagine a small bookshelf that only holds 3 books. You want to keep your favorite, most popular books on this shelf. When the shelf is full and you buy a new book, which one do you throw away?

The smartest choice is usually: throw away the book you haven't touched for the longest time.

In computer science, this strategy is called an LRU Cache (Least Recently Used cache).

Part 1: How accessOrder = true Works

A standard map in Java just remembers data (key and value pairs). A LinkedHashMap is special because it also ties all the items together with an invisible chain in a specific line.

  • Normal behavior (accessOrder = false): The line is organized strictly by when items were first put into the map (insertion order).
  • Special behavior (accessOrder = true): The line updates every time you touch an item (both reads and writes).

Normally, reading a book doesn't change anything. But because accessOrder = true, Java unlinks A and moves it all the way to the end as the newest accessed item: [B] → [C] → [A].

If your shelf fills up and you must insert D, Java kicks out the item at the very front of the line — which is now B, because A was recently protected by your read!

In Java, you turn this into a functioning LRU cache by overriding removeEldestEntry():

// Textbook JDK LRU Cache (Max capacity: 3)
Map<String, String> lruCache = new LinkedHashMap<>(16, 0.75f, true /* accessOrder = true */) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, String> eldest) {
        return size() > 3; // Evict the head entry once size exceeds 3
    }
};
Part 2: The Hidden Catch (Why it fails under heavy traffic)

Most of the time in programming, reading data is completely safe to do with multiple people at once. Ten people can look at the same webpage or read the same book at the exact same second without bumping into each other.

Writing (changing) data is different. If two people try to rewrite the same page at the same time, it causes chaos. So programmers put a lock on the book: only one person can write at a time while everyone else waits.

Here is the critical problem with accessOrder = true:

  • Because of that flag, a read is secretly a write.
  • When you call get(), Java isn't just looking at the value. It is actively unhooking pointers (before and after) and rearranging the doubly linked chain behind the scenes.
  • If two computer threads try to rearrange the chain at the exact same millisecond, the chain breaks, cyclic references are formed, and the program crashes or loops infinitely.
  • The consequence: You must force every reader to wait in a single line using a lock (such as Collections.synchronizedMap). If thousands of users are reading data at the same second, everything slows to a crawl because nobody can read at the same time.

In high-speed, multi-user systems, engineers avoid this flag and use specialized concurrent caches (like Caffeine or custom striped rings) that don't need to rebuild internal chains on every simple read. (See Module 06 · Advanced Performance & Caching for how W-TinyLFU and asynchronous ring buffers solve this without read locks).

TreeSet and TreeMap: the same Red-Black tree, used from the very first entry

You already met the Red-Black tree a moment ago — it's the shape a HashMap bucket turns itself into once its chain grows past 8 entries. TreeMap and TreeSet don't wait for that to happen. They use a Red-Black tree as their entire storage, starting from the very first entry you insert.

Here's the plain-English version of "self-balancing," since that word gets thrown around a lot without being explained: a normal binary search tree can accidentally turn into a straight line. If you insert 1, 2, 3, 4, 5 in that exact order into a plain BST, each new number is bigger than the last, so each one becomes the right child of the one before it — you end up with something that behaves exactly like a LinkedList, and looking something up costs O(n), a full walk. A Red-Black tree refuses to let this happen. Every time a node is inserted, the tree checks a small set of coloring rules (every node is marked red or black, and a few simple rules about which colors can sit next to each other must always hold), and if inserting the new node broke a rule, it performs a rotation — a quick local swap of a few pointers — to restore balance immediately.

The one guarantee that matters
A Red-Black tree guarantees the longest path from root to leaf is never more than roughly twice the length of the shortest path. That single guarantee is what keeps put(), get(), and remove() at O(log n) even in the worst case — unlike HashMap's O(1), which is only true on average and can degrade if hashing goes badly.

TreeSet follows the same pattern as HashSet and LinkedHashSet: it's a thin wrapper hiding a private TreeMap<E,Object> field, reusing the same one-shared-dummy-value trick. What you get in exchange for O(log n) instead of O(1) average is real ordering power a HashMap can never offer: first() / last() (smallest / largest), ceiling(x) / floor(x) (smallest ≥x / largest ≤x), higher(x) / lower(x) (strictly greater / strictly less), and whole range views like headMap(), tailMap(), and subMap(). None of this is possible on a HashMap — a HashMap doesn't track order, so it has no concept of "what comes just after this key."
