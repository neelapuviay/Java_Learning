06 — ORDERED EXTRACTION

Queue, Deque, and the binary heap

A List cares about position. A Queue cares about order of extraction — who gets served next.

ArrayDeque: the modern default

ArrayDeque ("double-ended queue") is a circular array with a head and tail index. It supports adding/removing from either end in O(1) without ever allocating a node object — so it plays FIFO queue, LIFO stack, and deque all at once, and generally beats both LinkedList and the ancient Stack class for these roles.

🔄
Analogy: a circular parking lot
Picture a row of parking spaces bent into a circle. Cars enter at one marker (tail) and leave from another (head). When the lot fills, instead of building a longer street, the whole ring just doubles in size. When the head pointer would run off the end of the array, it silently wraps back to index 0 — that's the bitwise trick head = (head - 1) & (capacity - 1), the same power-of-two masking trick HashMap uses.

PriorityQueue: a binary heap, not a sorted list

A common misconception: PriorityQueue does not keep its elements fully sorted. It keeps one guarantee only — the smallest element is always at the front — using a shape called a binary min-heap, stored compactly inside a plain array.

The trick is a pure-arithmetic tree: for any array index i, its parent lives at (i-1)/2, and its children live at 2i+1 and 2i+2. No pointers at all — the shape is implied entirely by position.

07 — JAVA 21

Sequenced Collections: one missing interface, finally added

A real gap existed for years: every ordered collection had a "first" and "last" element, but there was no common way to say so.
The problem, before Java 21
Getting the last element required a different idiom per type: list.get(list.size()-1) for a List, deque.getLast() for a Deque, sortedSet.last() for a SortedSet — and for a LinkedHashSet, there was no shortcut at all; you had to iterate the entire set just to reach the end.

JEP 431 introduced SequencedCollection<E>, sitting between Collection<E> and both List<E> and Deque<E>. It standardizes six methods every ordered collection can now share:

interface SequencedCollection<E> extends Collection<E> {
    void addFirst(E e);
    void addLast(E e);
    E getFirst();
    E getLast();
    E removeFirst();
    E removeLast();
    SequencedCollection<E> reversed();  // O(1) view, no copying
}

reversed() is the elegant part: it doesn't build a new reversed copy. It returns a thin view object that reads the same backing data back-to-front — so it's O(1) in time and memory, no matter the collection's size.

SequencedSet<E>

Extends both Set and SequencedCollection. LinkedHashSet now supports addFirst/addLast in O(1). SortedSet also implements this interface, but throws UnsupportedOperationException on addFirst — its order is dictated by a Comparator, not insertion, so "add at the front" is a contradiction it correctly refuses.

SequencedMap<K,V>

Adds firstEntry(), lastEntry(), pollFirstEntry(), pollLastEntry(), plus sequenced views sequencedKeySet() and sequencedEntrySet(). Implemented by LinkedHashMap and TreeMap.

💡 Quick Knowledge Check
Why does ArrayDeque consistently outperform LinkedList when used as a Queue or Stack (LIFO/FIFO), and why does ArrayDeque forbid null elements?
Answer: ArrayDeque uses a circular power-of-two array with head/tail pointers wrapped via bitwise (tail + 1) & (elements.length - 1). It has zero per-element Node object allocations and excellent CPU cache locality. It forbids null elements because methods like poll() and peek() return null as a sentinel value indicating that the deque is empty.
