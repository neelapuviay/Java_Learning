STAGE 10

The Big Picture — How the Whole Machine Connects

synthesis & lifetime phases

From the moment you type java MyApp to hours of continuous high-throughput production execution, the JVM constantly shifts its internal machinery. Select each lifecycle phase below to understand what dominates each era of execution.

Mental model — hold this picture

The JVM is not a program that runs your program. It is a machine that keeps rebuilding itself while your program runs on it. In the first hundred milliseconds it is mostly a file parser. A second later it is mostly an interpreter. Thirty seconds later it is mostly native code that no longer resembles your bytecode at all, running on assumptions it invented by watching you.

This is why "how fast is Java?" has no answer without a timestamp. The same method, unchanged, executes as bytecode dispatch, then as C1 code, then as inlined and vectorized C2 code, then possibly back to bytecode when an assumption breaks. The JVM's performance is a function of time, not just of code.

Every stage in this series is one subsystem of that self-rebuilding machine. This page is where they stop being nine separate topics and become one story.

The synthesis How the nine stages fit into one sentence each

If you can produce this chain from memory, you can answer almost any JVM question by locating it on the chain and expanding that link.

  1. Compile — javac emits bytecode for an imaginary stack machine, deliberately committing to nothing about the real hardware. Everything downstream exists because of that deliberate gap.
  2. Class loaders — a parent-first chain finds the bytes, and a class's identity becomes name + defining loader. That identity rule causes most exotic class-loading bugs.
  3. Load, link, initialize — bytes become a type in Metaspace, the verifier proves it safe so the fast path can skip checks, static slots get zero defaults, symbolic names get resolved lazily to pointers, and finally <clinit> runs once under a class lock.
  4. Interpret — execution starts at Tier 0, push/operate/pop, one frame per invocation on a thread-private stack. Slow by design, and it is where the profile begins.
  5. Profile — invocation and back-edge counters find the hot 20% of code, while richer telemetry records receiver types, branch frequencies and trip counts.
  6. JIT — C1 compiles fast and keeps profiling; C2 compiles slowly and brilliantly, using that profile to inline through virtual calls, delete unreached paths, remove allocations and vectorize loops.
  7. Deoptimize — every speculation carries a guard and a debug map, so when reality changes the JVM walks back to the interpreter mid-method rather than being wrong. Speculation is only sound because this exists.
  8. Memory areas — stacks are private and cheap; the heap is shared and collected; Metaspace, code cache, thread stacks and direct buffers are all native and all outside -Xmx.
  9. Garbage collection — trace from roots, exploit the fact that most objects die young, and trade pause time against throughput according to which collector you chose.

The three loops that run forever

Underneath the linear story, three feedback loops run continuously, and most production surprises are one of them changing state:

  • The compilation loop. Execute → profile → compile → speculate → guard fails → deoptimize → re-profile → recompile. Healthy during warm-up, pathological when it never settles.
  • The allocation loop. Allocate in Eden → young collection → survivors age → promotion → old generation fills → old/mixed collection. Healthy when almost everything dies young.
  • The loading loop. First active use → load → verify → initialize → resolve on first touch. Mostly front-loaded, but never finished — and late loading can invalidate compilations made hours earlier.

Where the connections actually bite

The genuinely valuable knowledge is where stages interact, because that is where symptoms appear in one subsystem and causes live in another:

  • Class loading → JIT. Loading a class that adds a second implementer invalidates every compilation that assumed one. A plugin loaded at hour six can cost throughput permanently.
  • JIT → GC. Escape analysis removes allocations entirely; when a refactor breaks it, allocation rate triples with no new new in the diff.
  • GC → latency → safepoints. A "5 ms GC pause" can be a 400 ms stall, because the pause is bounded by the slowest thread's time to reach a safepoint.
  • Class loading → native memory. A leaked loader pins every class it defined in Metaspace — invisible on every heap dashboard, fatal to the container.
  • JIT → concurrency. A missing volatile can be invisible under the interpreter and appear the moment C2 hoists a read out of a loop. The compiler revealed the race; it did not create it.

Interview drill · the whole machine Cross-cutting questions that span every stage

"Walk me through everything that happens when I run java MyApp." — the classic opener.

Structure it as launch → first instruction → steady state, and keep each step to one sentence. Interviewers are testing organisation, not trivia.

  1. The launcher creates the VM: reserves the heap, initialises the memory subsystems, starts the GC and compiler threads, and creates the main thread.
  2. The Bootstrap loader initialises the core JDK classes; then the Application loader is asked for MyApp, delegating parent-first up the chain.
  3. MyApp is loaded (bytes parsed into an InstanceKlass in Metaspace), linked (verified, static slots prepared to zero defaults, references resolved lazily) and initialized (<clinit> runs under a class lock).
  4. main() begins executing in the interpreter at Tier 0, one frame on the main thread's stack. Every class it touches repeats step 3 on first active use — this dominates startup, more than GC or JIT.
  5. Objects are allocated in Eden; when Eden fills, a young collection copies survivors and ages them; long-lived objects are promoted to the old generation.
  6. Invocation and back-edge counters accumulate; hot methods are queued for C1 (Tier 3), which runs fast and keeps profiling, then C2 (Tier 4), which uses that profile to inline, devirtualize, unroll and vectorize.
  7. C2's speculations are guarded; if one breaks — a new class loaded, an unexpected type — the method deoptimizes back to the interpreter at a safepoint and is recompiled with a better profile.
  8. Steady state: nearly everything hot is Tier 4 native code in the code cache, GC is periodic and mostly young, and class loading has largely stopped.

Then offer a hook: "I can go deeper on any of those — verification, the tier ladder, or how deoptimization reconstructs a frame." That turns a monologue into a conversation and lets you steer toward what you know best.

Why does the JVM's performance change over time, and what does that mean for how you measure it?

Because three things are still converging after the process starts: classes are still being loaded and initialised; methods are still being promoted up the tier ladder; and the GC has not yet reached a steady live set, so its cycle time is not representative.

What follows for measurement:

  • Discard warm-up. A benchmark without warm-up iterations measures the compiler. Use JMH, which does this by construction — and use Blackholes, because otherwise the optimizer deletes the work you are timing.
  • Measure for long enough that the GC has run many cycles, or you are measuring the interval before the first collection.
  • In production, expect the first minute after deploy to be unrepresentative, and either warm instances before they take traffic or exclude that window from alerting.
  • Report percentiles, not averages. GC pauses and deoptimizations live entirely in the tail, and an average hides exactly the thing you are trying to see.
Scenario · "Our Java service is slow." That is the entire ticket. How do you proceed?

Refuse to guess, and make the first move measurement rather than tuning. A defensible order:

  1. Define "slow". Throughput or latency? Average or tail? Always, or since a specific change? A p99 problem and a throughput problem have almost disjoint causes.
  2. Rule out the non-JVM world first. Most "JVM performance problems" are a database query, an N+1, a downstream timeout, a thread pool sized wrongly, or CPU throttling in the container. Check those before touching a flag.
  3. Look at the whole process, not the heap. CPU, RSS versus limit, thread count, safepoint stop time.
  4. Profile. A CPU profile (async-profiler, JFR) tells you where time goes; an allocation profile tells you where garbage comes from. This step answers the question far more often than any flag does.
  5. Then the JVM subsystems, using the symptom to pick one:
    • Slow only after deploy → warm-up / class loading (Stages 03, 05).
    • Erratic and bimodal → deoptimization churn (Stage 07).
    • Sudden permanent collapse → code cache full (Stage 05).
    • Tail-latency spikes → GC pauses or time-to-safepoint (Stages 07, 09).
    • Steady degradation over days → retention leak (Stages 08, 09).
    • Killed by the kernel with a calm heap → off-heap growth (Stage 08).
  6. Change one thing, measure, keep or revert. Every flag you keep is a decision someone must understand later.

The sentence that demonstrates seniority: "I would want the data to exist before the next incident — continuous JFR, GC logs with rotation, safepoint logging, and code-cache and Metaspace on the dashboard alongside heap. Most of these questions are trivial with the data and nearly unanswerable without it."

Scenario · Design the JVM configuration for a latency-sensitive API service in a 4-core, 8 GB container. Justify every flag.

Start with as little as possible, and be able to defend each line.

  • -XX:MaxRAMPercentage=70 — not a fixed -Xmx, so the heap scales with the container and leaves headroom for Metaspace, code cache, ~200 MB of thread stacks and any direct buffers. Sizing -Xmx to the container limit is how pods get OOM-killed.
  • -XX:+UseG1GC (explicit, even though it is the default) — pause-target-driven and well understood operationally. Consider ZGC instead if measurement shows G1's pauses are the p99 problem; on a heap this small, G1 usually suffices.
  • -XX:MaxMetaspaceSize=256m — so a ClassLoader leak fails fast and diagnosably instead of consuming the container silently.
  • -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps on a volume that survives restarts. Costs nothing until it saves an investigation.
  • -XX:StartFlightRecording=disk=true,maxsize=512m,settings=profile — continuous JFR so the data exists when something happens. Low single-digit percent overhead.
  • -Xlog:gc*,safepoint:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m — GC and safepoint logging, because the difference between them is the diagnosis for most tail-latency questions.
  • Warm-up on startup — a readiness probe that only passes after synthetic traffic has exercised the main endpoints, so a cold instance never takes production load.

What you deliberately leave out, and why: no hand-tuned generation sizes (G1 sizes adaptively and does it better than a guess); no MaxGCPauseMillis until you have evidence, since lowering it trades throughput for a target that may not be met anyway; no threshold tuning; no -XX:+AggressiveOpts-style grab-bags. Every flag is a hypothesis. Ship only the ones you have tested, plus the observability ones — those pay for themselves.

Scenario · A junior developer asks: "Should I worry about creating objects in a loop?" Give the honest answer.

Usually no, and the reason is worth teaching. Allocation in Java is a pointer bump in a thread-local allocation buffer — a handful of instructions, no lock. And an object that dies before the next young collection costs the collector nothing at all, because copying collectors pay for survivors, not for garbage. On top of that, escape analysis may delete the allocation entirely.

When it does matter:

  • Allocation rate in the hundreds of MB/s or more — the young collections themselves become frequent enough to matter, and survivors start being promoted prematurely.
  • Boxing in hot data structures — Long[] versus long[] is a 3–4× footprint difference plus catastrophic cache locality.
  • Objects that escape the loop and accumulate — that is not allocation cost, it is retention, and retention is the expensive thing.
  • Sub-millisecond latency requirements, where even short young pauses are unacceptable and allocation-free hot paths are a genuine design constraint.

What to tell them to do: write the clear version; if it turns out to be hot, measure with an allocation profiler and fix the specific site. Object pooling to "help the GC" is usually counterproductive — it converts cheap young garbage into long-lived objects the old generation must trace repeatedly, and adds a lifetime-management bug surface for free.

Why do microbenchmarks without warm-up iterations produce completely misleading numbers?
During the first few seconds of execution (Phase 2), the JVM is actively compiling methods, collecting profiling data, competing for CPU cores with application code, and triggering speculative deoptimizations. Measuring execution time during this warm-up phase benchmarks the JIT compiler itself rather than steady-state application performance. Harnesses like JMH (Java Microbenchmark Harness) explicitly discard initial warm-up iterations to measure only settled Tier 4 steady-state throughput.
Common Interview Trap "The JVM is a black box — you just tune the flags." Almost every JVM performance problem is a code or architecture problem visible through JVM telemetry. Flags move a workload along a trade-off curve; they rarely move the curve. A retention leak, a megamorphic hot call site, an unbounded cache, an allocation-heavy inner loop, a thread pool sized for a different machine — the JVM reports these faithfully, and no flag fixes any of them. Knowing the internals is what lets you read the report.
