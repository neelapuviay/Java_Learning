STAGE 09

Garbage Collection — Reachability Tracing, Generations & Modern Collectors

automatic memory management

Java memory management relies on two core principles: Root Reachability Tracing (which completely eliminates circular reference leaks) and the Weak Generational Hypothesis (most objects die young). Explore how modern collectors trade pause latency against throughput across different heap architectures.

Mental model — hold this picture

A library does not track which books are rubbish. Instead, once in a while, a librarian starts from the front desk records — the loans, the reading-room lists, the reservation slips — and follows every reference: this record points to a shelf, that book cites another book, and so on. Everything reached gets a chalk mark. Everything unmarked is, by definition, unreachable by any reader, and the shelves it occupies are simply declared empty.

Two consequences fall straight out of this, and both are interview answers. First, a pile of books that only cite each other, with no front-desk record pointing in, is unreachable — which is why Java has no reference-counting cycle problem. Second, the librarian's work is proportional to what survives, not to what is thrown away. Creating and discarding a million short-lived objects is nearly free; keeping a million alive is what costs.

And the observation that shapes every modern collector: most books are returned within the hour. So do not search the whole library each time — check the returns trolley by the door. That is the weak generational hypothesis, and it is why the heap has a young generation at all.

Reachability, not "unused"

The GC does not find objects you have finished with. It finds objects that cannot be reached from a GC root — thread stacks and their locals, static fields, JNI references, and a few VM-internal structures. Starting from those roots it walks every reference, and anything it never arrives at is garbage. Object E pointing at F and F pointing back at E changes nothing: if no root reaches either, both are collected. Play 9.1 above and watch exactly that happen.

The corollary is the one that matters in production: a "memory leak" in Java is always unintended reachability. The collector is not failing; you can still reach the object, so it is still live by definition.

The four primitive operations

Every collector is built from some combination of four steps:

  • Mark — starting from the application's roots, all linked memory blocks that can be reached are "painted".
  • Sweep — all the non-live objects are cleared from the heap.
  • Compact — surviving objects are brought closer together, defragmenting the heap by relocating them.
  • Copy — live objects are moved into a "to" space, leaving the old space entirely empty and reusable in one step.

Combining them gives the familiar families: Mark/Sweep/Compact, Copy (used for the young generation), and Mark/Compact. The crucial economic property of a copying collector is that its cost is proportional to the survivors, not to the size of the space collected — which is what makes young collections cheap when most objects die.

Generations, and why the heap is shaped this way

The design rests on two empirical claims: most objects die young, and few references from older to younger objects exist. Both hold for the overwhelming majority of real programs.

New objects are allocated in Eden. When Eden fills, a quick young collection runs: survivors are copied into a Survivor space, and objects that have survived enough collections are promoted ("tenured") into the Old Generation. The old generation holds longer-lived objects; it needs collecting far less often, but takes much longer when it does. Step 9.2 above and watch the ages increment.

The second claim is what makes it fast to implement. To collect only the young generation, the GC must know about old→young references without scanning the whole old generation — so the JVM maintains a card table (and, in G1, remembered sets), updated by a tiny write barrier the JIT inserts on every reference store. That barrier is a real, permanent tax on every Java program, and it is the price of never scanning the whole heap for a young collection.

Allocation rate: the number to look at first

Allocation rate, in MB/sec, tells you how quickly memory is being consumed. A high value indicates a lot of objects are being created, which means a lot of cleanups will be needed — more frequent young collections, more copying, more promotion pressure. It is often a more actionable number than pause time, because it points straight at code: a hot loop building strings, boxing primitives, or creating throwaway collections.

For sizing, a good starting guideline is a heap (-Xmx) of 2.5 to 5 times the average live set — the amount of data that genuinely survives collections. Below that range the collector runs constantly; far above it, you are paying for memory that only makes full collections slower.

Pause time, throughput, and why they fight

Most collectors cause GC-related pauses proportional to the size of their heaps — as a rough historical rule of thumb, on the order of a second of pause per gigabyte of live objects for a stop-the-world compacting collector. That single fact is why heap size and latency are not independent choices: a bigger heap buys throughput and costs tail latency.

The three shapes of collector:

  • Stop-the-world — halts application execution entirely while collecting. Simple, efficient per unit of work, and unbounded in pause as the heap grows.
  • Incremental — breaks the work into smaller chunks with gaps that permit the application to run.
  • Concurrent — performs collection while application threads continue running. It costs throughput (barriers, and CPU spent collecting alongside your work) and buys dramatically shorter pauses.

Modern concurrent collectors — C4, ZGC, Shenandoah — bring pause times down to units of milliseconds or lower, and importantly, pauses that no longer scale with heap size. The distinction to be precise about is "mostly concurrent" versus fully concurrent: a mostly-concurrent collector still has a stop-the-world fallback (typically for compaction) that it resorts to under pressure, and that fallback is exactly the pause that ruins your p99 at the worst moment.

Why tuning is genuinely hard

Be honest about this in an interview, because it is true: garbage collection tuning for most collectors is hard to get right, even when you understand your application's characteristics. Similar parameter sets produce very different outcomes on different workloads, and there is no "one size fits all" answer. Postponing tuning does not avoid pauses; it only delays when you meet them.

Which is why the practical advice is boring and correct: change the collector before you change its knobs. Picking G1 or ZGC to match your latency requirement solves more problems than a dozen tuning flags, and each flag you add is a decision your successor will have to understand.

minor / young GC
Collects the young generation only. Frequent, short, copying, always stop-the-world. Cost scales with survivors, not with garbage.
major GC
Collects the old generation. Rare, much longer, mark-sweep(-compact).
full GC
Everything — young + old + metaspace-related work — usually with a long stop-the-world pause, and often a sign of trouble: heap genuinely too small, promotion failure, or an explicit System.gc().
mixed GC (G1)
A young collection that also evacuates some old regions, chosen by which regions hold the most garbage. This is how G1 avoids ever needing a full collection in the healthy case.
Serial GC
One thread, stop-the-world. Correct for tiny heaps, single-core containers, and short-lived CLI processes. -XX:+UseSerialGC
Parallel GC
Multi-threaded stop-the-world. Best raw throughput if you genuinely do not care about pauses — batch jobs and analytics. -XX:+UseParallelGC
G1 GC
Default since Java 9. Region-based, mostly concurrent marking, evacuating collections chosen to meet a pause-time target (-XX:MaxGCPauseMillis, default 200 ms). The right default for most services.
ZGC / Shenandoah
Concurrent compaction using load/store barriers. Sub-millisecond pauses that do not grow with heap size — viable from small heaps to terabytes. Costs some throughput. -XX:+UseZGC (add -XX:+ZGenerational on JDK 21+).
System.gc()
A suggestion, not a command, and almost always a mistake — it typically forces a full collection at the worst possible moment. Disable it with -XX:+DisableExplicitGC if a library insists on calling it.
finalize()
Deprecated and removed. It made collection slower, was never guaranteed to run, and could resurrect objects. Use try-with-resources, and Cleaner only as a last-resort safety net.

Interview drill · stage 09 Questions they actually ask about garbage collection

How does the JVM know an object is garbage?

Reachability from GC roots, not reference counting. The collector starts from thread stacks (locals and parameters of every frame), static fields, JNI global references and a handful of VM-internal roots, and traces every reference transitively. Anything not reached is garbage.

The follow-up they are angling for: "Why not reference counting?" Because reference counting cannot reclaim cycles — two objects referring to each other keep each other's counts above zero forever. It also imposes a cost on every single pointer write, which is a bad trade in a language that writes pointers constantly. Tracing collects cycles for free, and pays only when it runs.

Explain the generational hypothesis and why it is worth designing a heap around.

Two observations: most objects die young, and few references point from older objects to younger ones.

The first means that if you collect only the recently-allocated region, you will find that almost everything in it is garbage — and because young collection is a copying collector, its cost is proportional to what survives. Collecting a nearly-empty Eden is nearly free regardless of how many objects passed through it.

The second is what makes it implementable: to collect the young generation independently you must find old→young references, and there are few enough of them that tracking them with a write barrier and a card table is cheaper than scanning the old generation.

The practical takeaway worth stating: allocating short-lived objects in Java is genuinely cheap — a pointer bump in a thread-local allocation buffer, and a death that costs nothing. Object pooling to "help the GC" usually makes things worse, because it converts cheap young garbage into expensive long-lived objects that the old generation must repeatedly trace.

Which collector would you choose, and why?

Answer from the requirement, never from a favourite:

  • Latency-sensitive service, large heap (interactive APIs, trading, gaming) → ZGC or Shenandoah. Sub-millisecond pauses independent of heap size, at some throughput cost.
  • General-purpose service → G1, the default. Pause-target-driven, good balance, and the one your operations tooling understands best.
  • Batch / analytics where only total time matters → Parallel GC. Highest raw throughput; pauses are irrelevant if nobody is waiting.
  • Tiny container, single core, short-lived process → Serial GC. Less overhead than coordinating parallel threads, and the JVM often selects it automatically on constrained hardware.

Then add the honest caveat: measure. Pick the collector that matches the requirement, run your real workload, and look at total safepoint stop time and p99 latency rather than at GC-log averages.

Scenario · p99 latency is 800 ms with 40 ms average GC pauses on a 32 GB heap. The team wants to cut -Xmx to 8 GB "so GC has less to do." Right call?

Probably backwards, and the reasoning matters more than the answer. Shrinking the heap does shorten each individual pause — pauses scale with heap and live-set size — but it also makes collections far more frequent, and if the live set does not fit comfortably, you get promotion failures and full collections, which are dramatically worse than what you started with.

Diagnose before changing anything:

  • What is the live set after a full collection? Guideline: heap of 2.5–5× the live set. If the live set is 6 GB, an 8 GB heap is already too tight.
  • What is the allocation rate (MB/s)? A very high rate means the fix is in the code — reduce garbage — not in the flags.
  • Is the 800 ms actually GC? Check total safepoint stop time (-Xlog:safepoint), not just collection duration. A 40 ms collection preceded by a 700 ms time-to-safepoint is a Stage 07 problem wearing a GC costume.
  • Are pauses young or full? Frequent full collections mean a retention problem; long young collections mean a high survival rate, and the fix is usually a larger young generation, not a smaller heap.

What actually fixes it, in order:

  • Change collector. On a 32 GB heap with a latency requirement, ZGC or Shenandoah is the answer — concurrent compaction makes pause time independent of heap size. This is usually a one-flag change that beats weeks of G1 tuning.
  • Reduce allocation rate in the top offenders found by an allocation profiler. Less garbage beats faster collection.
  • Fix retention. A live set that grew unintentionally is the root cause behind a surprising share of "GC problems".
  • Only then adjust G1's MaxGCPauseMillis — and understand it is a target the collector trades throughput to meet, not a guarantee.
Scenario · GC logs show young collections every 2 seconds, each promoting a large volume to old gen, and a full GC every 20 minutes that takes 6 seconds. Diagnose.

The pattern names itself: premature promotion. Objects that ought to die young are surviving long enough to be tenured, so the old generation fills with short-lived data, and eventually a full collection has to clean it up.

Why it happens:

  • The young generation is too small relative to the allocation rate. Objects are evacuated before they have had time to die, so they are promoted on age rather than on merit. This is the most common cause by a wide margin.
  • Survivor spaces are too small, so survivors overflow directly into old gen regardless of age.
  • Objects genuinely live longer than one collection cycle — a request whose working set survives a couple of collections under load. Same fix: give the young generation more room so a cycle spans more time.
  • Very large objects allocated directly into old gen (humongous allocations in G1: anything over half a region). A stream of large byte arrays or buffers does this.

Investigate: -Xlog:gc*,gc+age=trace shows the age distribution of survivors — if most objects are promoted at the maximum tenuring threshold, the young gen is too small; if they are promoted because survivor space overflowed, you will see the survivor overflow directly.

Fixes: increase the young generation (raise -Xmn, or for G1 raise G1NewSizePercent rather than pinning a fixed size, since G1 sizes adaptively); increase survivor space (-XX:SurvivorRatio); reduce allocation rate at the source; and for humongous allocations either reduce object size or raise G1HeapRegionSize.

The mental model to state: "Objects should die in the young generation. Every object promoted is a future old-generation collection's problem. Premature promotion converts cheap garbage into expensive garbage."

Scenario · A developer adds System.gc() at the end of each batch job "to keep memory clean." What do you tell them?

Explain the mechanism rather than just saying no. System.gc() is a suggestion; on HotSpot it normally triggers a full, stop-the-world collection of the entire heap plus Metaspace work — the single most expensive thing the collector can do — at a moment chosen by the calendar rather than by memory pressure.

Why it does not do what they think:

  • The GC already runs when memory pressure requires it, and it has far better information about when that is than a line of application code does.
  • It does not reduce the live set. If memory is being retained, a full collection frees nothing — it just proves the retention is real, expensively.
  • It disrupts the generational structure: an explicit full GC promotes surviving young objects into old gen, actively making the next collections worse.
  • Returning memory to the OS is a separate concern with its own mechanisms (-XX:+ShrinkHeapInPlace, G1 periodic collection, ZGC uncommit) that do not require a full pause.

Where it is defensible: at the end of a batch phase in a process that will now idle for a long time, on a JVM with heap uncommitting enabled, where the goal is explicitly to return RSS to the host — a rare and deliberate case. And in benchmark harnesses between iterations, for isolation.

What to do instead: find out what is actually being retained (heap dump, dominator tree). If the real goal is bounded memory, bound the cache. If a third-party library calls System.gc() and you cannot change it — DirectByteBuffer cleanup historically did — -XX:+DisableExplicitGC turns the call into a no-op, or -XX:+ExplicitGCInvokesConcurrent makes it concurrent rather than a full pause.

Common Interview Trap "Java can't have memory leaks, the GC handles it." Java leaks constantly — through unintended reachability. The classic four: a static collection that only ever grows; listeners and callbacks registered and never removed; ThreadLocal values on a pooled thread that outlives the request; and ClassLoader leaks where one lingering reference keeps an entire redeployed application's classes alive in Metaspace. All four are "working as designed" — the GC correctly refuses to collect objects you can still reach.
