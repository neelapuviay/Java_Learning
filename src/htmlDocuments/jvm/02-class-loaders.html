STAGE 02

The Class Loader Hierarchy — Java 8 vs. The Modular JDK (Java 9+)

architecture, security & JPMS

Before any bytecode can execute, a ClassLoader must locate its binary data and define it as a live type in memory. In Java 9, Project Jigsaw overhauled the classic 3-tier hierarchy: the monolithic rt.jar was dismantled into modular runtime images (jimage), the Extension ClassLoader was eliminated, and the Platform ClassLoader was introduced to enforce least privilege.

Mental model — hold this picture

Think of a large company where any expense must be approved. You submit a request to your immediate manager. Your manager does not decide — they pass it to their manager, who passes it to the director, who passes it to the CFO. The CFO answers first. Only if the CFO says "not my budget" does the answer come back down, one level at a time, until someone can handle it.

That is parent-first delegation, and it exists for exactly one reason: so a junior employee cannot approve their own expenses. Translate it back — if a random JAR on your classpath could define java.lang.String, every security guarantee in the JVM would evaporate. The Bootstrap loader answers first, always, so the real String always wins.

The second half of the picture: a class's identity in the JVM is not its name. It is name + the loader that defined it. Two loaders reading the same bytes produce two genuinely different types that cannot be assigned to each other. Almost every weird class-loading bug you will ever debug is that sentence biting you.

The class loader is where the JVM begins, and where all of the verification processes begin. Nothing else can happen first: before a single instruction executes, some loader must find bytes, hand them to the VM, and let the VM define a type from them. This is also the JVM's first security boundary — it is what stops arbitrary bytecode from simply being executed.

The three loaders, and what each one owns

Bootstrap is written in native C++ inside HotSpot itself. It is not a Java object, which is why String.class.getClassLoader() returns null — null is the API's sentinel for "the bootstrap loader". It loads java.base: Object, String, Integer, the primitives' box types, the core of the language.

Platform (called Extension before Java 9) loads the rest of the JDK's own modules — java.sql, java.xml, java.logging, crypto providers. It is a real Java object, so it has a non-null loader reference.

Application (also called the system loader) loads your code and your dependencies from the classpath or module path. This is the loader almost every class you write will report.

Why the Extension loader had to die

In Java 8, dropping a JAR into $JAVA_HOME/lib/ext made it load automatically, with higher priority than your application's own dependencies, with no version information, on every application on that machine. A single stray JAR could silently override a library for every process. That is "JAR hell" in its most concentrated form. Java 9 deleted lib/ext outright and replaced the implicit privilege with explicit module boundaries under the Platform loader.

Delegation is a default, not a law

Parent-first is what ClassLoader.loadClass does by default, but it is ordinary Java code you can override. Application servers routinely do: Tomcat's web-app loader is deliberately parent-last for most packages, so that a WAR bundling its own Jackson gets its Jackson rather than the container's. OSGi goes further and resolves per-package against a wiring graph. Knowing that delegation is policy rather than physics is what separates a memorised answer from an understood one.

The three phases every loader runs through

Whatever loader wins the search, the work it triggers is always the same triple, and the JVM specification fixes their order: Loading (find the bytes, define the type in Metaspace), Linking (verify, prepare static storage, resolve symbolic references), and Initialization (run <clinit>). Stage 03 walks each of them frame by frame.

class identity
Fully-qualified name + defining loader. Same bytes, two loaders → two incompatible types → a ClassCastException whose message looks like it is casting a class to itself.
defining vs initiating
The initiating loader is the one you asked. The defining loader is the one that actually called defineClass. getClassLoader() reports the defining loader — which is why your classes often report a parent you never touched.
ClassNotFoundException
Thrown by an explicit lookup — Class.forName, loadClass. It is a checked exception: someone asked for a name and it was not found.
NoClassDefFoundError
Thrown by the JVM itself when linking. The class was present at compile time but is missing (or failed to initialise) now. A repeated NoClassDefFoundError on a class that does exist usually means its <clinit> threw the first time — look for the earlier ExceptionInInitializerError.
unloading
A class is unloadable only when its entire defining loader becomes unreachable, along with every instance and every Class object. One live reference pins the whole loader — the mechanism behind every Metaspace leak.
TCCL
The Thread Context ClassLoader (Thread.currentThread().getContextClassLoader()) is the escape hatch for the SPI inversion problem: JDK code loaded by Bootstrap needs to instantiate your implementation, which Bootstrap cannot see. JDBC, JAXP and ServiceLoader all rely on it.

Interview drill · stage 02 Questions they actually ask about class loading

Why was the Extension ClassLoader removed in Java 9+?
In Java 8, dropping arbitrary JAR files into <JAVA_HOME>/lib/ext caused implicit, unversioned global classpath pollution (commonly referred to as JAR Hell). Any JAR in lib/ext was automatically loaded by the Extension ClassLoader with high privileges, frequently overriding application-level dependencies and causing silent classpath collisions. In Java 9, lib/ext was completely deleted; standard platform components were divided into modular descriptors with explicit boundaries under the Platform ClassLoader.
Why does String.class.getClassLoader() return null?
The Bootstrap ClassLoader is written in native C++ inside the HotSpot VM kernel — it is not a Java object instance. In the Java reflection API, null is the standard sentinel value representing the Bootstrap ClassLoader.
What exactly is the "parent delegation model", and name a case where breaking it is correct.

On a request, a loader first asks its parent, recursively up to Bootstrap, and only searches its own sources if every ancestor failed. Two guarantees fall out of that: uniqueness (a core class is defined exactly once, by the highest loader that can see it) and safety (user code cannot shadow java.*).

Correct places to break it:

  • Servlet containers — Tomcat's web-app loader is parent-last for non-java.* packages so each WAR keeps its own dependency versions and can be redeployed independently.
  • OSGi / module systems — per-package wiring rather than a linear chain, so two bundles can legitimately use two versions of the same library.
  • Plugin sandboxes — an isolated child loader per plugin so plugins cannot see each other, and so unloading a plugin actually frees its classes.

What you may never do is shadow java.* — the VM rejects that outright with SecurityException: Prohibited package name, regardless of your delegation policy.

Difference between Class.forName("X") and loader.loadClass("X")?

Class.forName(name) initialises the class; loadClass(name) does not. That single difference is the whole question.

Class.forName loads, links and runs <clinit>, using the caller's own loader. loadClass stops after loading — static blocks have not run, static fields still hold their zero defaults.

The historical proof is the old JDBC idiom: Class.forName("com.mysql.jdbc.Driver") worked only because the driver registers itself with DriverManager inside a static block. Swap in loadClass and no driver ever registers. (Since JDBC 4 ServiceLoader makes the call unnecessary entirely.)

The three-argument form Class.forName(name, initialize, loader) lets you pick both explicitly — useful when you want reflection without triggering side effects.

Scenario · Production throws ClassCastException: com.acme.Order cannot be cast to com.acme.Order. The same class name on both sides. How is that possible and how do you fix it?

This is the canonical proof that class identity is name + defining loader. Two different loaders each defined com.acme.Order, producing two runtime types that are unrelated as far as the VM is concerned. The message looks absurd only because getName() prints the same string for both.

Diagnose: print the loaders, not the names.

  • System.out.println(obj.getClass().getClassLoader() + " vs " + Order.class.getClassLoader());
  • obj.getClass().getProtectionDomain().getCodeSource() tells you which JAR each came from.
  • Run with -Xlog:class+load=info (Java 9+; -verbose:class on 8) and grep for the class name — you will see it defined twice, from two sources.

Typical causes: the same JAR present both in the container's lib/ and inside the WAR; a shared interface accidentally bundled in the plugin instead of only in the parent; a hot-redeploy where an old loader's objects leaked into a cache the new loader reads; a custom loader that defines instead of delegating.

Fix: make the shared type live in exactly one loader — normally the common parent. The plugin/WAR must depend on the API JAR as provided, never bundle it. If you genuinely need two versions, then the two sides must communicate through something loader-neutral (an interface from the shared parent, or serialised data), never by casting objects across the boundary.

Scenario · An app server dies with OutOfMemoryError: Metaspace after roughly the 8th hot redeploy, while the heap graph stays flat. Walk through it.

This is a ClassLoader leak, and the flat heap graph is the diagnostic signature: class metadata lives in Metaspace, which is native memory outside -Xmx, so heap dashboards show nothing.

The mechanism: each redeploy creates a fresh web-app loader that defines every one of your application's classes again. The old loader's Metaspace is freed only when the whole loader becomes unreachable. A single surviving reference from outside the application pins the loader, every class it defined, and every static field those classes hold. Eight redeploys, eight full copies.

The usual culprits — all of them references held by something that outlives the deployment:

  • ThreadLocals on container-pooled threads — the thread survives the redeploy and its ThreadLocal value pins your class, which pins your loader. The number-one cause in practice.
  • Threads your app started and never stopped — a running thread is a GC root, and its context loader is yours.
  • JDBC drivers registered in DriverManager, which is loaded by Bootstrap and therefore immortal.
  • Shutdown hooks, JMX MBeans, java.util.logging handlers, security providers, URL stream handlers — all JDK-level static registries.
  • Caches keyed by Class objects in a library sitting in the parent loader.

How to prove it: take a heap dump, find all instances of WebappClassLoader, and ask your tool for the path to GC root of the oldest one. That path is the bug — it names the exact static field holding it.

Mitigations: a ServletContextListener that deregisters drivers, stops threads and clears ThreadLocals on shutdown; set -XX:MaxMetaspaceSize so a leak fails fast and visibly instead of consuming the machine; and in containers, prefer restarting the process over hot redeploy — the leak stops being a problem when the process is the deployment unit.

Scenario · A library works standalone but throws ServiceConfigurationError / "provider not found" once packaged into a fat JAR inside a framework. Why?

Two independent causes, and a good answer separates them.

1. Merged META-INF/services files. Fat-JAR builders concatenate archives; if two dependencies both ship META-INF/services/javax.xml.parsers.DocumentBuilderFactory, a naïve build keeps only the last one and the others vanish. The fix is a shading plugin with a ServicesResourceTransformer (Maven Shade) or the equivalent merge strategy in Gradle — it appends the files instead of overwriting.

2. The wrong loader is doing the lookup. ServiceLoader.load(Foo.class) defaults to the thread context class loader. If the framework runs your code on a pooled thread whose TCCL is the container's loader rather than your application's, your provider file is invisible. Fix by passing the loader explicitly — ServiceLoader.load(Foo.class, Foo.class.getClassLoader()) — which is the correct habit in library code regardless.

The underlying idea worth naming: this is the SPI inversion problem. Code high in the loader hierarchy needs to instantiate implementations that live low in it, and delegation only goes upward. TCCL is the deliberate escape hatch built for exactly that.

Common Interview Trap "The class loader loads all the classes when the application starts." Nothing is eagerly loaded. Loading is triggered lazily, by first active use. The JVM does not scan your classpath at boot. A class is built in memory only when something actually needs it — the first new, the first static method call, the first non-constant static field access, or a reflective Class.forName. This is why a typo in a class name in a rarely-used branch can survive months of production traffic and then fail at 3 a.m.
