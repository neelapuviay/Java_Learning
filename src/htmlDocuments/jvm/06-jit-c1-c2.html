STAGE 06

JIT Compilers — C1 (Client), C2 (Server) & The Optimization Engine

tier 3 & tier 4 native code

HotSpot contains two distinct JIT compilers: C1 (fast compilation, light optimizations, instruments profiling counters) and C2 (heavy SSA graph optimizations, aggressive speculations, peak native speed). Explore each interactive optimization model below to see how bytecode transforms into high-performance machine code.

Mental model — hold this picture

Two translators are available for a long meeting. The first is fast and literal: she starts translating within seconds, sentence by sentence, and she is good enough immediately. The second is a specialist: he insists on listening to twenty minutes of the discussion first, and only then produces a translation that is dramatically better — because he now knows the jargon, the speakers' habits, and which topics actually matter.

You do not choose between them. You use both: the fast translator covers the opening while the specialist listens, and then you switch. That is C1 then C2, and the twenty minutes of listening is the profile.

The third option — AOT — is a translator who prepared from the agenda alone, before anyone spoke. Ready instantly, never wrong, and permanently unable to exploit anything that only became apparent once the meeting started. That trade is the entire AOT-versus-JIT argument, and neither side wins universally.

AOT compiles your Java to native code for a specific platform before the program ever runs — GraalVM Native Image is the mainstream implementation. The advantage is immediate and real: the application starts at full speed with the native code created ahead, with no warm-up and a much smaller memory footprint. For a CLI tool, a serverless function, or anything that lives for two seconds, this is simply the right answer.

JIT takes the opposite bet. The JVM executes bytecode, identifies frequently-used methods — the hotspots — and compiles them into native code using two compilers: C1 (fast compile, low optimization) and C2 (slow compile, high optimization). The disadvantage is unavoidable: at startup the virtual machine executes the slow bytecode during a "warm-up time" until it identifies the hotspots and reaches fully optimized native code.

The question that makes the difference click

If all the code is compiled before running it, how could AOT possibly perform worse than JIT-compiled code? Here lies the true strength of the JIT approach.

An ahead-of-time compiler must produce code that is correct for every possible execution. A JIT only has to produce code that is correct for the execution actually happening — and it can install a guard so that if reality changes, the code is thrown away rather than being wrong. That asymmetry lets the JIT do things AOT structurally cannot:

  • Devirtualize and inline through interfaces. The profile says this call site has only ever seen ArrayList. The JIT compiles a direct call, guarded by a type check. AOT must emit a full virtual dispatch, because a different implementation might exist.
  • Delete code that is never reached. A branch never taken in practice becomes an uncommon trap, not a branch. AOT must compile both sides.
  • Exploit the actual CPU. The JIT knows whether this machine has AVX-512 or NEON. AOT must target a baseline that runs everywhere.
  • Optimize across configuration. Feature flags, dependency-injected implementations and reflective wiring resolve to constants at runtime; the JIT constant-folds through them.

These speculative optimizations are not marginal. Vendors have measured them producing up to 50% performance gains over the same code compiled without a profile. The price is that every speculation needs a safety net — which is Stage 07.

choose AOT when
Process lifetime is short (CLI, lambda, batch job); memory is tight; startup latency is the product requirement; you can accept closed-world assumptions and limited reflection.
choose JIT when
The process runs for minutes to months; peak throughput matters more than the first second; you rely on dynamic loading, proxies, agents, or heavy reflection.
the honest middle
Long-running services: JIT wins on steady-state throughput. Short-lived processes: AOT wins outright. Everything else is a measurement question, not a doctrine question.

Read this alongside 5.2 and 5.3 What C1 and C2 each actually do

Both compilers turn bytecode into machine code. The difference is how much analysis they are willing to pay for, and the station lists above are literally their pipelines.

C1 — optimize for compile speed

C1 builds a high-level IR, does a modest set of local optimizations (local value numbering, simple inlining of small methods, basic constant propagation), lowers to a low-level IR, and allocates registers with linear scan — an algorithm chosen precisely because it is fast, not because it is optimal. Compilation takes microseconds to low milliseconds. The result is typically 5–10× faster than interpretation. When running at Tier 3 it additionally emits profiling counters into the generated code, so the machine keeps learning while running faster.

C2 — optimize for the code that comes out

C2 parses into a sea-of-nodes graph in which data dependencies and control dependencies are represented uniformly and instructions are not committed to an order. That freedom is the point: global value numbering can collapse identical computations anywhere in the method; global code motion can sink work into the branch that needs it and hoist loop-invariant work out; and the scheduler only fixes an order at the very end, once every optimization has had its say. Register allocation uses graph colouring — much slower than linear scan, and much better.

C2's aggressive passes — speculative inlining, escape analysis, loop transformations, vectorization — are all downstream of one thing: the profile. And every speculation it makes is recorded in a dependency map and a deoptimization map at each safepoint, so the assumption can be invalidated later.

The compilation itself never blocks your code

Look at panel 5.4. When a method crosses a threshold, a task is enqueued; background compiler threads do the work; the application thread continues at its current tier and picks up the new code only once it is installed. Nothing stops the world for compilation. The visible cost is indirect — compiler threads consume CPU, and a long queue delays promotion.

This also explains a common confusion: the same method can exist in several compiled forms at once — a Tier 3 version currently executing, a Tier 4 version being installed, and an older invalidated version still on some thread's stack until that frame returns.

Read this alongside the five engines Why inlining is the optimization that unlocks all the others

If you remember one thing from this stage: inlining is not primarily about avoiding call overhead. It is about widening the compiler's field of view. An optimizer can only reason about code it can see at once. Every method boundary is a wall. Inlining removes the wall, and everything else in this section becomes possible on the other side of it.

Concretely: once accumulate(a, b) is inlined into the loop, the compiler can see that its argument is loop-invariant, that its result feeds directly into the next iteration, that no reference escapes, and that the whole body is a single add. Now unrolling is legal, scalar replacement is legal, vectorization is legal. None of those analyses could cross the call.

① Inlining — and why it refuses

HotSpot inlines aggressively but not blindly. The usual refusals: the callee is too large (MaxInlineSize ~35 bytes for cold, FreqInlineSize ~325 bytes for hot methods), the call site is polymorphic beyond two types, inlining depth is exceeded, or the method is native or not yet compiled. -XX:+PrintInlining prints every decision and the reason for every refusal — this is the flag to reach for when a method is mysteriously slow.

Practical consequence: a huge method can be slower than the same logic split into small ones, because the huge one can never be inlined into its callers. "Extract method" is occasionally a performance optimization.

② Inline caches — monomorphic, bimorphic, megamorphic

At a virtual call site the JIT records which concrete types actually arrive. One type (monomorphic) is the best case: compile a direct call to that implementation guarded by a class check, then inline it. Two types (bimorphic) still works — an if/else of two guarded direct calls. Three or more (megamorphic) and the JIT gives up and emits a full vtable/itable dispatch, which is not just slower by itself but blocks inlining, and therefore blocks every optimization downstream.

This is why the shape of your abstraction has real performance consequences: an interface with one implementation in practice costs nothing, while a strategy interface with twelve implementations all flowing through one hot call site can cost a great deal. The fix is rarely "remove the interface" — it is to split the call site so each specialised path sees few types.

③ Loop unrolling

Every loop iteration pays a branch and a counter increment. Unrolling replicates the body N times and increments by N, amortising that tax and — more importantly — giving the scheduler a bigger straight-line block to reorder, and giving the vectorizer something to work with. The compiler must first prove the trip count and that the body has no cross-iteration dependency it cannot handle.

④ Escape analysis and scalar replacement

If the compiler can prove an object never escapes the compiling method — never stored to a field, never returned, never passed somewhere it might be retained — it can skip allocating it at all and keep its fields in registers as loose values. That is scalar replacement, and it is why the "always allocate objects and let the GC sort it out" advice is more often true than it sounds: the fastest garbage is the object that was never created. Related wins are lock elision (a lock on a non-escaping object is a no-op) and stack allocation where scalar replacement does not apply.

The catch, and it matters: escape analysis is fragile. Storing the object into a field, passing it to a non-inlined method, or a call site becoming megamorphic can all silently disable it. Performance that depends on escape analysis is performance that can vanish on a refactor — verify with -XX:+PrintEscapeAnalysis or by measuring allocation rate, never by assumption.

⑤ SIMD / superword vectorization

Modern CPUs can apply one instruction to 4, 8 or 16 values at once. C2's superword pass detects loops whose iterations are independent and rewrites them to use those wide registers. It requires a lot to line up — countable loop, unit stride, no aliasing, supported element type, alignment — which is why it is unreliable in hand-written code, and why the Vector API exists to express it explicitly instead of hoping the compiler notices.

Interview drill · stage 06 Questions they actually ask about the JIT

Explain C1 vs C2 to someone who has never heard of tiered compilation.

"Both compile bytecode to machine code. C1 is a sprinter, C2 is a marathon runner. C1 compiles in microseconds and produces code roughly 5–10× faster than interpreting — good enough, immediately. C2 spends milliseconds per method doing global analysis and produces code several times faster still, but only because it uses profiling data C1 collected while running."

"So the JVM uses them as a ladder: interpret to gather a first profile, promote to C1 to get fast quickly while gathering a richer profile, then promote to C2 for peak speed. You get low startup latency and high steady-state throughput, which neither compiler could deliver alone."

Why can the JIT produce faster code than a C++ compiler in some cases?

Not because it is a better compiler — it is not — but because it knows things no static compiler can know:

  • Runtime types. A virtual call whose profile shows one receiver becomes a direct, inlined call. In C++ the equivalent devirtualization requires whole-program analysis or link-time optimization, and even then a dynamically loaded library defeats it.
  • The actual CPU. Vector width, cache line size, instruction availability — all known exactly.
  • Actual values. Configuration read at startup becomes a compile-time constant, so branches on it disappear entirely.
  • The freedom to be wrong. A JIT can compile code that is invalid in general, guarded by a check, and recompile if the guard fails. A static compiler has no recompilation to fall back to.

Be honest about the other side too: C++ wins on memory layout control, no GC, no warm-up, no header overhead, and deterministic latency. The realistic claim is "competitive on throughput for long-running server workloads", not "faster than C++".

Scenario · You add a second implementation of an interface. One unrelated hot loop gets 3× slower. Explain.

You broke a monomorphic call site. Before the change, that call site had seen exactly one receiver type, so the JIT devirtualized it — direct call, guarded by a cheap class check, then inlined. Once a second implementation flows through it, the site becomes bimorphic or megamorphic and the JIT emits a real dispatch instead.

The 3× is not the dispatch cost itself, which is small. It is everything that inlining was enabling: with the callee body no longer visible, loop-invariant hoisting stops, escape analysis on objects crossing the call stops (so allocations reappear), constant folding through the callee stops, and vectorization stops. One wall reinstated, five optimizations lost.

Confirm it: -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining and look for the call site changing from an inlined entry to virtual call / not inlineable. PrintCompilation will also show the method being made not entrant and recompiled around the time you deployed.

Fixes:

  • Split the hot path so each call site sees one type — often just moving the dispatch outward, so the type is chosen once rather than per iteration.
  • Keep the abstraction but hoist the virtual call out of the loop: resolve the implementation before the loop, then loop over a concrete local.
  • If one implementation genuinely dominates, ordering matters less than you'd hope — bimorphic still inlines both, so two implementations is often fine; the cliff is at three.
  • Do not delete the interface for performance without measuring. Design cost is certain; the 3× may be specific to that one loop.

The line that lands: "The JIT was optimizing for a world with one implementation, and I changed the world."

Scenario · Allocation rate triples after a refactor that "did not add any new". Where did the objects come from?

They were always there — escape analysis was hiding them, and the refactor broke it. Scalar replacement had been eliminating those allocations entirely; now they materialise on the heap.

Typical breakages, all of them innocuous-looking:

  • The object is now stored into a field or a collection, even briefly — it escapes.
  • It is passed to a method that grew past the inlining size limit, so the compiler can no longer see what happens to it.
  • The call site became megamorphic (see the previous scenario), so nothing inlines and nothing can be proven.
  • It is now returned from the method, or captured by a lambda that outlives the frame.
  • Extra logging: log.debug("...", obj) passes the object to a varargs array — the array escapes into a method call that is not inlined.

Diagnose with an allocation profiler (async-profiler -e alloc, or JFR's ObjectAllocationSample) to find the exact site, then -XX:+PrintInlining to see whether the enclosing method still inlines.

The durable lesson: optimizations that depend on proofs are not contractual. Escape analysis, inlining and vectorization can all silently switch off. If a hot path's performance depends on one of them, it needs a benchmark that would fail if the optimization disappeared — otherwise you find out in production.

Scenario · Your team is evaluating GraalVM Native Image for a long-running REST service to "get rid of warm-up." What questions do you raise?

Start by separating the two things AOT actually gives you — fast startup and low memory — from the thing you are being asked about, which is steady-state throughput.

Questions to ask:

  • How long does an instance live? If it is hours or days, the warm-up cost is amortised to nothing, and you would be trading away peak throughput to fix a problem that lasts 60 seconds. Fix warm-up with pre-warming instead.
  • Have we measured steady-state throughput both ways? Native Image gives up profile-guided speculation. Depending on workload, expect it to be somewhat slower at peak unless you run PGO — which requires a representative profiling run and adds real build complexity.
  • What is our reflection/proxy/dynamic-loading surface? Native Image assumes a closed world. Spring, Hibernate and friends have native support, but anything doing dynamic class generation needs configuration and sometimes cannot work at all. Budget for this — it is usually the largest cost.
  • What do we lose operationally? No JFR/JMX in the same shape, different profiling and debugging tools, dramatically longer builds, and platform-specific binaries in CI.
  • What is the actual business driver? If it is per-instance memory on a large fleet or scale-to-zero serverless, AOT is a strong fit. If it is "deploy alerts are noisy", the fix is warm-up traffic and costs a day.

Middle grounds worth naming: CDS/AppCDS for startup at near-zero cost and no semantic change; -XX:TieredStopAtLevel=1 for short-lived processes; and Project Leyden's ahead-of-time caching, which is bringing much of the startup benefit into the standard JVM without the closed-world constraint.

Common Interview Trap "Inlining is a performance optimization because method calls are expensive." Call overhead is the small part. Inlining is what gives the optimizer visibility. On a modern CPU a predicted direct call costs a couple of cycles. The reason inlining is called the "gateway optimization" is that every other analysis — constant folding, escape analysis, loop-invariant hoisting, dead-branch elimination, vectorization — can only operate on code the compiler can see in one piece. Inlining does not make the call fast; it makes the callee optimizable.
