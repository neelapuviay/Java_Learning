STAGE 01

javac turns source into portable bytecode — and stops there

ahead-of-time, once

The Java compiler never produces machine code. It checks syntax and types, then emits bytecode: instructions for an imaginary CPU that does not exist in physical hardware. That is the fundamental mechanism behind "write once, run anywhere" — and the exact reason a second compiler (the JIT) must exist at runtime.

Mental model — hold this picture

Imagine you write a recipe in English, and it has to be cooked in a hundred different kitchens around the world, each with different equipment. You do not write "press the red button on the Bosch oven." You write "bake at 180 °C." That instruction is precise, complete, and yet deliberately not tied to any one oven. Every kitchen then has a local cook who knows how to turn "180 °C" into the buttons on their machine.

javac writes the recipe. Bytecode is "bake at 180 °C." The JVM on each machine is the local cook. This one idea — translate to a neutral instruction set now, translate to the real machine later — is the whole reason Java runs everywhere, and the whole reason a second compiler (the JIT) has to exist at runtime.

MathWizard.java javac 17 
public class MathWizard {

    static final int TOTAL = 15000;
    static int[] cache;

    static { cache = new int[8]; }      // static initializer

    public static void main(String[] args) {
        int result = 0;
        for (int i = 0; i < TOTAL; i++) {
            result = accumulate(result, i);
        }
        System.out.println(result);
    }

    static int accumulate(int balance, int item) {
        return balance + item;
    }
}

Read this alongside the panels What bytecode actually is, in plain words

Bytecode is simply a set of instructions that the Java compiler emits and the JVM then executes. It is not human-readable, and it is not machine-executable either — only the virtual machine understands it. That in-between status is the point, not an accident.

The name is literal. Each instruction is exactly one byte long. One byte gives you 28 = 256 possible operation codes, and Java currently uses around 205 of them. Some opcodes are followed by operand bytes (a constant-pool index, a jump offset), but the opcode itself is always a single byte. That is why a .class file is so compact compared to a native binary.

Why a "stack machine" and not a normal CPU

Your physical CPU is a register machine: it has a small set of named scratchpads (eax, rbx, x0…) and instructions say "add register 1 to register 2." The JVM instead defines an operand stack, and it works exactly like Reverse Polish Notation. The expression 1 + 2 becomes 1 2 +: push 1, push 2, then iadd pops both and pushes 3.

Look at the compiled accumulate in the right-hand panel and you are reading exactly that: ILOAD 0 pushes balance, ILOAD 1 pushes item, IADD pops two and pushes the sum, IRETURN pops it and hands it back. Four instructions for what one x86 instruction does — and that gap is precisely what the JIT closes later.

Why did the designers choose a stack? Because it makes the instruction set tiny and portable. A register-based bytecode would have to commit to how many registers exist, which is a hardware detail that differs on every chip. A stack has no fixed size to commit to, and a compiler can generate stack code without doing register allocation at all — the hard part is deferred to the JIT, which is the only component that knows the real CPU.

The constant pool: the class file's phone book

A .class file cannot store memory addresses, because when it was compiled nothing was in memory and no address existed. So it stores everything by name, as text, in a table called the constant pool: class names, field names, method names, type descriptors, string literals and numeric literals, each with an index.

Entries reference each other hierarchically. A Methodref does not contain a name directly — it points at a Class entry and a NameAndType entry, and those point at Utf8 entries holding the actual characters. That indirection is why the same string "accumulate" is stored once and reused by every instruction that mentions it. Stage 03 shows this pool being turned into real pointers.

Type descriptors — the shorthand you will see everywhere

Bytecode writes types in a compressed character notation, and you will meet it in every stack trace and every javap dump. I is int, J is long (not L — that is taken), Z is boolean, D is double, [I is int[], and a reference type is L + the slash-separated name + ;. A method descriptor puts parameters in parentheses followed by the return type: (II)I means "takes two ints, returns an int"; ([Ljava/lang/String;)V means "takes a String array, returns nothing."

How to see all of this yourself

You do not need a tool beyond the JDK. javap -c -p -v MathWizard.class disassembles the class: -c prints the bytecode instructions with their offsets, -p includes private members (by default only public and protected are shown), and -v dumps the constant pool, the version, the access flags and the stack/locals sizes. Every number in the "Class file anatomy" panel above comes straight out of that command.

magic
0xCAFEBABE — 4 bytes, always. If these are wrong the JVM throws ClassFormatError before parsing anything else.
major version
52 = Java 8, 55 = 11, 61 = 17, 65 = 21. A newer class on an older JVM → UnsupportedClassVersionError. This is a load-time error, never a compile-time one.
constant_pool
Indexed from 1, not 0. long and double entries occupy two slots — a historical quirk that still trips up bytecode-library authors.
<init>
The constructor. Called by invokespecial right after new. new alone only allocates zeroed memory; it does not run your constructor.
<clinit>
The static initializer javac synthesises from all static field initialisers and static { } blocks, merged in source order. Runs once, under a class-level lock (see Stage 03).
Code attribute
Holds the actual instruction bytes plus max_stack and max_locals — precomputed by javac so the JVM knows the exact frame size before executing a single instruction.

Interview drill · stage 01 Questions they actually ask about compilation & bytecode

Why doesn't javac just optimize the code ahead-of-time so no JIT is needed?
Because javac has no visibility into runtime execution behavior. It cannot know which branch is taken 99.9% of the time, which concrete subtype a polymorphic call site receives, how many times a loop executes, or the exact CPU instruction set (AVX-512, Neon) available on the host machine. It also must strictly preserve specification semantics. Therefore, javac performs only trivial AST desugaring — constant folding of static final constants, string concatenation lowers, and generic erasure — delegating aggressive optimization to the JIT compiler, which optimizes using real empirical telemetry.
Is Java a compiled or an interpreted language?

Both, in sequence — and the honest answer names both steps. Java is compiled ahead of time by javac into bytecode, and that bytecode is then interpreted at runtime by the JVM, and then compiled again — this time to native machine code — by the JIT.

The trap is answering with one word. Say: "javac is a static compiler that targets an abstract machine; the JVM starts by interpreting that output and progressively recompiles hot code to native. So Java is statically compiled, dynamically interpreted, and dynamically re-compiled."

What optimizations does javac actually perform?

Far fewer than most developers assume. javac essentially does desugaring plus a couple of legally-mandated foldings:

  • Constant folding of static final primitives and String constants — this is required by the JLS, not an optimization choice. It is why TOTAL disappears and SIPUSH 15000 appears inline.
  • Generic erasure — List<String> becomes List plus synthetic checkcasts.
  • Desugaring — enhanced for-loops become iterator loops, switch-on-String becomes a hashCode switch plus equals checks, lambdas become invokedynamic call sites, autoboxing becomes Integer.valueOf.
  • String concatenation lowering — in Java 9+ this becomes an invokedynamic to StringConcatFactory rather than a StringBuilder chain.

It does not inline, unroll loops, eliminate dead branches based on profiles, or vectorize. Those need runtime facts javac cannot have.

Why is the constant pool needed at all — why not just store addresses?

Because at compile time there are no addresses. System.out does not exist anywhere; the class java.lang.System has not been loaded, and on the target machine it may be a completely different JDK build than the one on your laptop. Writing an address into the file would break the moment anything moved.

Storing names as text also enables separate compilation: you can recompile one class without recompiling its callers, and swap a dependency JAR without touching your own bytecode, as long as the names and descriptors still match. The cost of that flexibility is the resolution step at runtime, which Stage 03 covers.

Scenario · You add a public static final int MAX = 100; to library A. Service B reads A.MAX. You later change it to 200, rebuild only library A, and drop the new JAR in. Service B still prints 100. Why?

This is the classic constant inlining / stale constant bug, and it is the single most-asked bytecode question in senior interviews.

Because MAX is static final with a compile-time constant initialiser, it is a compile-time constant expression under the JLS. javac is required to fold its value directly into every call site. Service B's .class file does not contain a field read at all — it contains the literal SIPUSH 100. There is no symbolic reference left to re-resolve, so replacing the JAR changes nothing.

Fixes, in order of preference:

  • Recompile all downstream consumers whenever a constant changes — the only correct answer if you keep the constant.
  • Defeat folding deliberately for values that may change: public static final int MAX = Integer.valueOf(200); or an accessor method public static int max(). A non-constant initialiser means javac must emit a real GETSTATIC.
  • Move genuinely configurable values out of constants entirely — into configuration, not into static final.

Say the phrase "binary compatibility" out loud in the interview: this is the textbook example of a change that is source-compatible but not binary-compatible.

Scenario · CI builds fine, but production throws UnsupportedClassVersionError: class file version 61.0, this version only recognizes up to 55.0. What happened and what do you check?

Read the numbers first — they tell you the whole story. 61 is Java 17, 55 is Java 11. Something compiled at 17 is being loaded by an 11 runtime. Note where the error appears: it is thrown by the class loader, at first use of that class, not at startup — so a rarely-hit code path can hide this for days.

What to check, in order:

  • The build's --release / maven.compiler.release setting. -source/-target alone is not enough: it produces the right version number but still links against the newer JDK's API, so you get NoSuchMethodError instead. --release is the only flag that checks both.
  • Transitive dependencies — a library upgraded to a 17-only build will fail exactly the same way, and it is usually the library, not your code.
  • The container base image versus the build image. A maven:17 builder writing into an eclipse-temurin:11-jre runtime image is the most common cause in practice.
  • Multi-release JARs (META-INF/versions/…) if the JAR claims to support both.

Verify quickly with javap -v Foo.class | grep major or unzip -p app.jar Foo.class | xxd | head -1 — bytes 7–8 are the major version.

Scenario · A teammate claims "we should turn off the JIT with -Xint in production because compilation wastes CPU." How do you answer?

Frame it as measurement, not opinion. -Xint forces interpreter-only execution, which typically runs 10–50× slower for compute-bound code. You save a small, bounded amount of background compiler CPU and pay an unbounded throughput penalty on every request.

The legitimate versions of that concern, and their real fixes:

  • "Compilation burns CPU at startup on a tiny container" → use AppCDS to cut class loading, or -XX:TieredStopAtLevel=1 (C1 only) for short-lived jobs — fast to compile, decent code, no C2 cost.
  • "Warm-up hurts our p99 after every deploy" → that is real; the answers are warm-up traffic before rotating in, or AOT/native-image if the process is genuinely short-lived.
  • "Compiler threads compete with app threads" → bound them with -XX:CICompilerCount rather than disabling compilation.

-Xint's only real uses are debugging a suspected JIT miscompilation and getting deterministic bytecode-level traces. It is a diagnostic switch, never a production tuning knob.

Common Interview Trap "Bytecode is machine code for the JVM, so it's already optimized machine code." Bytecode is an abstract instruction set designed for an imaginary stack machine. Physical CPUs are register machines (x86_64, ARM64). Every bytecode instruction must either be decoded and dispatched by the interpreter or transformed into native register instructions by the JIT compiler.
