STAGE 04

The Bytecode Interpreter — A Virtual Stack Machine in Action

Tier 0 execution

Execution begins at Tier 0 in the bytecode interpreter (HotSpot Template Interpreter). Unlike physical x86/ARM CPUs that operate on register banks, the JVM operates as an abstract stack machine. Every operation pushes values onto the operand stack, manipulates the top operands, and stores results back into local variable slots.

Mental model — hold this picture

Picture a clerk at a desk with an in-tray of numbered slips (the local variable array) and a spike on which papers are stacked (the operand stack). Every instruction is one tiny order: "copy slip 0 onto the spike", "copy slip 1 onto the spike", "take the top two papers off the spike, add them, put the result back", "take the top paper and hand it to whoever asked."

The clerk never improvises and never looks ahead. Read order, do order, read next order. That is the interpreter — and its honesty is exactly its weakness: a real CPU could have done all four of those orders in a single instruction, but the clerk cannot see four steps at once. The JIT is the manager who watches the clerk for a while, notices the same four-step ritual repeating ten thousand times, and replaces it with one motion.

Read this while stepping through How the interpreter actually executes a method

After class loading, the JVM feeds bytecode into the interpreter, which translates each instruction into machine-level work and drives the operating system underneath. It is the only execution mode that is always available — every method in every Java program starts here, at Tier 0, including methods that will later be compiled to peak native code.

Three things exist per method call: a frame

Every method invocation pushes a frame onto the calling thread's stack, and the frame is destroyed when the method returns. A frame holds exactly three things:

  • The local variable array — numbered slots. Slot 0 of an instance method is always this; for a static method slot 0 is the first parameter, which is why accumulate's balance is ILOAD 0. Parameters occupy the first slots, then declared locals. A long or double consumes two slots.
  • The operand stack — the scratch space where actual computation happens. Its maximum depth is max_stack, precomputed by javac and stored in the Code attribute, so the JVM knows the exact frame size before executing anything.
  • A reference to the runtime constant pool of the frame's class, so instructions like invokevirtual #18 can look up what #18 means.

Alongside, each thread has a PC register holding the address of the instruction currently executing. Frames are strictly thread-private, which is why local variables can never have a visibility problem between threads — there is nothing to share.

Everything is push, operate, pop

The JVM is a stack machine using Reverse Polish Notation: 1 + 2 is expressed as 1 2 +. Operands go up first, the operator consumes them. Watch the panel above and you will see nothing else ever happens — every arithmetic instruction pops its inputs from the top of the stack and pushes its result back.

The opcode names are a small, regular language once you see the pattern. The first letter is the type (i int, l long, f float, d double, a reference), and the rest is the action: iload_1 pushes the int in slot 1, istore_2 pops into slot 2, iconst_3 pushes the literal 3, iadd adds, ireturn returns an int, aload_0 pushes this. Learn the pattern and you can read any disassembly without a reference table.

Why this is slow — and why it is still worth having

The cost is not the arithmetic; it is the dispatch. For every single instruction the interpreter must fetch the opcode, jump to the handler for it, move values to and from the stack in memory, and advance the PC. A simple a + b costs four instructions and several memory round-trips where a CPU would use one register-to-register add. Worse, the indirect jump at the heart of the dispatch loop is hostile to the CPU's branch predictor.

HotSpot's answer is the template interpreter: rather than a giant C++ switch, at startup the VM generates machine code for each opcode handler and stitches the dispatch together with direct jumps. It is a substantial win over a naïve interpreter — and still roughly an order of magnitude slower than compiled code, which is precisely why the JIT exists.

So why not compile everything immediately? Because most code runs once. Compiling a method costs far more CPU than interpreting it a handful of times, and — the deeper reason — the interpreter is where the JVM collects the profile that makes the eventual compilation good. Stage 05 is that profile being gathered.

The two ways compiled code takes over

Switch the loop model selector above and watch the difference. In Model A the hot work lives in a method that is called repeatedly, so the invocation counter rises and the next call simply dispatches to the compiled version — clean and easy. In Model B the loop never leaves main(), so no invocation ever completes; the back-edge counter is what rises, and HotSpot must swap compiled code into a frame that is already running. That is On-Stack Replacement (OSR), and it is why a single monolithic main method can behave strangely in benchmarks.

Interview drill · stage 04 Questions they actually ask about interpretation & the stack

What exactly lives on the JVM stack versus the heap?

The stack holds frames; frames hold local variables and the operand stack. Objects always live on the heap.

The precise phrasing that separates a good answer from a vague one: for Order o = new Order();, the reference variable o is a slot in the frame on the stack; the object it points at is on the heap. For int i = 5; the value itself is in the slot — primitives declared as locals have no heap presence at all. An int field inside an object, by contrast, lives on the heap with that object.

Add the nuance and you sound senior: escape analysis (Stage 06) can let the JIT skip the heap allocation entirely for objects that never escape their method, breaking the object into raw values in registers. So "objects are always on the heap" is true of the abstract machine and not always true of the machine code that actually runs.

Why does the JVM start by interpreting instead of compiling everything up front?

Three reasons, and the third is the one interviewers are listening for.

  • Startup latency. Compiling every method that gets loaded — thousands of them, most executed once — would cost far more than simply running them.
  • Memory. Native code is many times larger than bytecode, and the code cache is a finite native region.
  • Profile quality. The interpreter is where the JVM learns: which branches are taken, which types actually appear at each call site, how many times each loop runs. That telemetry is what lets C2 produce code that is faster than any ahead-of-time compiler could have produced, because AOT never sees the real workload.

Roughly 80% of execution time is spent in 20% of the code. Interpreting first is how the JVM finds out which 20% — and spends its compilation budget only there.

Scenario · A recursive tree walk works in tests but throws StackOverflowError in production on real data. Someone proposes -Xss512m. What do you say?

First, the mechanism: each recursive call pushes a frame, frames are never reclaimed until the call returns, and the thread's stack is a fixed-size native region (default around 512 KB–1 MB). Real data is simply deeper than test data. Note that the heap is completely untouched — this is not a memory-pressure problem, and no amount of -Xmx helps.

Why -Xss512m is the wrong instinct: stack size is per thread and is native memory outside -Xmx. On a 200-thread server that is 100 GB of address space reservation; you will hit OutOfMemoryError: unable to create new native thread or get OOM-killed by the kernel long before you get a useful answer. It also only moves the cliff — the next deeper input fails again.

What to do instead, in order:

  • Convert recursion to iteration with an explicit stack. An ArrayDeque of nodes on the heap grows to gigabytes happily. This is the real fix and it is usually a ten-line change.
  • Bound the depth and fail with a domain error — an unbounded tree walk over user-supplied data is also a denial-of-service vector.
  • Modest -Xss bump (1 MB → 2 MB) as a stopgap, sized against your actual thread count, with the number written down.
  • Isolate the deep work on a dedicated thread created with an explicit stack size: new Thread(group, runnable, name, 16L*1024*1024) — the only way to give one thread a big stack without giving it to all of them.

The follow-up they will ask: "why doesn't the JVM do tail-call optimisation?" Because the JVM specification does not permit frames to be silently elided — stack walking is observable through Throwable.getStackTrace, security checks and reflection, so removing frames would change program-visible behaviour. It is a known limitation, not an oversight; Project Loren/Valhalla-era proposals have circled it for years.

Scenario · A JMH benchmark shows a method taking 0.3 ns per call — faster than a single CPU cycle. What is wrong?

Nothing is wrong with the JVM; the benchmark is measuring nothing. C2 discovered the result was never used and deleted the entire computation — dead code elimination, enabled by inlining the method into the benchmark loop.

This connects directly back to the interpreter: while the method was interpreted, the four-instruction push/add/pop dance genuinely happened. Once compiled and inlined, the compiler can see the whole thing is pure and unobserved, and the correct machine code for "compute a value nobody reads" is no machine code at all.

Fixes: return the value from the benchmark method (JMH consumes returned values), or pass it to a Blackhole. Also make the inputs @State fields rather than constants, or the compiler will constant-fold the whole expression at compile time.

The general lesson worth stating: a benchmark measures what the optimizer could not prove was useless. Any timing that looks physically impossible is an optimizer artefact, not a discovery.

Scenario · Production shows a bug you cannot reproduce. A colleague suggests running with -Xint to "rule out the JIT." Is that reasonable?

As a diagnostic, yes — as a fix, no. Running with -Xint is a legitimate and underused bisection step: if the bug disappears under interpretation, you have narrowed it to compiled code, which means either a genuine (rare) JIT bug or, far more likely, a data race in your code that only manifests once the compiler reorders memory operations.

That second case is the important one. The Java Memory Model permits reordering that the interpreter happens not to perform. Missing volatile, an unsynchronised lazy init, a non-thread-safe cache — all of these can be invisible at Tier 0 and appear the moment C2 hoists a field read out of a loop. The JIT did not cause the bug; it revealed one that was always there.

Better intermediate steps before the sledgehammer: -XX:TieredStopAtLevel=1 (C1 only — much less aggressive reordering, but still fast), -XX:-UseOnStackReplacement, or excluding one suspect method with -XX:CompileCommand=exclude,com/acme/Foo.bar. Each narrows the search without a 30× slowdown.

Why is a stack-based interpreter slower than a register-based VM?
A stack architecture is exceptionally compact and easy for compilers to generate without complex register allocation. However, executing a simple binary operation like a + b requires 4 bytecode instructions: two iload pushes to the stack, one iadd that pops two values and pushes the sum, and one istore. This generates massive memory traffic and dispatch overhead compared to a single physical machine instruction (e.g. add eax, ebx).
Common Interview Trap "Primitives go on the stack, objects go on the heap." Only local primitives live in a frame. A primitive field lives on the heap, inside its object. int count declared inside a method is a slot in the frame. int count declared as a field of Order is bytes inside the Order object on the heap. The distinction is where it is declared, never what type it is — and getting this precise is a cheap way to sound like you have actually looked at a frame.
