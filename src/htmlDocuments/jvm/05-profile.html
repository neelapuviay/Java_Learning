STAGE 05

Profiling & Tiered Compilation Counters — How HotSpot Spots Hot Code

telemetry & threshold engine

HotSpot does not compile code immediately. It attaches lightweight profiling counters to every method entry and loop back-edge. As counters accumulate execution "heat", the method crosses thresholds and triggers asynchronous background compilation by C1 (Client) and subsequently C2 (Server) compilers.

Mental model — hold this picture

A factory floor manager cannot rebuild every workstation, so she carries a tally counter. Every time a worker performs a task, she clicks. Most tasks get two or three clicks and are forgotten. A handful get clicked thousands of times — and those get the custom jig built for them, because only there will the investment pay back.

Crucially, she does not just count. While counting she also notices things: this station always receives the same part; that inspection never fails; this queue is always exactly eight items long. When the jig is finally built, it is built around those observations — and it comes with a tripwire, so that if a different part ever shows up, the jig is thrown away rather than producing a wrong result.

The counters are HotSpot's invocation and back-edge counters. The observations are the profile. The tripwire is deoptimization (Stage 07). An ahead-of-time compiler has the jig-building skill but never gets to watch the floor — that difference is the entire argument for JIT.

Read this while turning the counters How HotSpot decides what is worth compiling

The JIT watches how the code is being executed. It tracks which methods are frequently called and keeps a count for each one. When a count crosses a threshold, that method is compiled and its machine code is saved in the Code Cache, so the JIT never has to compile it again. That is the whole loop, and everything below is detail on it.

Two counters, because there are two ways to be hot

Each method carries an invocation counter (incremented on entry) and a back-edge counter (incremented every time control jumps backwards — i.e. every loop iteration). Two counters exist because there are two genuinely different shapes of hot code:

  • A small method called a million times — caught by the invocation counter, and the next call simply dispatches to the compiled version.
  • A method called once that loops a million times — the invocation counter stays at 1 forever. Only the back-edge counter notices. Compiled code then has to be installed into a frame that is already executing, which is On-Stack Replacement.

HotSpot actually triggers on a combination (roughly: invocations, or invocations + back-edges against a higher bar), and the thresholds are scaled dynamically by how busy the compiler queues are — a method will be compiled at a lower count when the compiler is idle. This is why the numbers you set in the panel are guidance, not a contract.

The tiers, and why there are five of them

Tiered compilation exists because the two compilers have opposite strengths. C1 compiles fast and optimizes lightly; C2 compiles slowly and optimizes aggressively. Rather than choosing, HotSpot uses both:

  • Tier 0 — Interpreter. Everything starts here. Slow, but instant to start and it gathers the initial profile.
  • Tier 3 — C1 with full profiling. The normal second step. Roughly 5–10× faster than interpreted, while still collecting the rich telemetry C2 will need. You pay a profiling overhead here on purpose.
  • Tier 4 — C2. Peak native code, no profiling overhead, built on the data Tier 3 gathered.
  • Tier 1 — C1, no profiling. For trivial methods (a getter) where C2 could never do better. Compiled once and left alone.
  • Tier 2 — C1, limited profiling. A pressure-relief path used when the C2 queue is long.

The important insight is that Tier 3 is deliberately slower than it could be. It carries instrumentation it does not need for itself, purely so that Tier 4 can be excellent. Warm-up is the price of that, and speculative optimization is what it buys.

What is in the profile

Counters are only the trigger. The data that makes C2 worth waiting for is:

  • Receiver type profiles at each virtual call site — "this List has been an ArrayList 100% of 40,000 times." That single fact enables inlining a virtual call, which unlocks nearly every other optimization.
  • Branch frequencies — "this null check has never been true", "this exception branch has never been taken". Cold paths get moved out of line or replaced with an uncommon trap.
  • Loop trip counts — how far to unroll, whether vectorizing pays.
  • Type and null-ness of values, enabling checks to be hoisted or removed entirely.

None of this is knowable statically. This is exactly the "true strength of the JIT approach": speculative optimizations grounded in observed behaviour, which vendors have measured at up to 50% performance gains over what the same compiler could do without a profile.

Compilation is asynchronous — and that shapes what you measure

Crossing a threshold does not pause your thread. It enqueues a compilation request; background compiler threads do the work; the application keeps running at its current tier and only picks up the compiled code once it is installed. A busy queue therefore means methods stay slow for longer, which is why the first seconds after a deploy are the worst seconds — thousands of methods cross their thresholds simultaneously and contend for the same handful of compiler threads.

The practical consequence: the JVM's performance at time T tells you almost nothing about its performance at time T+30s. Any measurement that does not discard warm-up is measuring the compiler, not the application.

-XX:+PrintCompilation
One line per compilation: method, tier, size, and flags like % (OSR), s (synchronized), ! (has exception handlers), made not entrant (deoptimized). The single most informative flag for understanding warm-up.
-XX:+UnlockDiagnosticVMOptions
-XX:+PrintInlining
Shows every inlining decision and, more usefully, every refusal with its reason (too big, not inlineable, callee is too large).
-XX:TieredStopAtLevel=1
C1 only. Fast to warm up, ~2–3× slower at peak. Genuinely correct for short-lived CLI tools and batch jobs that never reach steady state.
-XX:-TieredCompilation
C2 only, no C1 stepping stone. Slower warm-up, occasionally better peak. Rarely the right answer today.
-XX:CICompilerCount
Number of background compiler threads. Worth bounding on small containers where compiler threads steal CPU from request handling during the startup storm.
ReservedCodeCacheSize
If the code cache fills, the JIT switches off entirely and everything reverts to interpreted speed — a silent, catastrophic throughput collapse. Watch for CodeCache is full. Compiler has been disabled.

Interview drill · stage 05 Questions they actually ask about profiling & tiered compilation

What is tiered compilation and why not just always use C2?

Tiered compilation runs the interpreter, C1 and C2 as a ladder, promoting each method as it proves itself worth more investment.

Always-C2 fails on both ends. Compilation is expensive — C2 can take milliseconds per method and there are thousands of methods, so startup would crawl. And C2 needs a profile to be good; compiling immediately means compiling blind, and a blind C2 is not much better than C1 while costing far more.

The elegant part is that C1 solves both problems at once: it makes the code fast enough quickly, and it collects the profiling data that makes the eventual C2 compilation excellent. Tier 3 pays a tax so Tier 4 can be exceptional.

What is On-Stack Replacement and when does it matter?

OSR is HotSpot swapping compiled code into a method invocation that is already executing. It exists for the case where the invocation counter can never help: a long-running loop inside a method that is called once.

Mechanically, the compiler produces a special OSR entry point that accepts the current interpreter state — the locals and operand stack as they are right now, at a specific bytecode index — reconstructs them into the compiled frame's register layout, and jumps in mid-loop.

Where it matters in practice: naïve benchmarks. Putting your hot loop directly in main() measures OSR-compiled code, which is typically worse than normally-compiled code — the compiler has less freedom because it must accept an arbitrary entry state, and loop-invariant hoisting is constrained. This is one of several reasons JMH puts the work in a separate method.

Scenario · Your service is fast in load tests but the first 60 seconds after every deploy show 10× worse p99, causing alerts on every rollout. What is happening and what do you actually do?

This is warm-up, and it is not a bug. Three costs are stacking in those 60 seconds: thousands of classes being loaded, verified and initialised (Stage 03); every method executing at Tier 0 or Tier 3; and the compiler queue saturated so promotions arrive late. On top of that, the CPU spent compiling is CPU not spent serving.

Confirm before acting — -XX:+PrintCompilation plus a timestamped request-latency log, or JFR's Compilation and Class Loading events. Verify the tail actually tracks compilation activity rather than, say, a cold connection pool or an empty cache.

Fixes, ordered by leverage:

  • Warm the instance before it takes traffic. A readiness probe that only passes after N synthetic requests over the real endpoints. Cheap, boring, and by far the most effective thing on this list.
  • Roll out more slowly — smaller batches, or a load-balancer slow-start ramp, so a cold instance never receives full share.
  • AppCDS to eliminate most of the class-loading portion.
  • Give the JVM more CPU at startup than at steady state (Kubernetes startup probes plus a generous limit) so compiler threads are not competing with request threads.
  • Adjust the alert. If a 60-second warm-up is inherent, alerting on p99 during a known deploy window is a monitoring bug, not a JVM one.
  • If the process is genuinely short-lived, this is the case for AOT / native image — full speed from instruction one, at the cost of the speculative optimizations discussed in Stage 06.

What not to do: raise thresholds so things compile "sooner". Lower thresholds mean compiling on a thinner profile, producing worse code and more deoptimization — you usually make steady state worse to make warm-up marginally better.

Scenario · A long-running service is fine for days, then throughput collapses ~5× with no GC change, no traffic change, and no errors. What do you check first?

Check the code cache. The signature — sudden, permanent, no GC involvement, no exceptions — matches CodeCache is full. Compiler has been disabled. almost uniquely. Once the code cache fills, HotSpot stops compiling and, on older JDKs, may not recover even after methods are flushed. Everything drifts back toward interpreted speed as compiled methods are evicted.

How to confirm: jcmd <pid> VM.native_memory summary or Compiler.codecache; JMX MemoryPoolMXBean for the CodeHeap pools; or just grep the log — the JVM prints a warning when it happens.

Why it fills: genuinely large applications (thousands of compiled methods); heavy use of dynamically generated classes (proxies, ORMs, scripting, lambdas at scale); and — the sneaky one — deoptimization churn, where methods are repeatedly compiled, invalidated and recompiled, leaving zombie code behind.

Fixes: raise -XX:ReservedCodeCacheSize (default 240 MB with tiered compilation; 512 MB is a reasonable large-app value); ensure -XX:+UseCodeCacheFlushing is on; and treat repeated flushing as a symptom to investigate rather than a setting to raise forever. If the underlying cause is a megamorphic call site causing recompilation storms, fix that instead (Stage 06/07).

Monitor it like you monitor heap. Code cache utilisation belongs on the same dashboard — it is one of the few JVM resources that fails silently.

Scenario · A colleague sets -XX:CompileThreshold=100 "so the JIT kicks in sooner." What breaks?

Several things, and the interesting part is that they are not obvious.

  • CompileThreshold is ignored under tiered compilation (the default since Java 8). The relevant knobs are Tier3InvocationThreshold, Tier4InvocationThreshold and friends. So the first effect is nothing at all — and the colleague concludes it "helped", which is worse than it failing.
  • If they do lower the tiered thresholds: methods get compiled on a thin profile. A call site seen 100 times may look monomorphic and be megamorphic at 100,000. C2 speculates, the speculation fails, the method deoptimizes and recompiles — costing more than it saved and polluting the code cache.
  • More methods get compiled overall, including ones that would never have become hot, consuming compiler CPU and code cache for no benefit.

The general principle to state: HotSpot's thresholds are already adaptive — they scale with compiler queue length and with the method's size and shape. Hand-setting them replaces a feedback loop with a constant. Reach for them only with a measurement showing a specific method compiling too late, and even then prefer -XX:CompileCommand targeted at that one method over a global change.

Common Interview Trap "The JIT compiles a method after it has been called 10,000 times." There is no single magic number, and there is more than one counter. Tiered compilation uses separate invocation and back-edge counters with different thresholds per tier, scaled dynamically by compiler queue pressure and influenced by method size. A method may be compiled after a few hundred calls when the compiler is idle, or after far more when it is busy — and a method called exactly once can be compiled anyway, via OSR, if it loops enough. Quote the mechanism, never the constant.
