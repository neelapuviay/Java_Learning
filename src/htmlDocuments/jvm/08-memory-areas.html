STAGE 08

JVM Memory Areas & Data Layout — Where Every Byte Lives

heap, stack, metaspace, pc & native

Every variable, object, method frame, and constant belongs to one of the 5 fundamental JVM Runtime Data Areas. Use the interactive step debugger below to walk through Java execution instruction-by-instruction and inspect exactly where each byte is placed.

Mental model — hold this picture

Think of an office building. Each worker has a private desk — small, private, tidied instantly when they leave. That is the Thread Stack (with local variables and operand stack) and the PC Register (the page number they are reading). No other worker can reach into it.

In the middle of the building is a shared warehouse. Anything too big for a desk goes there. That is the Heap (Eden, Survivor, Old Gen, and the String Constant Pool), cleaned periodically by the Garbage Collector.

In the basement are the architect blueprints (Metaspace: class metadata, method bytecode, field layouts, and the runtime constant pool). Each blueprint has a managed-heap counterpart: a java.lang.Class mirror that carries HotSpot's static field values. In the back room is the machine workshop (CodeCache: JIT-compiled native machine code) and the loading dock outside the building (Native Memory & Direct Buffers).

The golden production rule: -Xmx sizes the warehouse only. Metaspace, CodeCache, Thread Stacks, and Direct Buffers are all outside it — which is why containers get OOM-killed (exit 137) while the heap graph looks perfectly calm.

In-Depth Architecture Explorer Explore the Inner Anatomy of All 5 JVM Memory Areas

Area 1: Metaspace (Native Method Area)

Metaspace holds class metadata, method bytecode, field definitions and offsets, and the Runtime Constant Pool. Introduced in Java 8 to replace PermGen, Metaspace resides entirely in native off-heap memory rather than the contiguous Java heap. HotSpot stores static field values with the corresponding on-heap java.lang.Class mirror.

  • Runtime Constant Pool: A per-class table of symbolic references (#1 = Methodref, #2 = Fieldref, #3 = ClassName, #4 = StringLiteral). When bytecode executes instructions like invokevirtual #18, the JVM looks up the resolved target method here.
  • Klass Metadata & Method Bytecode: The internal HotSpot C++ InstanceKlass structure defining class inheritance, method tables (vtables/itables), field offsets, and the raw bytecode arrays for all methods.
  • Static Fields: Static variables belong to the defining class rather than its instances. HotSpot stores their values with the heap-resident class mirror; reference values are traversed from the class-loader/class root set while that class remains live. They are not permanent: clearing the field or unloading the defining class can release the referenced object.
  • PermGen vs. Metaspace: PermGen had a fixed maximum size (-XX:MaxPermSize) inside the heap. Metaspace grows dynamically by default. Always cap it with -XX:MaxMetaspaceSize to prevent unconstrained ClassLoader leaks from consuming all host RAM!

Area 2: Managed Java Heap (-Xmx)

The Heap is the shared warehouse where all object instances and arrays live. It is managed automatically by the Garbage Collector and sized by -Xms (initial) and -Xmx (maximum).

  • Young Generation (Eden + Survivor S0/S1): Most ordinary new objects are allocated in Eden via fast Thread-Local Allocation Buffers (TLABs). Surviving objects are copied between S0 and S1 during Minor GCs, incrementing their aging bits.
  • Old Generation (Tenured): Holds long-lived objects that survived multiple GC threshold cycles (default 15 in CMS/Parallel, 15 or dynamic in G1) as well as Humongous Objects (large arrays exceeding 50% of a G1 region).
  • String Constant Pool (StringTable): Since Java 7, interned Strings live on the Heap (moved out of PermGen). It is implemented as an internal hashtable tuned via -XX:StringTableSize. Interned strings can be collected when no longer referenced.
  • 64-Bit Object Header Anatomy: Every object carries a 12-byte header with Compressed OOPs:
    • 8-byte Mark Word: Stores hash code, GC generation age (4 bits), lock state bits (biased, thin, fat monitor), and GC forwarding pointers.
    • 4-byte Klass Word: Compressed class pointer referencing the class metadata in Metaspace.
    • Instance Data & Padding: Field values followed by alignment padding to an 8-byte boundary.

Area 3: Program Counter (PC) Register

The PC Register is a lightweight, strictly thread-private register created when a thread starts.

  • Instruction Pointer: If the thread is currently executing a Java method, the PC register contains the address or Bytecode Index (bci) of the JVM instruction currently being executed (e.g., bci 0, bci 4, bci 12).
  • Native Method Behavior: If the thread is currently executing a native method (via JNI or C++ runtime stub), the JVM PC register value is undefined (null) because native code executes directly on the physical CPU's hardware register (e.g., RIP on x86_64 or PC on ARM64).
  • Concurrency Safety: Because each thread has its own private PC register, threads can switch, pause, and resume execution independently without interfering with other threads' instruction pointers.

Area 4: JVM Thread Stack (-Xss)

Every Java thread has a private stack sized by -Xss (often around 1 MB, but platform and JDK dependent). Whenever a method is called, a new Stack Frame is pushed. When the method returns, the frame is popped in O(1) time without GC overhead.

  • Local Variable Array (LVA): Numbered slots containing parameters and declared local variables. In instance methods, Slot 0 is always this. In static methods, Slot 0 is the first argument. Primitives (int, float, boolean) live directly in the slot; object variables hold 4-byte reference pointers to heap instances.
  • Operand Stack (OS): The working scratchpad for the virtual stack machine. Arithmetic and method invocation bytecodes push arguments onto the operand stack, perform operations, and pop results back to local variable slots.
  • Frame Data / Dynamic Linking: Holds a reference to the Runtime Constant Pool for the method's class to support runtime method dispatch and exception handling dispatch tables.
  • Thread Concurrency Note: A local variable slot is strictly thread-private and cannot itself race. An object referenced by that local can still be shared and raced on through another thread's reference.

Area 5: Native Memory & Native Method Stack

Native Memory encompasses all process memory allocated outside the managed Java heap (-Xmx).

  • Native Method Stack (C-Stack): The C/C++ execution stack used when Java calls into native C libraries via the Java Native Interface (JNI).
  • Direct Off-Heap Buffers: Memory allocated via ByteBuffer.allocateDirect() or Netty's pooled byte buffers. These reside in OS native memory for zero-copy socket and disk I/O. Sized with -XX:MaxDirectMemorySize.
  • CodeCache: Native memory allocated for storing JIT-compiled machine code (C1 Tier 3 and C2 Tier 4 nmethod compiled blocks) and interpreter dispatch stubs. Sized with -XX:ReservedCodeCacheSize.
  • Native Memory Tracking (NMT): Monitor all off-heap usage categories using -XX:NativeMemoryTracking=summary and query at runtime with jcmd <pid> VM.native_memory summary.

Read this alongside the memory map The runtime data areas, and who can see them

The JVM specification divides memory into runtime data areas, and the single most useful way to organise them in your head is per-thread versus shared, because that division is what determines whether you can have a concurrency bug at all.

Per-thread — created with the thread, destroyed with it

  • JVM stack — the frames: locals, operand stack, constant-pool reference. Sized by -Xss. Exhausting it gives StackOverflowError.
  • PC register — the address of the instruction currently executing (undefined while in a native method).
  • Native method stack — the C stack used when Java calls into JNI.

Because these areas are private, the local slots themselves cannot race. The object reached through a local reference can still be shared. Data races involve shared state, which in Java means heap-resident object state or class-level static values.

Shared by every thread

  • Heap — all objects and arrays, including each class's java.lang.Class mirror and HotSpot's static field values. Sized by -Xms/-Xmx. Managed by the GC (Stage 09). Exhausting it gives OutOfMemoryError: Java heap space.
  • Metaspace (the "method area" in specification language) — class metadata, method bytecode, field layouts, and the runtime constant pool. Native memory, outside -Xmx.
  • Code cache — native code produced by C1 and C2, plus the interpreter's own generated stubs. Native memory.
  • String constant pool — interned strings. Since Java 7 it lives on the heap (it was in PermGen before), which is why interned strings are now collectable and why -XX:StringTableSize tunes a hash table, not a memory region.

Metaspace, and why PermGen had to go

Before Java 8, class metadata lived in PermGen, a fixed-size region inside the Java heap. Class metadata therefore competed with your objects for space, and needed a -XX:MaxPermSize that was impossible to size correctly — the classic symptom being OutOfMemoryError: PermGen space after a few hot redeploys.

Metaspace lives in native memory and grows on demand, so the default is effectively unlimited. But it can still leak, because metaspace is freed per class loader: one leaked ClassLoader keeps every class it ever defined alive forever. Cap it with -XX:MaxMetaspaceSize so a leak fails fast instead of eating the machine — an uncapped leak degrades the whole host, while a capped one produces a clean, diagnosable error.

What an object actually costs

An object is not just its fields. On a 64-bit HotSpot with compressed oops (the default below a 32 GB heap), every object carries a 12-byte header — an 8-byte mark word (identity hash, lock state, GC age) plus a 4-byte class pointer — and is padded to an 8-byte boundary. Arrays add 4 more bytes for the length.

The consequences are practical: an Integer costs 16 bytes to hold 4 bytes of data; a Long[1000] is a thousand pointers to a thousand boxed objects scattered across the heap, versus long[1000] which is one contiguous 8 KB block. This is why boxing in hot data structures is expensive twice over — in footprint and in cache locality. It is also why crossing the ~32 GB heap boundary can increase effective memory use: compressed oops switch off and every reference doubles to 8 bytes.

Off-heap: the memory nobody puts on the dashboard

Total process memory is heap + Metaspace + code cache + thread stacks + direct buffers + GC data structures + the JVM's own native allocations + whatever native libraries allocate. On a 200-thread server with 1 MB stacks that is 200 MB before a single object exists. Netty, NIO and most high-performance I/O libraries allocate DirectByteBuffers outside the heap — fast, because the OS can read and write them without copying, and invisible to every heap-based tool.

The tool that makes this visible is Native Memory Tracking: start with -XX:NativeMemoryTracking=summary and query with jcmd <pid> VM.native_memory summary. It breaks the process down by category — Java heap, class, thread, code, GC, internal — and it is the only way to answer "the heap is 2 GB, so why is RSS 6 GB?"

Sizing for containers

Setting -Xmx equal to the container limit is the single most common production memory mistake, because it leaves nothing for everything above. Modern JVMs are container-aware and respect cgroup limits, so prefer -XX:MaxRAMPercentage (typically 50–75%) over a fixed -Xmx — the JVM then scales correctly when the limit changes, and reserves headroom for the non-heap regions by construction.

OOM: Java heap space
Live objects exceed -Xmx. Either genuinely too small, or a retention leak. Always take a heap dump: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/….
OOM: Metaspace
Class metadata exhausted. Almost always a ClassLoader leak — redeploys, dynamic proxies, generated classes, scripting engines.
OOM: Direct buffer memory
DirectByteBuffer exhaustion. They are freed only when a Cleaner runs after the Java wrapper is collected — so under low heap pressure, direct memory can exhaust while the heap is calm. Bound it with -XX:MaxDirectMemorySize.
OOM: unable to create
new native thread
The OS refused a thread. Usually a thread leak or stacks sized too large — not a heap problem, and raising -Xmx makes it worse by leaving less address space.
OOM: GC overhead
limit exceeded
More than 98% of time in GC recovering less than 2% of heap. The heap is not quite full, so it is technically still running — practically it is dead, and the real cause is retention.
StackOverflowError
Frames exceeded -Xss on one thread. The heap is untouched. Deep or unbounded recursion.
killed (exit 137)
Not a JVM error at all — the kernel OOM-killer. Total process RSS exceeded the container limit. Heap graphs look fine because the growth was off-heap.

Interview drill · stage 08 Questions they actually ask about JVM memory

Walk me through every memory region in the JVM and say which are shared.

Answer in the two-column shape — it demonstrates you understand why the division exists rather than reciting a list.

Per thread: JVM stack (frames: locals, operand stack), PC register, native method stack. Created and destroyed with the thread; never shared; therefore never a source of data races.

Shared: heap (all objects, arrays, class mirrors, and HotSpot static field values), Metaspace (class metadata, method bytecode, field layouts, runtime constant pool), code cache (JIT output), string constant pool (on the heap since Java 7).

Then the sentence that lands: "Metaspace replaced PermGen in Java 8 and is native memory outside -Xmx — which is why heap tuning does not prevent Metaspace OOMs, and why total process memory is always larger than the heap."

What is the difference between StackOverflowError and OutOfMemoryError?

Different regions, different causes, different fixes — and both are Errors rather than Exceptions because neither is meaningfully recoverable.

StackOverflowError: one thread's frames exceeded its -Xss stack. Caused by deep or infinite recursion. The heap is entirely unaffected. Fixed by converting recursion to iteration with an explicit heap-based stack.

OutOfMemoryError: some memory pool could not satisfy an allocation. Always read the message after the colon — "Java heap space", "Metaspace", "Direct buffer memory" and "unable to create new native thread" are four unrelated problems that share a class name, and the message is the entire diagnosis.

Nuance worth adding: catching OutOfMemoryError is almost always wrong, because the allocation that fails next may be inside your handler — but StackOverflowError is occasionally caught legitimately at a request boundary, since unwinding the stack genuinely does free the resource.

Scenario · A Kubernetes pod with a 4 GB limit is OOM-killed (exit 137) repeatedly. Heap usage never exceeds 1.5 GB and there is no OutOfMemoryError in the logs. Find it.

The absence of a Java OutOfMemoryError is the whole clue: the JVM never ran out of heap — the kernel ran out of container. Something outside -Xmx is growing.

Step 1 — make the invisible visible. Restart with -XX:NativeMemoryTracking=summary and take a baseline, then jcmd <pid> VM.native_memory summary.diff periodically. The category that grows is the answer, and this usually takes minutes rather than days.

Step 2 — the usual suspects, by category:

  • Thread — a thread leak. 1 MB stack each; an unbounded executor or a leaked pool per request adds up fast. Check jcmd Thread.print | grep -c tid over time.
  • Class — Metaspace growth from a ClassLoader leak (Stage 02) or heavy proxy/lambda generation.
  • Code — a large code cache, occasionally inflated by recompilation churn.
  • Internal / Other — direct byte buffers. Netty-based stacks are the classic case; check BufferPoolMXBean or Netty's own leak detector, and set -XX:MaxDirectMemorySize so it fails loudly instead of silently.
  • Not in NMT at all — a native library's own malloc: a JDBC driver, a compression or crypto library, a JNI integration. Diagnose with jemalloc/jeprof profiling or pmap deltas.
  • glibc arena growth — a genuine and under-known cause on multi-threaded Linux workloads. Test with MALLOC_ARENA_MAX=2.

Step 3 — size it properly regardless. Replace a fixed -Xmx with -XX:MaxRAMPercentage=60 and explicitly cap the other pools (MaxMetaspaceSize, MaxDirectMemorySize, ReservedCodeCacheSize, thread count). Bounded pools turn a mysterious kill into a specific, actionable Java error — which is worth doing even before you know the cause.

Scenario · Heap grows steadily over days until OOM. Restarting fixes it for a week. You have a heap dump. What do you do with it?

This is a retention leak, and the heap dump contains the answer — the skill is asking it the right question. Java leaks are always "unintended reachability": the GC is correctly refusing to collect objects you can still reach.

The method, in order:

  • Open the dump (Eclipse MAT, VisualVM, JFR's heap statistics) and run a dominator tree analysis. Do not look at object counts — look at retained size, which tells you how much memory would be freed if that object went away.
  • Take the largest dominator and ask for its path to GC root. That path is the bug. It ends at a static field, a thread, a ThreadLocal, or a JNI reference — and it names the exact line responsible.
  • Compare two dumps taken hours apart if the first is ambiguous. The delta is far more informative than either dump alone.

The classic four causes, all of which are "working as designed":

  • A static collection that only ever grows — a cache with no eviction policy is the number one Java leak, full stop.
  • Listeners or callbacks registered and never removed.
  • ThreadLocal values on a pooled thread that outlives the request — the thread never dies, so the value never clears.
  • ClassLoader leaks, where one lingering reference keeps an entire redeployed application's classes alive in Metaspace.

Two traps to avoid: WeakHashMap does not help if the value holds a strong reference back to the key — an extremely common mistake. And "just increase -Xmx" converts a weekly outage into a monthly one while making each heap dump harder to analyse.

Make it easier next time: ship with -XX:+HeapDumpOnOutOfMemoryError and a writable HeapDumpPath on a volume that survives pod restarts. A leak you cannot dump is a leak you cannot fix.

Scenario · Someone proposes moving a hot cache to DirectByteBuffer "to avoid GC pressure." Good idea?

Sometimes — but ask what problem is being solved, because off-heap trades a well-tooled problem for a badly-tooled one.

Genuine wins: very large caches (tens of GB) where the GC's cost scales with live-set size; zero-copy I/O, where the OS can read and write the buffer directly without a bounce through the heap; and data that is naturally byte-shaped, where you would otherwise pay object-header overhead per entry.

Real costs:

  • Deallocation is not deterministic. A DirectByteBuffer's native memory is freed by a Cleaner that runs only after the small Java wrapper object is collected. Under low heap pressure the GC has no reason to run, so you can exhaust native memory while the heap is nearly empty.
  • No tooling. Heap dumps show you nothing. You are back to NMT and native profilers.
  • Serialization cost. Objects must be encoded into and decoded out of bytes, which often erases the saving unless the data is already byte-shaped.

Measure first. If GC pause time is genuinely the problem, a modern low-pause collector (ZGC, Shenandoah — Stage 09) usually solves it with no code change at all, and that should be the first experiment. If the real problem is an unbounded cache, the fix is an eviction policy, not a different memory region.

If you do go off-heap, prefer a library that manages lifetime explicitly (Chronicle, Netty's pooled allocator, or the JDK's Foreign Function & Memory API with an Arena) over raw DirectByteBuffer, and always set -XX:MaxDirectMemorySize.

Common Interview Trap "-Xmx4g means the JVM uses at most 4 GB." It caps the Java heap only. Total process memory is heap + Metaspace + code cache + thread stacks + direct buffers + GC data structures + the JVM's own native allocations. This is the single most common reason a container is OOM-killed by the kernel while heap graphs look perfectly healthy — and why -XX:MaxRAMPercentage is the better flag in a container.
