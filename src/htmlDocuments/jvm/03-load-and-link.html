STAGE 03

Loading, Linking & Initialization — From raw bytes to a live type

runtime class lifecycle

Before any method can execute, the JVM transitions the class through three strictly ordered phases: Loading (reading bytes and defining the type in Metaspace), Linking (Verification, Preparation of static slots, and Resolution of symbolic references), and Initialization (executing static initializers <clinit>).

Mental model — hold this picture

A new employee joins. Loading is HR reading their CV and creating a personnel record — the person now exists in the system. Linking is compliance: verify the certificates are genuine (Verification), allocate a desk, a laptop and an empty mailbox (Preparation), and replace "reports to the London finance manager" with an actual named person's badge number (Resolution). Initialization is the first day: the desk gets filled, the passwords get set, the defaults become real values.

The ordering matters and is fixed by the specification. You cannot run the static initialiser before the storage exists, and you cannot allocate storage for a type nobody has verified. Everything confusing about static state in Java — null in a static field, deadlocking class initialisation, the holder idiom being thread-safe for free — falls out of where in this sequence you happened to look.

Loading — bytes become a type

The loader reads the byte stream, checks the 0xCAFEBABE magic and the version, parses the constant pool and the method table, and builds an InstanceKlass in Metaspace. From this moment MathWizard exists as something the JVM can talk about. Superclasses are loaded first, recursively — you cannot describe a type without describing what it extends.

Metaspace is native memory, not the heap. It holds the description of your classes: one copy, shared by every instance you will ever create. That is why loading thousands of generated classes can exhaust Metaspace while your heap graph looks perfectly healthy — and why the Class<MathWizard> mirror object you get from getClass() is a separate, ordinary Java object that does live on the heap.

Linking ① Verification — why Java can run code it did not compile

Anybody can hand-write a .class file. The compiler is not a security boundary — it is a convenience. So before trusting a single instruction, the verifier statically proves properties over every possible execution path: the operand stack never underflows or overflows, types line up at every merge point, every jump lands on a real instruction boundary, final methods are not overridden, and every method returns the type it claims.

The payoff is speed, not just safety. Because those properties are proven once, up front, the interpreter and the JIT can skip checking them on every one of ten million iterations. Verification is the reason the fast path is allowed to be fast. Try the "corrupted bytecode" button above: an iadd with one value on the stack is rejected before execution begins, with VerifyError.

Linking ② Preparation — the phase that explains half your NPEs

Storage for static fields is allocated and set to specification default values: 0, 0L, false, '\u0000', null. No user code runs. Your initialiser = 15000 has not executed yet; the slot holds 0.

Notice the one exception on screen: a static final field with a compile-time constant is given its real value during preparation, not initialisation, because the value lives in the ConstantValue attribute rather than in <clinit>. That is a genuinely different mechanism, and it is the root of the stale-constant problem from Stage 01.

Linking ③ Resolution — names become addresses

Every symbolic reference in the constant pool is looked up and replaced with a direct pointer. Crucially this is lazy in HotSpot: each entry is resolved at the first instruction that actually uses it, not all at once. That is a startup optimisation with a real consequence — a missing dependency does not fail at launch; it fails hours later, the first time that one code path runs.

Initialization — <clinit> runs, exactly once

Now the static initialisers execute, in source order, merged into the single synthetic method <clinit>(). The JVM holds a per-class initialisation lock while this runs, and it is re-entrant for the initialising thread. Two facts follow, both of them interview favourites: the initialization-on-demand holder idiom is thread-safe with no synchronized anywhere, and circular static initialisation can deadlock or silently observe zero-defaults, because a re-entrant thread is allowed to proceed on a half-initialised class.

If <clinit> throws, the class is marked erroneous permanently. The first failure surfaces as ExceptionInInitializerError with the real cause attached; every later access to the same class throws a bare NoClassDefFoundError with no cause at all. When you see that pair in a log, always scroll up for the first one — that is where the actual bug is.

Interview drill · stage 03 Questions they actually ask about loading, linking & initialization

What are the exact phases of the class lifecycle, and which of them run user code?

Loading → Linking (Verification, Preparation, Resolution) → Initialization → Using → Unloading.

Only Initialization runs your code. Everything before it is the JVM constructing and validating a description. The interviewer is usually probing whether you know that Preparation happens before Initialization — that is the seam where static fields hold zeros and where half the surprising behaviour lives.

Worth adding: Resolution is the one phase whose timing the specification deliberately leaves open. HotSpot does it lazily; a different VM could do it eagerly and still be conformant.

Why is the initialization-on-demand holder idiom thread-safe without any synchronization?

Because the JVM already holds a lock for you. Class initialisation is specified (JLS §12.4.2) to happen under a per-class initialisation lock, exactly once, with the correct memory-visibility guarantees.

So in:

  • private static class Holder { static final Singleton INSTANCE = new Singleton(); }
  • public static Singleton get() { return Holder.INSTANCE; }

Holder is not initialised until get() first touches Holder.INSTANCE — lazy, for free. And when it is, the JVM serialises competing threads and publishes the result safely — thread-safe, for free, with zero synchronisation cost on subsequent reads, unlike double-checked locking with volatile.

The follow-up they want: an enum singleton gets the same guarantee by the same mechanism, plus serialisation safety.

Scenario · Two classes have static fields initialised from each other. Depending on which class is touched first, one of them ends up null — but there is no exception. Explain and fix.

Classic circular static initialisation. Say A has static B b = B.INSTANCE; and B has static A a = A.INSTANCE;.

What happens: thread touches A → JVM marks A "being initialised by this thread" and starts <clinit> → that reads B.INSTANCE, so B initialises → B's <clinit> reads A.INSTANCE. The JVM sees A is already "in progress on this same thread", and the specification says a re-entrant thread must proceed, not block (blocking would be a guaranteed deadlock). So B reads A.INSTANCE while A's initialiser is only half-done and gets the Preparation default: null. B completes, A completes, and B.a is permanently null. No exception is thrown — the JVM did precisely what it promised.

Touch B first and the null lands on the other side. That is why the bug appears to depend on class-loading order, request order, or "only in production".

How to spot it: a static field that is null despite an initialiser that obviously assigns it. Confirm with -Xlog:class+init=info and read the interleaving.

Fixes: break the cycle — move shared state into a third class that neither initialises the other; make one side lazy behind an accessor method (B.instance() instead of B.INSTANCE); or use the holder idiom so initialisation is deferred to first real use. Static-initialiser cycles are one of the few places where "just use dependency injection" is a genuinely correct answer, because a container resolves the graph explicitly rather than by accident.

Bonus: the same mechanism can deadlock — if two different threads each start initialising one of the two classes, each blocks on the other's initialisation lock. That deadlock does not appear in a thread dump as a Java monitor; you will see threads parked in Class.forName0 or in-class-initialization, which is the giveaway.

Scenario · You add a Java agent (APM, coverage, mocking) and the app dies at startup with java.lang.VerifyError: Expecting a stackmap frame at branch target. Diagnose it.

The agent rewrote bytecode and produced a class that no longer passes verification. The specific message names the mechanism: since class version 50 (Java 6) the verifier uses StackMapTable — a precomputed type map at each branch target, so verification is a single linear pass rather than an expensive dataflow fixpoint. If an instrumentation library inserts instructions and does not recompute those frames, the map no longer matches the code.

Diagnose:

  • Read the class name in the error — is it yours, a library's, or a JDK class? That tells you whose transform broke.
  • Remove agents one at a time. Two agents transforming the same class in sequence is a very common trigger, and the pair may work fine individually.
  • Check versions: an ASM version that predates your target bytecode level literally cannot parse it. This is the single most frequent root cause.
  • Dump the transformed bytes and run javap -v or a CheckClassAdapter over them to see the malformed method.

Fix properly: upgrade the agent/ASM to one that understands your class-file version, and ensure the transform uses COMPUTE_FRAMES (with a correct getCommonSuperClass that can see the right loader) so the map is regenerated.

What not to do: -Xverify:none / -noverify "fixes" it by disabling the safety net. It is deprecated and ignored on modern JDKs, and on older ones it converts a clean startup failure into an unpredictable runtime crash. Say this out loud in an interview — recognising that the workaround is worse than the bug is the actual signal they are testing for.

Scenario · A microservice's p99 latency spikes to 4 seconds every time a rarely-used endpoint is first called after deploy — then it is fine forever. Nothing in the code is slow. What is going on?

Two lazy mechanisms compounding, and both live in this stage:

  • Lazy class loading + linking. That endpoint's class graph — the controller, the DTOs, the serialiser, the JDBC path, the validation framework — is loaded, verified and initialised on the first request that touches it, and that request pays for all of it. Hundreds of classes, each read from a JAR, parsed, verified, and initialised.
  • Lazy resolution + cold JIT. Every constant-pool entry on that path resolves on first use, and every method runs interpreted at Tier 0 until counters build up (Stage 05).

Confirm it in one run: -Xlog:class+load=info:file=cl.log and check whether a burst of loads coincides with the slow request. -Xlog:class+init and JFR's "Class Loading" event give the same story with timings.

Fixes, roughly in order of value:

  • AppCDS (-XX:SharedArchiveFile, or -XX:+AutoCreateSharedArchive on JDK 19+): pre-parses classes into a memory-mappable archive shared across processes. Class loading, not GC or JIT, dominates JVM startup — this is the highest-leverage fix.
  • Warm-up traffic before the instance enters the load balancer: synthetic requests over every endpoint. Crude, and extremely effective.
  • Move initialisation out of the request path — eager-init the beans/serialisers you know you need at boot rather than lazily.
  • If the process is genuinely short-lived, this whole class of problem is the argument for AOT / native image (Stage 06).

The sentence that lands in an interview: "the first request pays for everything the JVM deferred — and the JVM defers by design, because deferring is what makes startup fast for the paths you never call."

Common Interview Trap "Loading a class runs its static initializer." Loading only builds the type. <clinit> runs at Initialization — a separate, later, lazily-triggered phase. A class can sit fully loaded, verified, prepared and linked for the entire life of the process and never be initialised, if nothing ever actively uses it. This is exactly why loader.loadClass("com.mysql.Driver") never registered a JDBC driver but Class.forName("com.mysql.Driver") did.
