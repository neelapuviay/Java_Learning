01

javac turns source into portable bytecode — and stops there

ahead-of-time, once

The Java compiler never produces machine code. It checks syntax and types, then emits bytecode: instructions for an imaginary CPU that does not exist in hardware. That is the whole trick behind "write once, run anywhere" — and the reason a second compiler (the JIT) has to exist later.

MathWizard.javajavac 17
public class MathWizard {

    static final int TOTAL = 15000;
    static int[] cache;

    static { cache = new int[8]; }      // static initializer

    public static void main(String[] args) {
        int result = 0;
        for (int i = 0; i < TOTAL; i++) {
            result = accumulate(result, i);
        }
        System.out.println(result);
    }

    static int accumulate(int balance, int item) {
        return balance + item;
    }
}

Why doesn't javac just optimize the code properly, so no JIT is needed?
Because javac has no idea what will actually happen at run time. It cannot know which branch is taken 99% of the time, which concrete class a variable will hold, how many times a loop runs, or which CPU the code will land on. It also must not change observable behaviour. So javac does only trivial work — constant folding of static final, string concatenation desugaring, generic type erasure — and leaves real optimization to the JIT, which can measure instead of guess.
Common wrong answer "Bytecode is machine code for the JVM, so it's already optimized." Bytecode is a portable instruction set for a stack machine that no physical CPU implements. Real CPUs are register machines. Every bytecode must either be interpreted (slow) or translated to real machine instructions by the JIT (fast).
02

The Class Loader Hierarchy — Before Java 9 vs. The Modular JDK

architecture, security & JPMS

Before the JVM can link, verify, or allocate memory for a class, it must locate and read its byte stream using ClassLoaders. In Java 8 and earlier, the JVM relied on a monolithic runtime (rt.jar) and global drop-in extension folders (lib/ext). Starting with Java 9 (Project Jigsaw / JPMS), this was fundamentally re-engineered: the extension mechanism was completely removed, rt.jar was decomposed into discrete modules, and the Platform ClassLoader was introduced to enforce the Principle of Least Privilege.

2.1 · extension vs platform1. Extension ClassLoader → Platform ClassLoader (True)

Java 8 & EarlierLegacy

• Implemented internally by sun.misc.Launcher$ExtClassLoader (a URLClassLoader).

• Loading mechanism: Scanned and automatically loaded any JAR placed in <JAVA_HOME>/lib/ext or specified by the java.ext.dirs system property.

• Flaw: Implicit, unversioned drop-in mechanism that caused silent classpath collisions across all applications sharing the JRE.

Java 9+ Modular JDKModern (JPMS)

• Implemented internally by jdk.internal.loader.ClassLoaders$PlatformClassLoader.

• Extension mechanism removed: The lib/ext directory and java.ext.dirs property were completely eliminated from the JDK.

• New Role: A built-in module loader that loads selected standard Java SE platform and JDK-specific modules (e.g., java.sql, java.compiler, java.xml, java.desktop) not in java.base. Accessible via ClassLoader.getPlatformClassLoader().

2.2 · terminology clarity2. System ClassLoader vs. Application ClassLoader (Partially True / Interchangeable)

Key Clarification: They refer to the exact same ClassLoader System ClassLoader and Application ClassLoader describe the exact same class loader instance across all Java versions:
  • In official Java API & Specifications: It is accessed programmatically via ClassLoader.getSystemClassLoader().
  • In JVM documentation & architecture: It has always been commonly called the Application ClassLoader because its primary responsibility is loading user application classes and dependencies from the classpath (-cp) or module-path (--module-path).
  • Internal HotSpot class: In Java 8 it was sun.misc.Launcher$AppClassLoader; in Java 9+ it is jdk.internal.loader.ClassLoaders$AppClassLoader.
  • It was not renamed from "System" to "Application" in Java 9; both terms were and still are used interchangeably.

2.4 · architectural driversWhy the Java 9 Transition Happened (Project Jigsaw)

The transition from the Extension ClassLoader to the Platform ClassLoader and the division of standard Java modules between the Bootstrap ClassLoader and Platform ClassLoader was driven by three key architectural and security goals:

1. Remove lib/ext FlawJAR Hell Fix

The Problem: In Java 8, any JAR placed in <JAVA_HOME>/lib/ext was automatically loaded across all applications running on that JRE. This caused severe "JAR hell," classpath conflicts, and silent version collisions (e.g., if a shared server had an outdated library in ext/, it silently overrode an application’s newer dependency).

The Fix: Java 9 completely eliminated the extension mechanism in favor of explicit module declarations (module-info.java), --module-path, and explicit dependencies.

2. Deconstruct rt.jarCloud & Containers

The Problem: Prior to Java 9, all runtime classes — from core primitives and collections to desktop UI (AWT/Swing), SQL, XML, and legacy CORBA — lived inside a single, massive rt.jar loaded entirely by the Bootstrap ClassLoader. The runtime could not be scaled down for microservices, containers, or embedded systems.

The Fix: Project Jigsaw decomposed the JDK into dozens of discrete modules (java.base, java.sql, java.xml, java.desktop).

3. Custom Runtimesjlink Images

The Advantage: Because modules are decoupled from the monolithic bootstrap runtime, developers can use jlink to package only the modules their specific application requires.

Result: You can create a ~30 MB custom runtime image containing only java.base and java.logging for a cloud microservice instead of deploying the full 200+ MB JDK.

Deep Dive: Why Not Load All Modules in the Bootstrap ClassLoader? Splitting modules between the Bootstrap ClassLoader and the Platform ClassLoader serves specific purposes:
A. Principle of Least Privilege & Security Classes loaded by the Bootstrap ClassLoader are granted full, unrestricted security permissions by default (AllPermission) and operate at the highest privilege level within the JVM.
Subsystems like XML processing, SQL, networking, or desktop UI do not need full native/bootstrap-level privileges. Moving non-essential platform modules (like java.sql, java.xml, java.compiler) to the Platform ClassLoader creates a cleaner security boundary and limits the attack surface.
B. Clear Architectural Separation (java.base vs. the Rest) Bootstrap ClassLoader: Loads strictly the foundational core runtime module (java.base), which contains essential JVM types (Object, String, Class, basic I/O, concurrency primitives) that the JVM must have to boot up.
Platform ClassLoader: Loads other standard Java SE platform modules and JDK-specific modules (e.g., java.desktop, java.net.http, java.transaction.xa).
Application ClassLoader: Loads user code and third-party libraries from the classpath or module path.

Why does String.class.getClassLoader() return null in both Java 8 and Java 9+?
The Bootstrap ClassLoader is implemented in native C++ inside HotSpot, not as a Java object instance of java.lang.ClassLoader. In Java API design, null represents the Bootstrap ClassLoader. This is why calling getClassLoader() on any core bootstrap class (e.g. Object.class, String.class, Integer.class) returns null, and why a custom classloader created with a null parent delegates directly to Bootstrap.
Is the Platform ClassLoader just the Extension ClassLoader under a new name?
No. The Extension ClassLoader was a URLClassLoader that scanned an arbitrary directory on disk (lib/ext) and loaded any JAR placed there. The Platform ClassLoader (jdk.internal.loader.ClassLoaders$PlatformClassLoader) is a built-in modular class loader integrated with the Java Platform Module System. It does not scan arbitrary folders; it specifically resolves non-base standard Java SE platform modules (java.sql, java.xml, etc.) and JDK modules according to module graph dependencies.
Why did Java 9 isolate non-core standard modules to the Platform ClassLoader instead of Bootstrap?
Principle of Least Privilege and Security Boundaries. Classes loaded by the Bootstrap ClassLoader are automatically granted all JVM security permissions (AllPermission). By placing complex, non-essential platform modules like XML parsers, SQL database bridges, and UI toolkits into the Platform ClassLoader, the JVM limits the high-privilege attack surface and decouples them so that custom lightweight runtimes can be created with jlink.
Common wrong answer "Java 9 removed the Bootstrap ClassLoader in favor of the module system." The Bootstrap ClassLoader still exists in all modern Java versions. What changed in Java 9 was its scope: instead of loading all standard Java classes from a monolithic rt.jar, it now strictly loads the core foundational module java.base and native boot essentials.

The JVM has to build the class in memory before any code can run

nothing has executed yet

Your .class file is just bytes on disk. The JVM cannot run bytes on disk — it has to fetch them, check them for danger, carve out memory for them, wire up the names inside them, and finally run your static setup code. That is what "loading, linking, initialization" actually means. Press Play and watch it happen frame by frame.

The mental model to keep A new employee joining a company. Loading = HR receives their file and creates a record. Verification = security background check before they get in the building. Preparation = a desk is allocated, drawers empty. Resolution = the names on their contact list get turned into real desk locations. Initialization = day‑one setup where they actually fill their drawers. Only after all of that does the person start doing work — that's main().

The trap almost everyone falls into Preparation ≠ Initialization. During preparation the JVM only reserves slots and fills them with default values — 0, 0.0, false, null. Your static int[] cache = new int[8]; has not run yet. The real value only appears during initialization, when <clinit> executes. Watch the "Static fields" box change from null to int[8] — that gap is the whole point.
When does all this even trigger? Lazily, on first active use — the first new, the first static method call, the first non‑constant static field read. Classes are not loaded when the JVM starts. And a class is initialized exactly once, with the JVM holding a lock so two threads can never both run <clinit>. That guarantee is why the "static holder" singleton idiom is thread‑safe for free.
Explain the parent-delegation model and why it matters.
When a loader is asked for a class it first asks its parent, all the way up to Bootstrap, and only searches its own path if every ancestor failed. Two consequences: (1) security — you cannot shadow java.lang.String by putting your own copy on the classpath, because Bootstrap is always asked first; (2) uniqueness — a class's runtime identity is name + defining loader, so the same com.acme.Order loaded by two loaders is two distinct types. That is how app servers isolate deployments, and why you occasionally see ClassCastException: Order cannot be cast to Order.
Which of loading / linking / initialization can throw, and what?
Loading → ClassNotFoundException (reflective lookup failed) or NoClassDefFoundError (it was there at compile time, missing now). Verification → VerifyError. Preparation → nothing, it is pure allocation. Resolution → NoSuchMethodError, NoSuchFieldError, IllegalAccessError, thrown lazily at first use. Initialization → anything your <clinit> throws, wrapped in ExceptionInInitializerError; after that the class is marked erroneous and every later use throws NoClassDefFoundError.
Common wrong answer "ClassNotFoundException and NoClassDefFoundError are the same thing." They are not. ClassNotFoundException is a checked exception from an explicit lookup — Class.forName("…"). NoClassDefFoundError is an Error meaning the class was present when you compiled but the JVM cannot find or initialize it now — often because its <clinit> blew up earlier.

The interpreter executes bytecode one instruction at a time

always correct, always slow

The JVM is a stack machine: values are pushed onto an operand stack, instructions pop what they need and push results back. The interpreter is a loop that fetches a byte, decides what it means, and does it — every single time, even the ten‑thousandth time. That repeated decode-and-dispatch is the cost the JIT exists to eliminate.

Why is a stack machine used for bytecode instead of registers?
Because bytecode has to be portable and compact. A register machine's instructions must name registers, and different CPUs have different numbers of them — so the bytecode would be tied to a specific architecture. A stack machine needs no operand names at all: iadd is one byte and always means "pop two, push the sum". The cost is that stack code is slower to execute directly, which is fine, because the JIT converts it into real register-based machine code anyway.
Common wrong answer "The interpreter is used only until the JIT kicks in, then it's gone." The interpreter runs for the entire life of the JVM. Most methods in a real application never get hot enough to be compiled, so they stay interpreted forever. The interpreter is also the fallback target for deoptimization, and it is what runs during class initialization and at startup.
05

Every method carries its own heat counters

the profiler runs alongside the interpreter

HotSpot never guesses which code is worth optimizing — it measures. Two counters live on every method: an invocation counter (how many times was this method called) and a back‑edge counter (how many times did a loop inside it jump backwards). Cross a threshold and a compile request is queued. The interpreter also records what kinds of values it saw — which types arrived at each call site, which branches were taken — and that profile is what makes C2's aggressive optimizations possible.

Editing a value resets the run. Real HotSpot defaults are higher and version‑dependent (-XX:Tier3InvocationThreshold=200, -XX:Tier4InvocationThreshold≈15000) and are also scaled dynamically by how busy the compiler queues are — these are shrunk for a live demo.

The part people forget: it is not just counting Alongside the counters, tier‑3 (C1‑with‑profiling) code records a type profile per call site and a branch profile per if. That is the raw material for C2: "this call site saw only ArrayList in 12,000 calls", "this null check never fired", "this branch went left 99.8% of the time". C2 then compiles code that assumes those facts and guards them cheaply. No profile, no speculation — which is exactly why a JVM is slow for the first second and fast afterwards.
What is the difference between the invocation counter and the back-edge counter, and why do we need both?
The invocation counter fires when a method is called often — the natural moment to swap in compiled code is the next call. But a method might be called only once and still spend minutes inside a loop, like main(). Nothing would ever trigger. So the back‑edge counter counts backward jumps (loop iterations); when it crosses the threshold, HotSpot compiles and uses On‑Stack Replacement to swap native code into the frame that is already executing, mid‑loop. Both counters are needed because "hot" can mean called-a-lot or looping-a-lot.
Common wrong answer "The JIT compiles a method after exactly 10,000 invocations." There is no single fixed number. With tiered compilation the tier‑3 (C1) threshold is a few hundred, the tier‑4 (C2) threshold is in the thousands, and both are adjusted at run time based on compiler queue length. Counters can also decay. Quote the mechanism, not a magic number.

The JIT compiler, C1 and C2 — from first principles

the heart of HotSpot

This is the part that is usually explained badly, so we build it from zero. Four questions, in order: What is a JIT and why does Java need one? → What are C1 and C2, literally? → When does each one run? → What does a compiler actually do to your code? Each has its own animation.

6.1 · the reason it existsWhy does Java need a compiler at run time?

The insight that makes the JIT worth its cost A JIT is not just "an interpreter that got faster". It can produce code an ahead-of-time compiler cannot legally produce, because it knows things that are unknowable before the program runs:
• Which types actually show up. AOT sees List<Order> list and must emit a virtual dispatch. The JIT observes 50,000 calls that were all ArrayList, so it inlines ArrayList.get directly and just guards the type with one compare.
• Which branches are cold. The JIT moves never-taken branches out of the hot path entirely, so your instruction cache holds only code that runs.
• Which CPU it is on. AOT must target a baseline instruction set; the JIT emits AVX‑512 if the machine has it.
• What is dead. Whole configuration branches, logging guards and null checks that are provably unreachable in this deployment get deleted.
And the price you pay for it Warm-up. For the first seconds a JVM is slower than the equivalent C program, because it is interpreting and compiling at the same time — the compiler is stealing CPU from your application. That is the entire reason short-lived processes (CLI tools, serverless functions) look bad on the JVM, and why GraalVM native-image and Project Leyden exist: they trade the JIT's knowledge for instant startup.
What is "JIT compilation" in one paragraph?
Just-in-time compilation means translating bytecode into native machine code while the program is running, driven by measurements of what the program is actually doing. The JVM starts by interpreting so it can begin instantly, counts how often each method and loop runs, and hands the hot ones to a compiler on a background thread. The compiler uses the collected profile to emit specialised machine code, installs it in the code cache, and future calls jump straight to it. Because the assumptions come from observation rather than proof, the JVM also keeps the ability to throw the compiled code away — deoptimize — if reality changes.

6.2 · the two compilersWhat C1 and C2 actually are

C1 and C2 are two separate compilers written in C++ that ship inside the JVM binary. They are not tools you run; they are threads inside your Java process, called C1 CompilerThread0, C2 CompilerThread0 and so on — you can see them in a thread dump. Both take bytecode in and produce machine code out. They differ in one thing: how much time they are willing to spend.

The names are historical. C1 was the "client" compiler, built for desktop apps where startup time is what the user notices. C2 was the "server" compiler, built for long-running servers where only steady-state throughput matters. Before Java 8 you picked one with -client or -server. Since Java 8, tiered compilation uses both, automatically: C1 for the quick win, C2 for the peak.

Why keep C1 at all — why not go straight to C2?
Two reasons. Latency: C2 is slow to compile, so if you wait for C2 the method stays interpreted (roughly 20× slower) for the whole compile. C1 gives you ~5× within a millisecond, which covers the gap. Data: C2 needs a profile to speculate, and the tier‑3 C1 code is what collects that profile efficiently — the interpreter's profiling is slower. So C1 buys time and gathers evidence; C2 spends the evidence. Interview one-liner: "C1 optimizes for how soon, C2 optimizes for how fast."
Common wrong answer "C1 and C2 are two stages of one compiler — code goes through C1 and then through C2." They are independent compilers. C2 does not consume C1's output; it recompiles the original bytecode from scratch, using the profile data that C1's instrumented code collected. When C2's version is installed, C1's version is thrown away.

What each step means for you as a developer 1. Counter crosses the threshold → a compile task is enqueued with the method and the target tier. 2. Common wrong answer "JIT compilation causes stop-the-world pauses." It does not — GC does that, not the JIT. Compilation happens on separate threads and only competes for CPU. Two related real effects exist though: installing compiled code needs a safepoint (very brief), and -Xbatch/-Xcomp deliberately make compilation synchronous for benchmarking.

6.5 · inside the black boxWhat "optimizing" actually does to your code

A compiler does not read your source. It builds a graph of operations and dependencies, then rewrites that graph. 6.7 · the optimizations, explained properlyWhat C2 does once it has your graph

Each of these gets the same four questions answered before the animation: what is it, what problem does it solve, why can only a JIT do it, and what stops it working. These five are the ones interviews actually ask about.

① Inlining — replacing a call with the callee's body

the most valuable optimization there is
inlining OFF
What it is

The compiler deletes the call to accumulate() and pastes its body straight into the loop. The method still exists; the call stops existing.

What problem it solves

Calling a method is not free. The CPU must push arguments, save a return address, allocate a frame, jump, run the body, tear the frame down and jump back. When the body is a + b, that bookkeeping costs more than the work.

Why only a JIT can do it well

Most Java calls are virtual — the target depends on the runtime type, so javac cannot know what to paste. The JIT looks at the type profile, sees that one class showed up 50,000 times, and inlines that one with a cheap type guard. That is speculative devirtualization, and it requires runtime knowledge.

What stops it

Method too big (-XX:MaxInlineSize=35 bytes, or FreqInlineSize=325 when hot), the call site is megamorphic (many types), recursion depth, the caller already being huge, or native/synchronized-with-contention bodies.

② Monomorphic inline cache — devirtualizing the dispatch

polymorphism at native speed
What it is

Java methods are virtual by default (invokevirtual). A normal virtual call looks up the target in a vtable at run time. An inline cache replaces that lookup with a direct call guarded by a single pointer comparison: if (obj.klass == Fast) Fast::draw().

What problem it solves

Vtable lookups mean two dependent memory reads and an indirect branch that the CPU cannot easily predict. Inline caches turn that into one direct compare-and-jump.

Why only a JIT

Only the JIT knows which concrete classes actually arrive. 95% of real-world call sites see exactly one receiver type in production (monomorphic), even when dozens exist in the class hierarchy.

What stops it

Passing three or more distinct concrete implementations to the same call site — turning it megamorphic. At that point HotSpot gives up, falls back to a full vtable lookup, and inlining becomes impossible.

③ Loop unrolling — fewer jumps, wider pipeline

reducing loop overhead
unroll 1×
What it is

C2 duplicates the loop body 2, 4, 8 or 16 times, increments i by that factor, and handles the remainder in a "post-loop".

What problem it solves

A loop does two things per iteration: the work, and the loop bookkeeping (i++, compare i < N, conditional jump). If the work is small, bookkeeping is half the time. Unrolling by 4 divides that overhead by four.

Why only a JIT

C2 unrolls based on the measured trip count and the exact CPU's instruction-cache size. Too much unrolling pollutes the L1 instruction cache; too little wastes CPU pipeline slots. The JIT balances both.

What stops it

Complex loop bodies that would blow the unroll budget (-XX:LoopUnrollLimit=60), non-counted loops (e.g. while(iterator.hasNext())), or loops containing non-inlined calls.

④ Escape analysis & scalar replacement — objects that never exist

no heap · no GC · no overhead
What it is

C2 proves an object never "escapes" the method — it is not returned, not stored in a field, not passed to an un-inlined method. It then deletes the allocation entirely: the object header is gone, and its fields become raw local variables held in CPU registers. This is scalar replacement.

What problem it solves

Not the allocation itself — that is a pointer bump. It solves everything downstream: heap filling up, GC pauses, and fields living in RAM instead of registers so every read risks a cache miss.

Why only a JIT

The proof requires seeing every use of the reference — which usually means seeing through several method calls. Only after inlining is that possible, and inlining decisions need the runtime profile. Chained back to 6.7①: no inlining, no escape analysis.

What stops it

Storing the reference in a field or static, returning it, passing it to a method that could not be inlined, or putting it in a collection. Arrays whose size is not a compile-time constant also usually block scalar replacement.

⑤ Auto-vectorization — four adds in the time of one

C2 · SIMD · -XX:+UseSuperWord
What it is

Your CPU has wide registers (128/256/512 bit) that hold several numbers side by side, and instructions that operate on all of them in one cycle. If C2 can prove four iterations are independent, it packs them into a single vpaddd.

What problem it solves

Hardware you already paid for sitting idle. A scalar add uses 32 bits of a 512-bit register — 94% of the CPU's width wasted on every instruction.

Why only a JIT

It knows the exact CPU. The same bytecode gets SSE on an old machine, AVX2 on a newer one, AVX‑512 or NEON elsewhere — decided at run time, from cpuid. An AOT binary must target the oldest CPU it might land on.

What stops it

Any dependency between iterations, a branch inside the loop, a call that could not be inlined, array bounds it cannot prove, or unaligned/aliasing accesses. This is why superficially identical loops can differ 4× in speed.

6.8 · the rest of the toolboxFive more you should be able to name

Intrinsicshand-written assembly

Some methods are too important to compile from bytecode. Math.sqrt, System.arraycopy, String.indexOf, Integer.bitCount, Objects.hash, the atomics — HotSpot replaces the call with a hand-written machine-code template that uses a single CPU instruction where one exists. That is why you should never "optimize" these by writing your own loop: you lose the intrinsic. See them with -XX:+PrintIntrinsics.

Range-check eliminationarrays

Java checks every array index. In for (int i=0;i<a.length;i++) a[i]… C2 proves i can never leave [0, a.length) and deletes the check from the loop body entirely, sometimes hoisting one check before the loop. This is why idiomatic indexed loops in Java run at C speed — and why an unusual bound like i <= a.length-1 mixed with other arithmetic can accidentally defeat it.

Loop-invariant code motionhoisting

Anything inside a loop whose result cannot change is computed once, before the loop. for(…){ x = a.length * 2; … } becomes one multiplication. This is also why writing manual "optimizations" like hoisting list.size() yourself usually changes nothing — C2 already did it, provided the call was inlinable.

Lock elision & coarseningsynchronization

If escape analysis proves an object never leaves the thread, its synchronized blocks protect nothing and are removed. Adjacent locks on the same object are merged into one. This is why StringBuffer used in a single method performs like StringBuilder after warm-up. (Biased locking, a related optimization, was deprecated in 15 and removed in 18.)

Dead code & constant foldingthe basics

Results nobody reads are deleted; arithmetic on known values is computed at compile time; branches whose condition is provably constant are removed together with the code inside them. After inlining a config-flag check like if (DEBUG), the whole block often vanishes. This is also a benchmarking hazard: if your benchmark never uses the result, C2 deletes the whole computation — which is exactly why JMH's Blackhole exists.

On-stack replacement (OSR)swapping mid-flight

A long loop inside a method that is only called once — like main() — would never benefit, because compiled code normally takes effect on the next call and there is no next call. OSR compiles a special entry point that can take over from the middle of a running loop, rebuilds the frame in the compiled layout, and continues. Watch it happen by choosing loop model B in Stage 04.

Give a complete answer to "how does the JIT compiler work?"
"Java compiles to bytecode ahead of time, and the JVM starts by interpreting it so startup is instant. While interpreting it counts invocations and loop back-edges per method, and records type and branch profiles. When a method crosses a threshold, a compile task is queued and a background compiler thread picks it up — the application never blocks. HotSpot has two compilers: C1 compiles in about a millisecond with light optimization and adds profiling, giving roughly 5×; C2 spends far longer building a sea-of-nodes graph and applying inlining, escape analysis, loop transforms and vectorization using the collected profile, giving 10–50×. The result, an nmethod, is installed in the code cache and the entry point is patched. Because C2's optimizations are speculative — 'this call site only ever saw ArrayList' — every compiled method records how to reconstruct interpreter state, so if an assumption breaks the JVM deoptimizes, falls back to the interpreter, and recompiles without that assumption. This is called tiered compilation, and it is why the JVM is slow for the first second and can then beat statically compiled code."

Safepointsthe link to garbage collection

Compiled code contains safepoint polls — cheap checks placed at method returns and loop back-edges. When the JVM needs all threads stopped (for GC, for deoptimization, for a thread dump) it flips a flag and waits for every thread to reach its next poll.

Consequence worth knowing: a long int-counted loop that C2 decided needed no poll can delay a GC for a surprisingly long time — the infamous "time to safepoint" problem. Diagnose with -XX:+PrintSafepointStatistics or JFR.

Why a "downgrade" is the clever part An ahead-of-time compiler can never assume "this variable is always an ArrayList" — it must handle every legal case, so it emits slower, defensive code. HotSpot is allowed to bet on what it observed because it keeps a way out: every compiled method stores a map describing how to rebuild the exact interpreter state at each safepoint. Being able to undo an optimization is what makes aggressive optimization safe.
Name concrete things that cause a deoptimization.

The two rules that answer every "where does it live?" question 1. Objects are always on the heap; references may be anywhere. Order o = new Order(); creates one object on the heap and one 4/8-byte reference in the current frame's local variable slot. The variable is on the stack, the object never is.

In HotSpot, a static int lives with the heap-resident java.lang.Class mirror, while its definition and offset live in Metaspace. There is no single answer for "where do primitives live" — that is the trap in the question.

"Where is the String pool, and what does intern() do?"
Since Java 7 the string pool is a hash table in the Java heap (before that it lived in PermGen, which is why interning used to cause OutOfMemoryError: PermGen space). Every string literal in your code is automatically interned at class load, so "PAID" == "PAID" is true. new String("PAID") deliberately creates a separate heap object, so == is false while equals is true. intern() returns the pooled instance, adding it if absent. Because the pool is in the heap, its entries are garbage collectable.
"What replaced PermGen and why?"
Metaspace, in Java 8. PermGen was a fixed-size region inside the Java heap, so class metadata competed with your objects for space and needed a fixed -XX:MaxPermSize that was impossible to size correctly — the classic symptom being OutOfMemoryError: PermGen space after a few hot redeploys. Metaspace lives in native memory and grows on demand, so the default is effectively unlimited. It can still leak: metaspace is freed per-classloader, so a leaked ClassLoader keeps every class it defined alive forever. Cap it with -XX:MaxMetaspaceSize so a leak fails fast instead of eating the machine.
Common wrong answer "-Xmx4g means the JVM uses at most 4 GB." It caps the Java heap only. Total process memory is heap + metaspace + code cache + thread stacks + direct buffers + GC structures + the JVM's own native allocations. This is the single most common reason a container gets OOM-killed by the kernel while heap graphs look perfectly healthy — and why you should prefer -XX:MaxRAMPercentage in containers.

Garbage collection — what it collects, and what it costs you

the other half of JVM performance

Java has no free(). Instead the JVM periodically works out which objects your program can still reach, and reuses the memory of everything else. Three things to understand, in this order: how it decides what is garbage, why it splits the heap by age, and how the four collectors differ in when they stop your application.

9.1 · what counts as garbageReachability, not reference counting

An object is garbage if it cannot be reached by following references from a GC root. Roots are the places execution can start from: local variables in every live stack frame, static fields, JNI references, active thread objects, held monitors and class loaders. Two consequences worth stating out loud in an interview 1. Reference cycles are not leaks. Objects E and F point at each other but nothing points at them, so both are collected. A reference-counting system (C++ shared_ptr, CPython) would leak that pair forever. Tracing from roots is immune to cycles — this is a genuine advantage of the JVM's design.
2. Cost scales with live data, not garbage. The collector only touches objects it can reach. Ten million dead objects cost nothing to "delete"; the memory is simply reused. This is why allocation-heavy code with short-lived objects is fast in Java, and why a huge heap full of live objects is slow to collect.
Common wrong answer "Setting a variable to null frees the object." It only removes one reference. The object is collectable when no path from any root reaches it — and if it is a local variable in a method that is about to return, nulling it changes nothing at all. Equally, finalize() is deprecated and unreliable, and System.gc() is only a hint the JVM may ignore entirely (and -XX:+DisableExplicitGC makes it a no-op).

9.2 · why the heap is split by ageThe weak generational hypothesis

One empirical observation drives almost every GC design: most objects die very young. A request handler creates hundreds of temporary objects that are all garbage a millisecond later, while the few objects that survive their first collection tend to survive for a long time. So the heap is split: a small young generation collected often and cheaply, and a large old generation collected rarely and expensively.

What just happened, in the words you want in an interview A minor GC (also called a young collection) is a copying collector, and it is stop-the-world but very short. It traces from the roots, and every object it finds alive in Eden or the in-use survivor space is copied into the other survivor space with its age counter incremented. Everything not copied is dead by definition, so Eden and the old survivor space are declared empty in one stroke — no per-object cleanup. Once an object's age passes -XX:MaxTenuringThreshold (default 15) it is promoted to the old generation instead. Objects too large for Eden are allocated directly in old space.
Why two survivor spaces? So the copy always has an empty destination. One is always the "to" space and one the "from" space, and they swap every collection. Copying into empty space means the result is automatically compacted — no fragmentation, and allocation stays a pointer bump. The price is that half the survivor capacity is idle at any moment.
Where the pauses actually come from Minor GC pause length is proportional to how much survives, not to the size of Eden. A high survival rate is the real enemy: objects get copied repeatedly, then promoted early ("premature promotion"), which fills the old generation and forces expensive old collections. If you only remember one tuning fact: a healthy young collection reclaims 90–98% of Eden.
Minor vs major vs full GC — what is the difference?
Minor / young GC: collects the young generation only. Frequent, short, copying, always stop-the-world. Major GC: collects the old generation. Rare, much longer, mark-sweep(-compact). Full GC: everything — young + old + metaspace-related work — usually with a long stop-the-world pause, and often a sign of trouble (heap genuinely too small, promotion failure, or an explicit System.gc()). Note the terms are used loosely in the wild; the precise thing to say is "young collection" versus "old/whole-heap collection", and for G1 also mixed collection — a young collection that also evacuates some old regions.

Also worth naming: Shenandoah (-XX:+UseShenandoahGC) — concurrent compaction like ZGC, developed at Red Hat; Epsilon (-XX:+UseEpsilonGC) — a no-op collector that never reclaims anything, used for benchmarking allocation cost and for jobs that are expected to exit before the heap fills; and CMS, removed in Java 14, whose concurrent-mark-sweep design G1 replaced.

How would you choose a collector for a service?
Frame it as a trade-off, not a favourite. "Start with the default, G1 — it gives predictable pauses at a small throughput cost and you can ask for a target with -XX:MaxGCPauseMillis. If it is a batch job where total wall-clock time is all that matters and pauses are invisible, Parallel gives the best raw throughput. If it is a latency-sensitive service with a p99 requirement in single-digit milliseconds, or a heap over ~32 GB, use ZGC and accept the extra CPU. If it is a small container with one CPU and a small heap, Serial is genuinely the fastest because it has no coordination overhead. Then I would validate with GC logs — -Xlog:gc* — rather than guessing."
What is G1 actually doing differently? Why the name "garbage first"?
G1 abandons fixed generation boundaries. The heap is divided into ~2048 equal-sized regions, and each region is dynamically labelled Eden, Survivor, Old or Humongous — the young generation is just "whichever regions are currently Eden", so it can grow and shrink. Marking happens concurrently with your application, producing a per-region estimate of how much garbage it holds. Then, in a short stop-the-world evacuation pause, G1 copies live objects out of the regions with the most garbage first — best value per millisecond spent — and only as many regions as fit the pause target. Regions it evacuates become instantly free. The cost is bookkeeping: remembered sets tracking cross-region references, maintained by write barriers on every reference store.
How can ZGC move objects without stopping the application?
Two mechanisms. Coloured pointers: ZGC stores metadata bits inside the 64-bit reference itself (marked, remapped, finalizable), so the GC state of an object is readable from the pointer with no memory lookup. Load barriers: every time your code reads a reference from the heap, a few injected instructions check those colour bits — and if the object has been relocated, that read fixes the pointer on the spot before your code sees it. So relocation can happen concurrently: the application may hold stale pointers, and the first thread to touch one repairs it. Pauses shrink to a handful of root-scanning operations, which is why ZGC pause times are independent of heap size — the thing that makes it usable at terabyte scale.

9.4 · reference strengthsFour ways to hold an object

You can tell the collector how badly you want an object kept. This comes up whenever caches are discussed.

Strong
Order o = new Order(); — the normal kind. Never collected while reachable.
Default. If you have a leak, this is what is holding it.
Soft
SoftReference — collected only when the JVM is about to run out of heap.
Memory-sensitive caches. In practice unpredictable; prefer a real cache with an eviction policy.
Weak
WeakReference — collected at the very next GC once no strong reference remains.
Canonicalising maps, listener registries. This is what WeakHashMap and ThreadLocal keys use.
Phantom
PhantomReference — get() always returns null; you are only notified after finalization.
Deterministic cleanup of native resources. The modern Cleaner API is built on it.
Common wrong answer "Java can't have memory leaks, the GC handles it." Java leaks constantly — through unintended reachability. The classic four: a static collection that only ever grows; listeners/callbacks registered and never removed; ThreadLocal values on a pooled thread that outlives the request; and ClassLoader leaks where one lingering reference keeps an entire redeployed application's classes alive in metaspace. All four are "working as designed" — the GC correctly refuses to collect objects you can still reach.
Common wrong answer "Increasing -Xmx fixes GC problems." It changes the shape of the problem. A bigger heap means less frequent collections but more live data to trace, so each old-generation pause gets longer. If pauses are your problem, a bigger heap can make it worse. The fix is usually to reduce allocation rate or retention, or to switch to a concurrent collector — not to add gigabytes.

10.2 · the interactionsWhere one stage changes another

ConnectionWhat actually happens
JIT → GCEscape analysis removes allocations, so a well-inlined hot path produces far less garbage than the same code interpreted. This is why GC pressure often drops after warm-up with no code change — and why measuring allocation rate in the first second of a benchmark is meaningless.
GC → JITGC needs every thread at a safepoint. Compiled code contains safepoint polls; if C2 proves a counted int loop is short it may omit them, so a long-running loop can delay a collection — "time to safepoint" — and the pause you see in logs is longer than the GC work itself.
Class loading → MetaspaceEvery loaded class occupies metaspace, freed only when its whole ClassLoader becomes unreachable. One lingering reference to one object from a redeployed app pins every class it loaded. This is the mechanism behind OutOfMemoryError: Metaspace after N redeploys.
JIT → native memoryCompiled code lives in the code cache, which is native memory outside -Xmx. Aggressive inlining and thousands of generated classes inflate it; when it fills, the JIT switches off and throughput silently collapses to interpreted speed while the heap looks fine.
Threads → native memoryEach thread costs a full stack (-Xss, often 1 MB) in native memory, again outside -Xmx. 2,000 threads ≈ 2 GB the heap graph never shows. The usual reason a container is killed by the kernel while heap usage looks healthy.
Deopt → profileA deoptimization does not just discard code — it updates the profile so the recompile does not repeat the same bad guess. Repeated deopts on one method (a "deopt storm") mean the call site is genuinely megamorphic and no speculation will stick.
Allocation rate → pause frequencyYoung collections are triggered by Eden filling. Halving your allocation rate halves the number of pauses without changing their length — usually a bigger win than any flag.

10.3 · the cheat sheetOne-line answers worth memorising

Execution & JIT

• Bytecode is portable stack-machine code; no CPU runs it directly.

• Loading → linking → initialization. Linking = verify, prepare, resolve. Preparation (Stage 03) gives defaults; <clinit> gives real values.

• Parent delegation exists for security; class identity = name + loader.

• Tiered compilation: 0 interpreter, 1 C1-terminal, 2 C1-limited-profile, 3 C1-full-profile, 4 C2.

• C1 = fast to compile, ~5×. C2 = slow to compile, 10–50×, speculative, profile-driven.

• Compilation is asynchronous on compiler threads; the app never blocks.

• Inlining first — it is what makes every other optimization possible.

• Deoptimization is normal and is what makes speculation safe.

Memory & GC

• Objects on the heap, references anywhere; primitives follow their container.

• Per thread: stack, PC register, native stack. Shared: heap, metaspace, code cache, string pool.

• Metaspace replaced PermGen in Java 8 and is native memory.

• Allocation is a pointer bump in a TLAB — that is why new is cheap.

• Garbage = unreachable from GC roots, so cycles are collected fine.

• GC cost scales with live data, not with garbage.

• Young = copying + compacting, two survivor spaces, promote at age 15.

• Serial tiny, Parallel throughput, G1 balanced default, ZGC sub-ms pauses.
